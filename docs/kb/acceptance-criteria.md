# 完成标准要「可观测」

## 出处
- Martin Fowler《Given When Then》：<https://martinfowler.com/bliki/GivenWhenThen.html>
  核心：把验收写成**可观察的结果**（给定什么、做了什么、观察到什么），而不是一句愿望。

## 它怎么做的
「做好这个 issue」无法验收；「给定输入 X，调用 Y，返回 200 且日志有 Z」可以。
差别在于**有没有一个外部可检验的观察点**。

## 我们能怎么用
主理鱼的唤醒消息就是任务书。原来结尾是一大句：

> 完成标准 = 有测试结果：没跑测试不算完成，跑不了就写清原因；做完一条就写回 GitHub，并调用 watch_ack …

信息都在，但**不可逐条核对**。改成独立的三条（最多 4 条）：

```
【完成标准】
1. 改了什么：文件清单 + 一句话为什么（别只写"已修复"）
2. 怎么验证的：跑过的测试/命令 + 结果；跑不了就写清为什么跑不了
3. 回写到哪：推分支并开 PR（隔离模式下）/ 在 issue 里留言 + watch_ack 打标签
```

第 3 条会随「是否隔离执行」变化 —— 有 worktree 时要求开 PR，否则只要求在 issue 里留言。

## 是否已落地
✅ 0.8.58（`watch.js:formatWatchText` 的 `criteriaLine` + `index.js` 传入三条）。
用例：必须出现【完成标准】、按序号列出、超过 4 条丢弃、不传时退回原一句话。

## 还没做的
- 没有按仓库 `AGENTS.md` 动态提取标准（现在是固定的三条框架）；
- 没有让客户自定义标准（`entry.goal` 目前只影响「本条目主理目标」那一行）。
