# 给数量设上限，要能说出"为什么是这个数"

## 出处
- 资源上限的正确姿势：**上限来自实测/成本模型，不是"看着差不多"**。
  Kubernetes 的 ResourceQuota 文档也强调上限要按命名空间的实际需求来设：
  <https://kubernetes.io/docs/concepts/policy/resource-quotas/>

## 现场
之前没有上限：客户可以给一条会话挂 200 条守 —— 每条每 60 秒轮询，
`/state` 再压缩也挡不住真实的请求量与上下文压力。

## 为什么是 20
- 一条守每 60 秒一次 = 每分钟 1 次请求；20 条 = 每分钟 20 次，约 2 秒一次；
- 再往上，GitHub 速率 + 会话被叫醒的频率都会明显超出"一个人能处理"的量；
- 面板一屏也放不下更多（20 行已经需要滚动）。

**说不出理由的上限会被人绕过；说得出理由的上限会被接受。**

## 改法
```js
const MAX_WATCHERS_PER_SESSION = 20
// 拒绝时的文案要给出路：
// 「一条会话最多挂 20 条守（现在 20 条）—— 先 watch_stop 停掉不用的，或把多个仓库合成一条规则」
```

## 批量必须整批校验
第一版只在"单条写入前"检查 → 19 条时一次加 2 条会**只写进去第一条**。
补了整批预校验：`这次要新增 2 条`，并整批拒绝。

## 是否已落地
✅ 0.9.92。用例覆盖：20 条为止 / 第 21 条被拦 / 19+2 整批拒绝且不写入 / 更新不受影响。

## 还没做的
- 上限不可配置（客户没法"我知道风险，给我 50 条"）；
- 面板上没显示"X/20"，客户只有撞到错误才知道有上限。
