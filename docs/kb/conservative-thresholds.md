# 用历史影响判断时，阈值要故意定高

## 出处
- 这是"告警疲劳"的老问题：阈值定得太松，提示会变成噪音，最后没人看
  （Google SRE 关于 alerting 的章节反复强调"只对需要人介入的情况告警"）。
  <https://sre.google/sre-book/monitoring-distributed-systems/>
- 我们要用历史（近 7 天日均）影响判断，风险是**误报**，所以阈值取了保守值。

## 规则（`busierThanUsual`）
| 条件 | 结论 |
|---|---|
| 历史不足 3 天 | 不提示（没有基线） |
| 历史日均 = 0 | 不提示（除零无意义） |
| 今天 < 日均 × 2 | 不提示 |
| 今天 ≥ 日均 × 2 | 提示「今天明显比平时忙 —— 上限可能不够用」 |

阈值下限写死 1.5 倍（即使调用方传了更小的 factor 也不会更低）。

## 为什么"宁可不提示"
- 历史基线的用途是**发现异常**，不是制造焦虑；
- 一次误报会让客户开始忽略所有提示，代价远大于少提示一次；
- 真积压的情况已有另一条更硬的信号：`sessionUsage.capped > 0`（有守真被挡住了）。

## 判断放在哪侧
阈值计算放在**服务端**（`busierThanUsual`），`/state` 回传 `busy: true/false`，
面板只负责显示。理由与 0.9.21 那条一致：**面板不要再实现一份判断逻辑**。

## 是否已落地
✅ 0.9.35。用例：历史不足 / 日均 0 / 不到 2 倍 / 刚好 2 倍 / 明显更忙 / 坏输入；
面板用例覆盖 busy=false 不提示、busy=true 提示且给出原因。

## 还没做的
- 没有"连续 N 天都偏高"的升级提示（那更像趋势问题，需要更长数据）；
- 没有让客户自己调阈值（现在是常量，写死在服务端）。
