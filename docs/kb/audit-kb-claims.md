# 知识库的 ✅ 不能只靠自己声称

## 出处
- 这是"自证"问题的通用形态：任何**只由自己维护的索引**都会漂移。
  对照 SBOM / 供应链里的做法：组件清单要能被**外部数据源交叉验证**，
  不是"我们保证它是准的"（<https://www.cisa.gov/sbom>）。
- 我们这里的"外部数据源"就是 `CHANGELOG.md` —— 它来自提交历史，比 KB 的自由文本硬。

## 做了什么
`scripts/audit-kb-claims.mjs`：

1. 从 `CHANGELOG.md` 抽出所有已发布版本号；
2. 扫 `docs/kb/*.md` 里每条 `✅ … x.y.z`；
3. 逐个核对版本是否真的发布过；
4. 同时检查每篇是否写了「是否已落地」（KB 的固定格式要求）。

## 实测（本机）
```
知识库文档        71 篇
CHANGELOG 版本    152 个（最新 0.9.22）
✅ 声明            68 条
没写落地状态的     0 篇
PASS 所有 ✅ 的版本都能在 CHANGELOG 找到对应发布
```

**68 条 ✅ 全部有据** —— 这次没有抓到假声明，但**抓到过口径问题**：
最初的实现要求"✅ 与版本号在同一行"，于是三篇早期文档（`list-path-decision` /
`no-sse-decision` / `rate-limit-pools`）被判成"没写落地状态" ——
它们其实写了 `## 是否已落地`，只是结论是"不做"或"⚠ 部分"。
**审计器的口径错了，会给出假警报**；改成"有该段落即算写了状态"之后才归零。

## 已接进门禁
`preflight --fast` 第 **11** 项：`PASS 知识库有据　68 条 ✅ 都能找到发布`。
这样以后写 KB 时随手编一个版本号，会在验收时被挡住。

## 是否已落地
✅ 0.9.23。

## 还没做的
- 只核对"版本存在"，不核对"内容确实在这个版本里"（那要 diff CHANGELOG 正文，误报率高）；
- ~~没有检查 KB 里提到的文件名是否存在~~ → **0.9.24 已加**（见下）

## 0.9.24 追加：文件路径也交叉验证
再扫一遍 KB 里形如 `scripts/…` / `lib/…` / `docs/…` 的路径，逐个 `existsSync`。
实测 26 个路径里抓到 1 个漂移：`docs/kb/docs-four-kinds.md` 写的 `UPDATING` 路径前缀写错了（真实文件在**仓库根目录**）。已改正。

这条门禁的收益是实打实的：**KB 里的路径是客户会照着去找的**，写错等于把人带进死胡同。
