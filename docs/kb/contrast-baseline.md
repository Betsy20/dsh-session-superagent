# 对比度门禁为什么要有基线

**是否已落地**：是。**落地状态**：✅ 0.9.191（audit-contrast.mjs + contrast-baseline.json，已接进 preflight）

面板的对比度体检（`scripts/audit-contrast.mjs`）会把**每一处**文字与控件边界都按 WCAG 2.1 算一遍。
问题在于：DSH 官方设计语言里大量用**细边框**（0.5px 的分隔线、幽灵按钮的描边），
它们的比值天然只有 1.3–1.9 —— 而 WCAG 1.4.11 要求控件边界 ≥3:1。

于是「脚本全绿」这件事根本做不到，除非把官方设计语言整个推翻。**拿退出码直接当门禁 = 天天红 = 门禁失效。**

## 做法：基线只许变小

`test/fixtures/contrast-baseline.json` 记着当前的不达标条数。preflight 里那条检查
**只在「比基线多」时报红**：

```
浅色 34 组 / 深色 32 组（不高于基线）   ← PASS
浅色 41 组 > 基线 34                    ← FAIL
```

## 判据：不达标要分三类，别一刀切

1. **文字**（正文 4.5 / 大字 3）—— 真该修，修一处就把基线调小；
2. **控件边界**（输入框/按钮描边，1.4.11 要求 3）—— 该修，但改动面大，先登记；
3. **装饰性分隔线** —— WCAG 不强制，**列出来供参考，改不改看设计**。

## 真机教训

- 0.9.190 修浅色对比度时，我把 `.dt-stat-btn .dt-stat-unit` 只替换了后半截，
  留下一个悬空的 `.dt-stat-btn`（被注释吃掉）→ 变成后代选择器 → **只修好了一半**。
  基线从 40 组 → 37 组这种「看起来改了」的数字，必须配上「哪几条消失了」才算数。
- 只跑浅色会漏：深色主按钮文字 4.09、深色占位符 3.81 都是只跑一个主题发现不了的。
