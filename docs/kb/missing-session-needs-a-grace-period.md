# 「找不到会话」要分「还没加载」和「真的没了」

## 出处
- 真机现场：2026-11-04 重启宿主后，本仓库那条守第一轮轮询就报
  `会话已不在：请删除或重建这条主理鱼` —— 而那个会话当时**正开着**（就是当前对话）。
- 同族判据：[失败要分「会不会自己好」](failure-classes-need-different-actions.md)。

## 现场

```
宿主刚启动 → agents.get(sessionId) 短暂返回 undefined
  → pollOnce 判定「会话已不在」→ setEntryError + bumpFailure（退避）
  → 面板红字：请删除或重建这条主理鱼
```

三分钟后再轮询一次，会话已被加载，错误自己消失了。

## 为什么这条特别糟

1. **给的是不可逆建议**：客户照做就会删掉一条好好工作的守，水位、历史、隔离区全没了；
2. **退避是冤枉的**：这不是失败，是启动时序；
3. **它会自己好**：三分钟后什么都没发生过 —— 但客户已经删了。

## 判据

**凡是"资源暂时查不到"的判定，先问一句：它有没有可能在几秒后再出现？**

- 有可能 → 用**宽限期 + 计时**，期内只记 `lastDeferred`（不记失败、不退避）；
- 过了宽限期才判死，且错误文案要带上「等了多久」「确认后再决定」。

本仓库的落地：`sessionMissingVerdict()`，宽限期 10 分钟（≈5 个轮询周期）。
第一轮只记起点，期内提示「约 N 分钟后仍找不到才报错」，超时才报
「会话已不在（连续 N 分钟找不到）：确认该会话是否已被删除，再决定是否重建」。

## 是否已落地
✅ 0.9.173：`lib/watch.js` 的 `sessionMissingVerdict` + `lib/index.js` 接入，2 条用例覆盖
（宽限期内不判死 / 超期判死 / 时间戳坏掉也不卡死）。

## 还没做的
- 其他"暂时查不到"的场景（仓库 404、凭证刚失效）没有同样的宽限期，仍按永久失败处理；
- 宽限期长度是拍的（5 个周期），没有真实启动耗时分布支撑。
