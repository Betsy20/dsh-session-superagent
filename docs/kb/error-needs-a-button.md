# 错误旁边要有按钮，不能只有建议

## 出处
- 可用性启发式里"帮助用户识别、诊断并从错误中恢复"是**三条要求**，最后一条（恢复）最常被漏掉：
  <https://www.nngroup.com/articles/ten-usability-heuristics/>
- 光写"请检查 token"等于把恢复工作全甩给客户。

## 现场
上一版把错误拆成「现象 + 建议」两句，但**建议仍是文字**：客户读完还得自己找地方点。
而三种错误的正确动作完全不同：
| kind | 客户要做的 |
|---|---|
| auth | 去设置页填 token |
| moved / notfound | 改仓库地址 |
| network / ratelimit | 等一会儿再试一次 |

## 改法
- `/state` 每条守增加 `lastErrorKind`（服务端用 `classifyGhError` 算一次，面板不解析中文）；
- 面板按 kind 渲染按钮，点一下就到下一步：

| kind | 按钮 | 去哪 |
|---|---|---|
| auth | 去填 token | 设置页 |
| moved / notfound | 改仓库地址 | 触发页 |
| network / ratelimit / gateway | 立刻重试 | 直接重跑这一轮 |
| 其它 | 不给按钮（**不猜**） | — |

## 判据
**"下一步"必须是可点的东西。** 如果只能说"请检查 X"，说明我们还没想清楚客户具体该动哪只手。

## 顺带撞到的一条
新按钮的文案来自变量（`fix.label`），`ui-audit` 的"图标按钮缺可读名字"当场报红 ——
加 `aria-label` 才过。**体检盯的是可访问性，不是文案长度。**

## 是否已落地
✅ 0.9.98。新增 1 例：四种 kind 各出现对应按钮，未归类的不给按钮。

## 还没做的
- 「立刻重试」在退避期内会不会被后端拒绝，没有单独提示；
- 面板上没把 kind 显示出来（客户只看按钮，看不到分类）。
