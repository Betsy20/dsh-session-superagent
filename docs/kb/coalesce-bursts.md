# 三个守同时有动静 ≠ 三条消息

## 出处
- Google SRE Book《Handling Overload》里的核心思想：**过载时要"减少工作"而不是"更快地失败"**，
  常见手段就是合并/丢弃（coalesce & shed），并强调不要用"重试放大"去解决。
  <https://sre.google/sre-book/handling-overload/>

## 实测（本轮）
同一会话挂 3 个守、间隔都是 60 秒，首轮抖动 `jitterMs(id, min(5000, every*0.1))` 只把相位拉开一点：

```
三个守的首轮相位（毫秒）: 1184 / 2145 / 3106
相邻两次唤醒的间隔（秒）最小/中位/最大: 0.96 / 0.96 / 0.96
```

关键在于：**抖动是一次性的**，之后每个守按自己的 `every` 推进，相对相位几乎不变 ——
所以每一轮都会在约 1 秒内连着收到 3 条注入。5 个守就是 5 条。

## 为什么不设"最小间隔"（那是错的）
最直觉的做法是"30 秒内不许再唤醒"。但先到的守会**永远赢**，后面的守永远被挡 —— 饿死。
（这和限流里"固定窗口让突发者占名额"是同一类问题。）

## 改法：合并
同会话 3 秒窗口内的多条唤醒，攒成一条再注入：

```
【主理鱼】这一小段时间内有 3 处变化，合并成一条：

—— 第 1 处 ——
repoA 有 2 条新动态…
—— 第 2 处 ——
repoB 有 1 条新动态…
```

- 单条时**不加任何包装**（不打扰原本体验）；
- 窗口 3 秒：单守场景最多延迟 3 秒，几乎无感；
- 合并发生在"注入前"，`decideWake`（会话是否 idle）在真正发送时再判，比原来更新鲜。

## 是否已落地
✅ 0.9.3（`watch.js:mergeWakeTexts` + `index.js:wakeMerged`）。
用例：空输入、单条不包装、全空白丢弃、三条合并要有"3 处变化"与逐段分隔且内容不丢。

## 还没做的
- `wakeTimes` 在**入队**时就记录（不是发送成功时），所以合并且最终发送失败会多计一次；
  影响很小（退避与上限会自然收敛），但值得记下来；
- 没有把合并后的条目按仓库分组去重。
