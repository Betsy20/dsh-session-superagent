# "本轮"和"累计"混用，数字就会撒谎

## 出处
- 与"速率 vs 总量"的经典混淆同源：监控里看 QPS 与看累计计数器是两个问题，
  混用会让人对趋势判断完全错误（Prometheus 文档对 counter 与 rate 的区分：
  <https://prometheus.io/docs/practices/instrumentation/#counter-vs-gauge>）。

## 发现（两处都真实存在）
1. **累计冒充本轮**：`entry.filterCounts` 从创建守起一直累加，
   而唤醒消息写的是"同时跳过 …"，读起来像本轮 —— 跑一上午后这个数字会大得离谱；
2. **只报原因不报总数**：只列前 3 个原因（`slice(0, 3)`），被截掉的完全看不见，
   读者会以为"就跳过了这几条"。

## 改法
- 每轮开始**重置** `filterCounts`（语义明确成"本轮"）；
- 消息行改成：
  ```
  本轮跳过 9 条（已关闭 × 5、机器人 × 2、草稿 PR × 1 等）
  ```
  有总数、有前三个原因、被截断标"等"。

## 为什么之前没人发现
消息里的这行**只在有跳过时出现**，而演示数据一直是空 `skippedReasons: {}` ——
**离线演练脚本根本没走过这条分支**。这再次说明：演练脚本的样例要覆盖异常分支。

## 是否已落地
✅ 0.9.52。用例断言总数 = 5+2+1+1 = 9、前三个原因都在、第四个不列、标"等"、无跳过时不出现该行。

## 还没做的
- 演练脚本（`first-run.mjs`）仍用空的 `skippedReasons`，没把这条分支演示出来；
- 其它"累计"字段（如 `silentWakes`）语义没有逐条复核。
