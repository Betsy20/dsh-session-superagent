# 「需要关注」的排序是一个决策，不是默认行为

## 出处
- 告警设计的常识：**同样的信息，顺序不同，行动顺序就不同**。
  PagerDuty / SRE 实践里"severity 决定谁先被叫起来"，本质就是排序规则：
  <https://sre.google/sre-book/managing-incidents/>

## 现场
面板「需要关注」原来按**发现顺序**往数组里塞：先结构问题、再只读、再没回音、再失败……
结果 `仓库已归档` 这种**静态提示**可能压在一堆**正在丢消息**的问题上面。

## 做法
给每类问题一个权重（`rank`），排序按 rank 升序、同权重按文本：
| rank | 类型 | 为什么排这个位置 |
|---|---|---|
| 0 | gh 不可用 | 所有轮询都会失败 |
| 1 | 轮询失败 | 正在丢消息 |
| 2 | 叫醒后没回音 | 消息进去了但没人处理 |
| 3–5 | 结构 / 只读 / 重开 | 需要人看，但不会立刻丢 |
| 6–7 | 暂停 / 未配置 token | 提示性 |

顺带修掉一个**重复推送**：`structure` 那条被 push 了两次，列表里会出现两条一模一样 ——
排序前先保证"同一条只出现一次"。

## 验证
把排序语句替换成 `void 0` → 用例立刻红（`轮询失败` 不再排在 `已归档` 前面），恢复后绿。

## 判据
**任何"列表"都要回答：第一行是谁？为什么是它？** 答不上来就说明顺序是随机的。

## 是否已落地
✅ 0.9.87。用例锁住四条相对顺序。

## 还没做的
- 权重是拍定的，没有真实事故数据支撑（例如"没回音"是否该排在"轮询失败"前面）；
- 面板列表行内没有显示 rank 或"为什么排这"。
