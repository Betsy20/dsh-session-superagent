# 追溯要能指名原因，而不是列举可能性

## 出处
- 可解释性的最低标准：**能指出具体那一个原因**，而不是"可能是 A/B/C"。
  这与"可解释的判定"同源（我们自己的 KB `filter-explainability.md`），但这里多一层要求：
  **原因要在发生的那一刻被记下来**，事后才有得说。

## 现场
客户问「#42 为什么没叫醒我」，`watch_trace` 原来答：
```
已记入水位但没唤醒（被吸收/仅观察/或上报前就已存在）
```
三合一 = 没说。根因很具体：**"被冷却期吸收"这件事从来没被记录过**，
只留了一个总数 `lastAbsorbed`。

## 改法
```js
// 吸收时记一条（有界 50 条）
entry.absorbedLog = pushAbsorbed(entry.absorbedLog, absorbed, entry.lastPoll)

// 追溯时读它
else if (absorbed.length > 0) verdict = '被冷却期吸收了（' + at + '）—— 那一批刚唤醒过，等下一轮'
```

## 判据
- 任何"多选一的模糊结论"，都说明**当时该记的东西没记**；
- 记的时候要有界（否则日志会长成几 MB），50 条足够回答最近的问题。

## 是否已落地
✅ 0.9.78。文本 + JSON 都带 `absorbed`；契约清单已登记 `stable`。

## 还没做的
- 「仅观察模式」下被跳过的条目仍走 `seen` 分支（结论里"仅观察"是猜的，没有硬证据）；
- 吸收日志是**每守 50 条**，跨守查同一条要逐个查。
