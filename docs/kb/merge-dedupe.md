# 合并之后还要去重：同一段【完成标准】不该出现三遍

## 出处
- 与上一条同源（SRE《Handling Overload》的 coalesce）：**合并是第一步，去重是第二步**；
  合并只减少了"消息条数"，重复的样板文字仍然占着上下文。
  <https://sre.google/sre-book/handling-overload/>
- 具体的"别重复告诉读者同一件事"属于写作/信息设计的常识，这里靠**实测长度**判断值不值得做。

## 实测
三条唤醒（两条/一条/一条）直接拼接：

```
合并长度: 1065 字符
【完成标准】出现 3 次
goal 行出现 3 次
```

样板段落（完成标准、本条主理目标）在每条里都一样 —— 合并后纯属噪音，且占长度近一半。

## 改法
`mergeWakeTexts` 在拼接前先过一遍：
1. **【完成标准】块**：内容完全相同 → 只留第一份；**不同则各自保留**（不同仓库的标准可能确实不同）；
2. **`本条目主理目标：`行**：同上。

实测效果：

```
合并长度: 1066 -> 575 字符（-46%）
【完成标准】3 -> 1 次；goal 3 -> 1 次
```

## 是否已落地
✅ 0.9.4。用例：完成标准相同只留一份、目标行只留一份、两个仓库内容都在、合并后显著短于简单拼接；
完成标准**不同**时必须都保留（防止误删）。

## 还没做的
- 只按"整块完全相同"判断，没有做行级相似度合并（收益小、风险高）；
- 条目行本身若高度相似（同一 issue 在两次唤醒里重复）不会去重 —— 那种情况靠 seen 水位本来就不该发生。
