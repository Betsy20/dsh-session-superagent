# 要不要改成 SSE 推送？—— 量完，不值得

## 出处
- HTTP/1.1 与 SSE（`text/event-stream`）：<https://html.spec.whatwg.org/multipage/server-sent-events.html>
- 条件请求（我们已用）：<https://www.rfc-editor.org/rfc/rfc9110.html#section-13>

## 数字（本机实测，2026-11-02）
```
GET /session-superagent/state
  200: 0.002052s / 0.002166s / 0.002003s   （本机回环，空仓 1815 B）
```
- 面板轮询间隔 5 秒 → **720 次/小时**；
- 每次 ≈ **2 ms** → 一小时 ≈ **1.44 秒**；
- 0.8.85 之后其中 ≥99% 是 **304（无正文）**。

## 结论：不改 SSE
要换 SSE 需要：长连接生命周期管理、断线重连、与宿主重载的交互（我们已经被重载坑过两次）、
流上鉴权、以及"多面板同时打开"的连接复用。**换来的是每小时 1.44 秒和几乎为零的流量**。
收益与复杂度严重不成比例 —— 不做。

真正该做的（已做）：
1. 0.8.84 减字段（3.8 → 2.2 KB/守）；
2. 0.8.85 ETag/304（没变化零正文）。

这两步已经吃掉 95% 的可优化空间，剩下的靠 SSE 只是零头。

## 是否已落地
✅ 结论 + 数字记录在案；**代码不改**（这是有意识的选择，不是遗漏）。

## 附带发现（重要）
本机实测线上 `/state` 的 `serverVersion` 是 **0.8.38** —— 而仓库已经到 0.8.85。
服务端代码改动只有**重启宿主**才生效，所以最近 40 多个版本的服务端改进
（ETag、诊断、限流、GraphQL 批量、关联 PR、租约…）**目前都还没在真机跑起来**。
按本机铁律，重启必须由用户执行，我只准备步骤。
