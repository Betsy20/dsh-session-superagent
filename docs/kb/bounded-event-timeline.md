# "为什么没叫醒我"要有据可查：有界事件流

## 出处
- OpenTelemetry 对 log record 的定义：**时间戳 + 主体 + 结构化属性**，
  可读性交给展示层（<https://opentelemetry.io/docs/concepts/signals/logs/>）。
- 有界这一点来自日志系统的普遍做法：内存/状态里只保留最近 N 条（ring buffer），
  否则"记录一切"会变成新的故障源。

## 我们原来的状态
只有一个 `lastDeferred` 字符串 —— 它**只描述最后一次**，看不出前后因果。
客户问"我加了标签为什么一条都没叫醒"，我们只能看到屏幕上那一句，
再加上 `filterCounts` 的累计数，仍然拼不出时间线。

## 改法
`pushEvent(events, event, max = 20)`：每条 `{ at, kind, text }`，**有界 20 条**，
`kind` 截断 24 字符、`text` 截断 160 字符（防止脏数据撑大状态文件）。

打点位置（都在**既有分支**里，不新增逻辑）：

| kind | 什么时候 |
|---|---|
| `defer` | 不在活跃时段 |
| `ratelimit` | 被 GitHub 限流（按 Retry-After 等） |
| `unchanged` | 304 未变化 |
| `observe` | 仅观察，本轮本会唤醒 N 条 |
| `cap-session` | 撞会话级小时上限 |
| `cap-watcher` | 撞单守小时上限 |
| `wake` | 真的唤醒了（带条号） |
| `wake-failed` | 唤醒被拒（会话忙等） |

面板「判定」页新增「时间线（最近 20 条）」，按类型着色（唤醒绿 / 失败红 / 其它中性）。

## 是否已落地
✅ 0.9.8。用例：
- 纯函数：无 kind 的事件丢弃、30 条只留最近 20、超出长度被裁剪、带时间戳；
- 面板：判定页必须出现「时间线」、事件类型 `cap-session`、以及人话内容。

## 还没做的
- 没有导出（复制全部事件）按钮；
- 事件没有做去重（同一原因连续 10 轮会占满 20 条）—— 可以改成"连续同类合并计数"，但那会牺牲时序感。
