# 一次只能处理 N 条时，先处理"更该处理的"

## 出处
- GitHub REST《List repository issues》支持 `sort=created|updated|comments`（服务端排序）：
  <https://docs.github.com/en/rest/issues/issues#list-repository-issues>

## 它怎么做的
服务端排序是"热度/时间"维度：哪条更新、哪条评论多。

## 我们能怎么用（以及为什么不用它）
我们要的不是"热"，是"**哪条更该现在处理**"。所以本地排，权重可解释、可测：

| 信号 | 权重 | 理由 |
|---|---|---|
| `state_reason === 'reopened'` | **100** | 之前判过"不做"被推翻，最该看 |
| `comments > 0` | **10** | 有人在等回应 |
| 有标签 | **5** | 命中过某个分类 |
| 其他 | 0 | 保持 GitHub 给的 updated 顺序 |

实现要点：**稳定排序** —— 分数相同就保持原相对次序，否则同一批条目每次顺序都不一样，
客户会以为数据在乱跳。用例专门验了"多次调用顺序一致"。

## 是否已落地
✅ 0.8.75（`watch.js:priorityScore` + `batchFresh` 排序后取前 N）。
用例：单项权重、组合权重（100+10+5=115）、重开第一/有评论第二、稳定排序。

## 还没做的
- 权重是拍的，没有数据支撑（要调就得看客户实际处理顺序）；
- 没有让客户自定义权重（可做成配置，但先别加面）。
