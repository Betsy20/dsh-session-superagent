# 有了原因码，就要能"按原因归类看"

## 出处
- 与 0.9.15 的「快捷筛选」同源，但这次筛选的**维度来自结构化字段**而不是文案：
  <https://www.nngroup.com/articles/progressive-disclosure/>（收窄之后必须有还原）
- 更直接的一条来自可观测性实践：日志要能**按维度聚合**（否则只是"一堆行"）。

## 上一轮留下的半成品
0.9.21 让服务端写 `deferReason`，但面板只是把它当字段传着玩 —— 客户仍然只能一行行看
"暂停唤醒：…"。**数据有了不等于用上了。**

## 改法
「判定」页新增一排「暂停原因」Pill：

```
暂停原因： [撞会话上限 ×2] [被 GitHub 限流 ×1] [清除]
```

- 值来自 `watcher.deferReason`（结构化字段，不解析文案）；
- 复用已有的 `reasonFilter` 状态槽位，内部用 `defer:` 前缀与「跳过原因」筛选区分；
- 选中后：**明细列表和「需要关注」一起收窄** —— 否则列表只剩一条、上面告警还列着别的仓库，自相矛盾。

## 两个实现坑
1. **常量要在组件最前面**：`DEFER_LABELS` 一开始定义在组件中段，判定页先用到 →
   `Cannot access 'DEFER_LABELS' before initialization`。它不依赖任何状态，就该放最前。
2. **筛选要贯彻到所有派生视图**：只筛列表不筛告警 = 自相矛盾。
   这次是靠用例"别的原因不该出现"抓出来的。

## 是否已落地
✅ 0.9.22。用例：原因码翻成人话（`撞会话上限`）、另一个原因也在、选中后只剩那一类。

## 还没做的
- Pill 的数量是当前快照，不是"这一小时累计"（要累计得服务端另存计数）；
- 没有把「暂停原因」做成时间线里的事件（时间线已有 kind，重复度较高）。
