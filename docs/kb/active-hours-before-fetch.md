# 时段判断要放在拉数据之前，不是之后

## 出处
- 同类的思路在 Renovate 的 `schedule` 配置里：**不在时间窗内就不去查更新**，
  而不是"查完再决定要不要发 PR"。
  <https://docs.renovatebot.com/configuration-options/#schedule>
- 通用原则：**把"不做"的判断尽量前移**，越靠前省的越多。

## 我们的问题（实测出来的）
`pollOnce` 里 `activeHours` 的判断原本在**拉完 API 之后**：

```js
const res = await run('gh', [ ... ])   // ← 先打一次 GitHub
...
if (entry.activeHours && !inActiveHours(entry.activeHours)) return   // ← 才决定不叫醒
```

后果：客户设了 `09:00-18:00`，**夜里 14 小时照样每 N 秒打一次 GitHub**。
按 60 秒间隔算，一夜 ≈ **840 次请求**（多数是 304，不计额度，但每次都要起一个 `gh` 进程 + 一次网络往返）。
而且开门后要等下一个周期才处理攒着的条目。

## 改法
1. 把时段判断**移到函数最前面**（拉数据之前）；
2. 不在时段内时，用 `msUntilActiveWindow()` 算出"还有多久开门"，把 `nextAt` 直接设到那一刻。

夜里实测语义（用例锁死）：
- 23:30 且时段 `09:00-18:00` → **9.5 小时**后开门；
- 07:00 → 2 小时；
- 跨夜 `22:00-06:00` 在 15:00 → 7 小时；
- 空/非法 → 0（当作一直活跃）；
- 最小 1 秒，避免 0 延迟死循环。

## 是否已落地
✅ 0.8.98（`watch.js:msUntilActiveWindow` + `pollOnce` 前置判断）。
用例 1 例 8 种情况；测试合计 **141 例**。

## 还没做的
- 没有统计"一夜到底省了多少次调用"（需要真机跑满 24 小时，属于宿主验证）；
- 时段内如果正好卡在 `nextAt`（退避中），开门那一刻仍会等退避结束 —— 这是刻意的（别让故障期间的守疯狂重试）。
