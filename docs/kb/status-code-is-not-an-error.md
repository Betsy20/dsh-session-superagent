# 状态码不等于错误：304 是"没变化"

## 出处
- RFC 9110 §15.4.5：**304 Not Modified 不是错误**，它表示"客户端缓存的表示仍然有效"：
  <https://www.rfc-editor.org/rfc/rfc9110#name-304-not-modified>
- 危险在于**工具层把它当失败**：`gh` CLI 对非 2xx 一律 exit 1，于是"没变化"看起来像"出错"。

## 现场（客户截图）
面板上出现一条"异常"的守：
```
gh: HTTP 304
（没归类的错误：已按退避自动重试；持续出现就跑 watch_doctor 看检查清单，或把这行贴给对方）
```
而 304 根本不是错误 —— 是我们自己加的条件请求命中了。

## 根因链
1. 我们给 GitHub 加了 `If-None-Match`（省速率限制）；
2. 没变化时 GitHub 回 304，`gh` 以 **exit 1** 结束；
3. 轮询的失败分支先命中 `res.code !== 0`，进了"出错"路径；
4. 代码里确实有一个 `parsed.status === 304` 的"未变化"分支 —— 但它在**成功分支**里，
   永远轮不到；
5. 最终落到 `classifyGhError` 的 `other`，文案变成"没归类的错误"。

## 改法
1. 失败分支先认 304 → 走"未变化"（清 `lastError`、重置退避、记事件 `unchanged`）；
2. `classifyGhError` 新增 `notmodified`：`（没有变化 —— 条件请求命中 304，这不是错误）`；
3. 面板：历史数据里残留的 304 也不再算「异常」。

## 判据
**加条件请求/缓存时，必须同时处理"工具把它当错误"的那条路。**
只在"成功分支"里写 304 处理，等于没写。

## 是否已落地
✅ 0.9.110。新增 2 例（分类表 + 面板计数）。

## 还没做的
- 其它非 2xx 但语义正常的码（如 301 已有分类）没有系统性梳理；
- 面板没有"未变化"这类良性状态的展示（只在事件流里）。
