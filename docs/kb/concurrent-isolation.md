# 并发隔离要证明"互不影响"，也要说清"哪里会打架"

## 出处
- `git worktree` 的设计目标之一就是"同一仓库多个工作区互不干扰"
  <https://git-scm.com/docs/git-worktree>。但"文档说互不影响"和"我们这里真的互不影响"是两件事。
- 冲突是 git 的合并语义：同一文件同一区域被两条分支改动，合并必然冲突
  <https://git-scm.com/docs/git-merge#_how_conflicts_are_presented>。

## 做了什么
`scripts/verify-concurrency.mjs`：两个会话对同一仓库开隔离区、改**同一个文件**、
各自提交、再合入主线，9 步全部打印结论。

关键几条：
```
PASS 各自改同一文件互不干扰　A 与 B 内容不同
PASS A 提交不影响 B 的工作区
PASS 两条分支各自独立提交
PASS 后合的会冲突（同文件同区域）
PASS 冲突可中止，仓库回到干净状态
```

## 它顺手抓到一个产品问题
隔离区在仓库内的 `.dsh-zhuli/`，默认是**未跟踪目录**：
客户一跑 `git status` 就看到一堆副本，甚至可能误提交。

修法：开隔离区前把它写进 `.git/info/exclude` ——
**本地生效、不进版本库、不改客户 `.gitignore`**（改客户的 .gitignore 属于越权）。

## 边界（要写进产品说明）
并发隔离成立，但**同一文件同一区域**被两个会话改动时，后合并的必然冲突。
这不是缺陷，是 git 的语义 —— 客户需要知道，否则会以为是产品 bug。
