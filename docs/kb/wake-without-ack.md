# 投递成功 ≠ 有人动手

## 出处
- RabbitMQ《Acknowledgements and Publisher Confirms》：**投递成功不代表处理完成**，
  消费者必须显式 ack 才算确认。
  <https://www.rabbitmq.com/docs/confirms>
- 把这个语义搬到我们这里：`wake()` 成功只说明消息进了会话，
  真正"处理了"的证据是后来出现了 `watch_ack`（给条目打「主理鱼:已处理」）。

## 我们原来的盲区
`wakeTimes` 一直在涨、面板显示"唤醒过 N 次"，看起来一切正常。
但客户真正会遇到的情况是：**守在工作、消息也进去了，会话却没动手** ——
原因是仓库的 `AGENTS.md` 没给规则，或者任务书里的完成标准被忽略。
现有指标**完全看不到**这种情况。

## 改法
`silentStreak({ previousWakeAt, lastAckedAt, previousStreak })`：

| 情况 | 结果 |
|---|---|
| 上一次唤醒之后**有** ack | 清零 |
| 上一次唤醒之后**没有** ack | +1 |
| ack 在唤醒**之前**（上一轮留下的） | 不算这次的回音，仍 +1 |
| 还没唤醒过 | 保持原状 |

连续 ≥ **2** 次时，面板「需要关注」出现：
> `repo 已连续 3 次唤醒后没有回音（没看到 watch_ack）—— 检查这个仓库的 AGENTS.md 有没有给出处理规则`

## 是否已落地
✅ 0.9.11（`watch.js:silentStreak` + `index.js` 唤醒回调里累计 + 面板提示 + `/state` 回传）。
用例 6 种情况：未唤醒过 / 无 ack 累加 / 有 ack 清零 / ack 在唤醒前不算 / 坏数据不崩 / 无参数不崩。

## 还没做的
- 阈值 2 是拍的（唤醒本身有成本，连续 2 次没回音已经很可疑；但没数据支撑）；
- 没有把"没有回音"与"被跳过"区分开（会话可能确实判断为无需处理 —— 那也该 ack，否则我们无从知道）。
