# 隔离区只按天数回收，管不住"堆"

## 出处
- `git worktree prune` 清理的是"目录已经不在的管理记录"，**不负责控制副本数量**
  <https://git-scm.com/docs/git-worktree#Documentation/git-worktree.txt-prune>
- 数量上限的思路来自所有"缓存/临时目录"的通用做法：**时间线 + 数量线**双保险
  （任何只靠其中一条的清理策略都会被极端情况绕过）。

## 实测数字（本轮）
| 场景 | 结果 |
|---|---|
| 合成测试仓库（3 MB 文件） | 每个 worktree **2.9 MB**（≈ 工作树大小，不含 `.git`） |
| 我们自己的仓库（工作树 1.3 MB） | 副本体积同量级 |

推演：上限 **6 次/小时** × 保留 **3 天** = 最坏 **432 个副本**。
按 10 MB/副本估 ≈ **4 GB**；按我们这种 1.3 MB 的小仓库也有 **560 MB**。

## 改法
`staleWorktrees(entries, { keepMs, keepCount })`：
1. **年龄线**：超过 `keepMs`（默认 3 天）→ 回收；
2. **数量线**（新增）：按 mtime 倒序，只保留最近 `keepCount`（默认 5）个，其余回收；
3. 两条线的结果去重，**最近 N 个无论多老都留着**（正在用的那个不能被删）。

配置：`entry.maxIsolated`（1–50，默认 5），面板「隔离」区可直接改，`/state` 回传。

## 是否已落地
✅ 0.9.0。用例：8 个都在 3 天内 + keepCount=5 → 回收最旧 3 个；
keepCount=100 → 只剩年龄线生效；超龄的（60 天）即使很新也回收；非法条目不让它崩。

## 还没做的
- 没有"磁盘占用超过 X MB 就回收"的第三条线（要遍历目录算大小，成本高）；
- 面板没有显示"当前有几个隔离区 / 多大"（`/state` 已有 `isolation` 汇总，可以接上）。
