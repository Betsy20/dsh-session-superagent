# "这条为什么没叫醒我"要能像 EXPLAIN 一样查

## 出处
- PostgreSQL 的 `EXPLAIN`：**不改变执行，只解释"为什么是这个结果"**
  <https://www.postgresql.org/docs/current/sql-explain.html>
- 我们要回答的是同类问题，但对象是"一条 issue 的命运"。

## 之前的状态
同一件事的数据散在三个地方：
- `seen[number]`（水位：≥ 这个时间点的更新才会再叫醒）
- `filteredLog`（被过滤的记录与原因）
- `history`（每轮唤醒成功/失败）

客户问"#42 为什么没叫醒我"，我得在脑子里把三者拼起来 —— 拼错就会给错答案。

## 做了什么
`itemTrace(watcher, number)` 把三处拼成一条**结论** + 明细：

| 情况 | 结论 |
|---|---|
| 被过滤 | `被过滤掉了：<原因>` |
| 唤醒成功过 | `已经唤醒过 N 次` |
| 记了水位但没唤醒 | `已记入水位但没唤醒（被吸收/仅观察/或上报前就已存在）` |
| 尝试过但都失败 | `尝试唤醒过 N 次但都没成功` |
| 完全没有痕迹 | `还没轮到它（可能还没被轮询到，或在批外）` |

两个入口：
1. **工具 `watch_trace`** —— agent 被问到时直接查，不用猜；
2. **脚本 `node scripts/trace-item.mjs <编号>`** —— 客户/维护者在命令行就能看，
   支持 `--demo`（内置样例，不读状态文件）与 `--state <path>`。

## 一个真实的实现坑
`String(null) === 'null'` 是**真值**，所以 `if (!target) return null` 拦不住 `null` 入参 ——
用例当场红了（期望 null，实际返回了一个 trace 对象）。先判断入参本身，再转字符串。

## 是否已落地
✅ 0.9.30。工具进了契约快照；用例覆盖"被过滤 / 已唤醒 / 唤失败 / 无痕 / null 入参"五种。
