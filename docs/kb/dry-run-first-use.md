# 写一条 5 分钟的演练脚本，比自己读一遍代码更能发现问题

## 出处
- 这是"可执行文档"（executable documentation）的轻量形态：README 会腐烂，脚本不会 ——
  它跑不起来就是失败。类似 `cargo doc --test` / Python doctest 的思路：
  **文档里的例子必须能被执行**。
- 我们的形态更简单：一个脚本，把产品真实产出的**文本**打印出来。

## 做了什么
`scripts/first-run.mjs`：不装宿主、不装 gh，用 `lib/watch.js` 的真实函数走一遍：

1. 轮询 3 条动态 → 哪些算「新」；
2. 按批大小挑 2 条；
3. **打印客户会读到的唤醒消息原文**；
4. 面板会看到的仓库汇总与徽章；
5. 异常情况的文案（归档 / 关闭 Issues / 只读）；
6. 过滤默认值。

跑一次不到 1 秒。

## 它第一次运行就抓到的 bug
```
#77 [open] 修复表头错位 … (PR)
（另有 1 条：#77，处理完这批再看）   ← 同一条出现两次
```

根因：剩余写成 `fresh.slice(listed.length)`，而 `batchFresh` 会**按优先级重排**，
切片拿到的是"原始顺序的尾巴"，可能包含已经选中的条目。

## 教训
**"读代码觉得没问题"和"看到输出"是两件事。**
这个 bug 在 168 个单测里没被覆盖，因为每个函数单独看都对；
错在两者的**组合**（重排 + 切片）。演练脚本的价值正是走完整链路。

## 0.9.53 追加：演练脚本必须覆盖异常分支
0.9.52 修的那个"累计冒充本轮"的 bug，藏了很久的原因很具体：
**演练脚本一直传 `skippedReasons: {}`，那条分支从没被走过。**

现在脚本第 3b 段用真实数据（已关闭 × 2、机器人 × 1、已 ack × 1）演示"有跳过时的同一条消息"：
```
【为什么是这几条】本轮共 7 条变化；按「最近更新」取前 2 条；本轮跳过 4 条（已关闭 × 2、机器人 × 1、已 ack × 1）
```
并纳入文案快照（47 → 50 行），以后每次改文案都会被看见。

**教训：演练脚本如果只跑主路径，它就只是"主路径回放"，不是演练。**

## 还没做的
- 脚本没有接进门禁（它是给人看的，不适合当断言，除非做成快照测试）；
- 没有覆盖"隔离执行"分支（需要 git 仓库，成本更高）。
