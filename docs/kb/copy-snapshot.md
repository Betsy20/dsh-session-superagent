# 客户读到的文字要有快照，改动必须是有意的

## 出处
- 快照测试（snapshot testing）的原始思路（Jest）：把"输出长什么样"固化成文件，
  变化时**显式确认**而不是默默漂移。
  <https://jestjs.io/docs/snapshot-testing>
- 用在文案上比用在结构上更合适：结构改动该被断言拦住，文案改动该被人**看一眼**。

## 做了什么
`scripts/first-run.mjs` 两个模式：

| 模式 | 作用 |
|---|---|
| `--write` | 把当前输出写成 `docs/示例-唤醒消息.md`（44 行，含完整唤醒消息） |
| `--check` | 与快照比对，不同则退出码 1，并提示怎么更新 |

实测（临时把 `【为什么是这几条】` 改掉）：
```
提示 客户会读到的文字有变化：约 1 行不同
      确认没问题后跑 node scripts/first-run.mjs --write 更新示例
exit=1
```

## 为什么值得做成门禁
- 文案是**客户唯一能读到的产品**，但它最容易被"顺手改一下"；
- 现有 168 个单测只断言"包含某个关键词"，改坏成"包含关键词但语义变了"完全测不出来；
- 快照把"整体读起来是什么样"固化下来 —— 它天然覆盖了排版、顺序、重复、缺失。

## 与"硬断言"的分界
- **硬断言**（单测）：必须是那样，不一样就是 bug；
- **快照**（本项）：这次确实变了，请确认 —— 人确认后才更新。

✅ 0.9.26。`preflight --fast` 第 12 项：`PASS 文案快照　示例与当前实现一致（44 行）`。

## 还没做的

- 快照只比对全文，没做逐行 diff 展示（现在只报"约 N 行不同"）。
