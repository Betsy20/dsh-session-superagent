# 备份要"从第一次写入就存在"

## 出处
- 这是普遍的"恢复点"问题：备份策略里最容易被忽略的是**第一个备份窗口**
  （NIST SP 800-34 的 contingency planning 里强调恢复点目标 RPO 要覆盖全生命周期：
  <https://csrc.nist.gov/pubs/sp/800/34/r1/upd1/final>）。

## 现场（三条路径都跑过）
| 场景 | 修复前 | 修复后 |
|---|---|---|
| 正常写入 | 1 条守 | 1 条守 + `.bak` |
| 主文件被截断 | **0 条守（全丢）** | 1 条守（从备份恢复） |
| 主 + 备份都坏 | 0 条守 + `.corrupt-*` 留证 | 同左（本就正确） |

根因很具体：`writeState` **只在"盘上已有好的主文件"时才写 `.bak`**。
于是「第一次写入之后、第二次写入之前」这段时间里，一次损坏等于全部丢失。
而这段时间恰恰是**新客户刚开始用**的时候。

## 改法
```js
try { renameSync(tmp, STATE_FILE) } catch { writeFileSync(STATE_FILE, text) }
if (!existsSync(STATE_FILE + '.bak')) writeFileSync(STATE_FILE + '.bak', text)  // 引导备份
```

再让 doctor 说清恢复事实：
```
WARN 状态文件坏过一次，已从备份恢复（原文件留在 .corrupt-* 里，可人工检查）
FAIL 状态文件和备份都读不了 —— 已从空状态开始……请重新添加守
```

## 判据
**恢复路径要在"最坏的时刻"演练**：不是"用了一周之后坏了"，而是"刚写下第一条就坏了"。

## 还没做的
- `.bak` 只有一份（没有滚动多版本）；
- `.corrupt-*` 不会自动清理，长期会堆积（很小，但没管）。
