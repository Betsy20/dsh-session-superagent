# 不是错误的状态码：一张清单，而不是一个 if

## 出处
- RFC 9110 §15：**2xx 是成功，3xx 是重定向/缓存有效，4xx/5xx 才是失败**。
  但 CLI 工具通常只按"非 2xx 即失败"处理（`gh` 就是），所以"语义"和"工具判定"会分叉：
  <https://www.rfc-editor.org/rfc/rfc9110#name-status-codes>

## 我们踩过的两次
| 状态码 | 语义 | 曾经的错误处理 |
|---|---|---|
| **304** | 没有变化（条件请求命中，不计入速率限制） | 落进 `other` → 显示「没归类的错误」 |
| **204** | 没有内容（DELETE / 空列表） | 落进 `JSON.parse` → 「返回内容不是合法 JSON」 |

两次都是同一类：**把"没有内容"当成了"内容坏了"**。

## 现在的清单
| 状态码 | 语义 | 我们的处理 |
|---|---|---|
| 200 | 正常 | 解析 body |
| 204 | 没有内容 | 按「未变化」处理（清错误、重置退避、记 `unchanged`） |
| 304 | 没有变化 | 同上 |
| 301 | 改名/转移 | 归 `moved`，提示换新地址 |
| 401 / 403 / 404 | 要人动手 | 归 `auth` / `ratelimit` / `notfound` |
| 5xx | 服务端/网关 | 归 `gateway`，暗示可重试 |

## 判据
**"不是错误"的情形要列成清单**，不要每发现一个就补一个 `if`。
清单写在 KB 里，代码里每个分支都指回这张表 —— 下次遇到 3xx/2xx 的其它码，先查表再决定。

## 是否已落地
✅ 0.9.113。用例：`parseGhInclude` 认 200/204/304；304 分类提示必须直说「不是错误」。

## 还没做的
- 清单只覆盖轮询用到的码；`github` 工具（任意 REST 调用）没有同样的分类；
- 没有自动检查"新加的 HTTP 处理分支是否在清单里"（目前靠人）。
