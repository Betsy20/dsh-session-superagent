# 索引按主题分组，别按时间堆

## 出处
- 沿用 Divio 的对文档分类思路（tutorial / how-to / reference / explanation）：
  <https://docs.divio.com/documentation-system/> —— 但这次解决的是**更浅一层的导航问题**：
  一个 66 行的扁平表格，本质上是"按时间堆"的索引。
- 判据很朴素：**读者是带着问题来的（"为什么没叫醒我"），不是带着版本号来的**。

## 重构前（实测）
`docs/kb/README.md` 是 66 行一张表，14 个"主题"标签，其中 4 组是近义重复：

```
判定与可解释性 11 / 可靠性 10 / 交互 8 / 轮询调度 7 / 性能 7 / 通知设计 6 /
隔离执行 3 / 文档 3 / 工程 3 / 可观测性 3 / 安全 2 /
GitHub API 性能 1 / 状态可靠性 1 / 限额 1   ← 后三个其实是前三组的子集
```

## 重构后
合并成 **9 个板块**，顶部先给一张"板块 → 篇数 → 看点"的表：

| 板块 | 篇数 |
|---|---|
| 调度、限额与隔离执行 | 11 |
| 通知与消息设计 | 6 |
| 判定与优先级 | 11 |
| 可靠性与状态 | 11 |
| 性能 | 8 |
| 可观测性 | 3 |
| 交互与可用性 | 8 |
| 工程与文档 | 6 |
| 安全 | 2 |

每篇的「状态」列保留（✅ 0.9.x / ⚠️ 未落地），所以不会因为重构丢掉"哪些是真做过的"。

## 顺手给索引加了门禁
`check-docs.mjs` 原本只查"孤儿文档"，现在多查一项：
**顶部声明的篇数必须等于该板块下实际列出的条数**。
重构索引最容易出的错就是"表头写 11 篇、下面只列 9 篇"—— 这种错单看表看不出来。

## 是否已落地
✅ 0.9.18。`check-docs` 现在输出三项 PASS（链接可解析 / 无孤儿 / 篇数一致），并已被 preflight 守卫。

## 还没做的
- 没有"按关键字搜索知识库"（88 篇 markdown 目前只能靠 `grep`）；
- 板块内的条目仍按加入顺序，没有按"客户最常问"排序（缺数据）。
