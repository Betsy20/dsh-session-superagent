# 批量输入要么全成、要么全不成

## 出处
- 这是"原子操作"在 API 设计里的应用：**部分成功比彻底失败更难收拾**
  （Stripe 的幂等键与批量接口文档都强调"要么整个请求生效，要么都不"，见
  <https://stripe.com/docs/api/idempotent_requests>）。

## 现场
`watch_start` 原来一次只收一个 `repo`。客户三个仓库要点三次、三个工具调用 ——
而它们的间隔/过滤/限流通常完全一样。

## 改法
`repo` 支持 `a/b, c/d e/f`（逗号、空格、换行都认）：
- 文本：每个仓库一行 `watching a/b → session s1 every 60s`；
- JSON：保留原字段（兼容），新增 `repos: [{repo,id,updated}]`；
- **有一个写错就整体拒绝**：`仓库要写成 owner/name，这些不对：not-a-repo`，且**一条都不写**。

## 为什么不做"部分成功"
如果 `a/b` 加上了、`c/d` 拼错了：
- 客户以为"没成功"，实际已经有一条在跑（还会开始轮询、可能叫醒会话）；
- 重试又会让 `a/b` 走 update 分支 —— 状态看着对，但客户的心智模型已经错了。

## 过程中踩到的坑
第一版把新逻辑包在 `applyOne()` 外面，但**原逻辑里还留着旧的 `format=json` 提前 return**，
于是多仓库时只返回第一个仓库的 JSON。删掉那段才对 ——
**重构时最容易漏掉的就是"提前返回"**。

## 是否已落地
✅ 0.9.89。用例：三仓库三行、守数=3、JSON 带 `repos`、一个写错时整体拒绝且不写入。

## 还没做的
- 面板仍是一次加一个（表单只收一个 `owner/name`）；
- 失败时没有指出"第几个"错（只列出错的字符串）。
