# 有 ETag 不等于 304 会命中：必须量一次

## 出处
- RFC 9110 §13.1.2 要求 ETag 表示**选中表示**的版本；如果指纹里混入每次都会变的字段，
  校验器就永远不匹配，缓存等于不存在：<https://www.rfc-editor.org/rfc/rfc9110#name-validator>

## 现场
`/state` 早就有 ETag/304，但**从没验证过是否命中**。面板每 5 秒拉一次 ——
如果指纹里混进易变字段（`updatedAt`、`gh` 版本探测时间、`sessionUsage` 的秒级计算），
ETag 永远不匹配，这段代码等于不存在。

代码里确实专门把 `updatedAt` 排除了：
```js
const stable = JSON.stringify({ ...stateBody, updatedAt: undefined })
```
但"我当时想到了一个字段"不等于"没有别的易变字段"。

## 实测（新增用例）
12 次拉取（第 6 次改一条守的 cursor）：
```
200,304,304,304,304,200,304,304,304,304,304,304
→ 只有 2 次 200
```

按 20 条守 37.8 KB 算：
| 情况 | 每分钟下载 |
|---|---|
| 无 ETag | 12 × 37.8 ≈ **454 KB** |
| 有 ETag | 2 × 37.8 ≈ **76 KB** |
| 省 | **约 83%** |

## 判据
**缓存/条件请求的唯一验收方式是"数 304 的次数"**，不是"代码里有 ETag"。
顺手把 `/state` 体积接进 `preflight`（第 30 项），防止以后又悄悄变大。

## 是否已落地
✅ 0.9.100。用例断言 12 次里恰好 2 次 200。

## 还没做的
- 只测了"无变化"和"改一条守"两种情形；`gh` 探测失败切换时 ETag 行为没测；
- 没有统计真实面板上的 304 命中率（需要真机埋点）。
