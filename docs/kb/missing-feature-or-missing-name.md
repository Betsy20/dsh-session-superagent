# 有些"功能缺失"其实是命名问题

## 出处
- 可用性里的经典区分：**capability gap vs discoverability gap**。
  Nielsen 的"可用性启发式"里"系统状态可见"讲的就是后者：
  能力在系统里，但用户找不到（<https://www.nngroup.com/articles/ten-usability-heuristics/>）。

## 现场
池子里写着「面板上直接看某条守最近 5 次唤醒结果（现在要点进 trace 查单条）」。
我按这个假设开始加折叠区，写到一半发现：**判定页的「判定日志」已经在显示这些**——
每轮结果、跳过原因、条目编号全都在（`history` 取最近 5 条）。

所以这不是能力缺失，是**命名**问题：标题写着"判定日志"，
客户不会把它和"最近几次唤醒"联系起来。

## 改法
- 撤掉刚加的重复区块（不留两份实现）；
- 标题改成 `判定日志（最近 5 次唤醒）`；
- 用例锁"标题能看出这是最近几次"，并继续断言条目与失败原因可见。

## 判据
**动手前先确认"是不是已经有了"。** 判断方式很简单：问"如果这个功能存在，它会在哪个页面出现？"
——然后去那个页面看一眼。这一步花 30 秒，能省掉一次重复实现。

## 成本对比
- 先确认：翻 1 个文件、跑 1 次用例 → 发现已有 → 只改 1 个标题（10 分钟）。
- 不确认：实现折叠区 + 用例 + 快照 + 两处入口 → 半小时后才发现重复。

## 是否已落地
✅ 0.9.91。用例锁标题可发现性。

## 还没做的
- 池子里的条目没有"先确认是否已存在"的检查项；
- 面板里可能还有别的"能力在但名字不显眼"的地方（如 trace 的入口）。
