# 错误信息的最后一道防线：兜底也要有下一步

## 出处
- NN/g 错误信息指南里最常被漏掉的一条：**每条错误都要给出可执行的下一步**
  （<https://www.nngroup.com/articles/error-message-guidelines/>）。
- 我们之前只对"认识的错误"给了建议 —— 这等于**对未知错误不管**。

## 现状盘点（6 类）
| kind | hint |
|---|---|
| auth | 跑 `gh auth login` 或填 token |
| ratelimit | 等几分钟，或换带 token 的凭证 |
| gateway | 已自动重试；持续出现检查代理 |
| nogh | 确认 gh 已安装且在 PATH |
| notfound | 检查 owner/name |
| **other** | **（空）** ← 问题 |

另外两条**根本不走分类器**的内部错误更糟：
- 解析失败 → `bad json`
- 结构不对 → `unexpected payload`

这两个词对客户毫无意义，也没说该怎么办。

## 改法
兜底 hint：
> （没归类的错误：已按退避自动重试；持续出现就跑 watch_doctor 看检查清单，或把这行贴给对方）

两条内部错误改成：
> 返回内容不是合法 JSON（可能是代理干扰）—— 已按退避自动重试；持续出现请跑 watch_doctor

## 判据
**兜底不必聪明，但必须有下一步。** 宁可说"跑 watch_doctor 或把日志贴给对方"，
也不要给一条让客户无从下手的原文。

## 是否已落地
✅ 0.9.62。用例：7 个样本（含兜底）都必须有非空 hint；兜底要匹配 `watch_doctor|重试`。

## 还没做的
- 面板上仍然直接 `slice(0, 160)` 截断（超长错误会被切掉后半段的建议）；
- 没有统计"实际生产中最常出现哪一类错误"（需要真机数据）。
