# 幂等痕迹有"两半"，要各自验证

## 出处
- 幂等（idempotence）在分布式系统里通常靠**持久化标记**实现；标记放在两个地方时，
  要分别问"其中一半丢了会怎样"：<https://learn.microsoft.com/en-us/azure/architecture/reference-architectures/containers/aks-mission-critical/mission-critical-idempotency>

## 现场
`watch_ack` 的幂等有两层：
1. GitHub 上的标签「主理鱼:已处理」（跟着仓库走，换机器也有效）；
2. 本地状态里的水位 `seen[number]`（跟机器走，标签被删也还在）。

**这条链路此前没有任何断言** —— 全靠"读代码看起来对"。而"标签被别人手动删掉"是很常见的动作
（清理标签、别人批量整理）。

## 四种情形（新增用例锁死）
| 情形 | 行为 | 是否合理 |
|---|---|---|
| 标签还在 | 跳过，判定日志记「已 ack」 | ✅ 可追溯 |
| 标签被删、水位还在 | **不重复叫醒**（`updated_at` 未变新） | ✅ 正是要的效果 |
| 标签被删、水位也没了（换机/重建） | **会再叫醒一次** | ✅ 宁可多叫一次，不漏 |
| 标签被删、但条目被编辑过 | 会重新叫醒 | ✅ 内容变了就该重看 |

实现细节：第三/四种情形都落在 `partitionItems` 的一个判断上 ——
`if (!(Date.parse(item.updated_at) > baseline)) continue`。

## 判据
**每个"持久化标记"都要写两行测试：标记在时怎样、标记消失时怎样。**
只测"在"的情况，等于假设世界不会变。

## 是否已落地
✅ 0.9.105。README「已知限制」也如实写了这一条。

## 还没做的
- 没做"标签被删"的主动告知（需要额外 API 调用，权衡后不做）；
- 多会话同守一个仓库时，A 会话 ack 的标签会让 B 会话也跳过 —— 这是共享语义，尚未在 KB 里单独讨论（下轮）。
