# 解释类功能按需拉，别塞进轮询负载

## 出处
- "按需查询 vs 预加载"的老权衡：轮询接口要小且稳定，解释类数据是**低频、偶发、可能很大**的，
  塞进轮询会拖慢每一次刷新（Google 的 Web Vitals 里 TTFB 直接影响体验，同理适用）。
- 我们的既有约束更硬：`/state` 已被用例锁死"不回传客户端从不读的字段"。

## 这轮的取舍
面板要做"追溯这条 issue"，本地算需要 `seen` / `lastReported`：

| 方案 | 代价 |
|---|---|
| 让 `/state` 回传 `seen`/`lastReported` | **每 5 秒**传一次两个大 map（每条守各一份）；而且违反既有契约用例 |
| 客户端再实现一份 `itemTrace` | 第三份重复实现（前两份已经开始走偏过） |
| **新增 `GET /trace?repo=&number=`** | 一次点击一次请求，只传结论 —— 选它 |

面板交互也因此简化：搜索框里输入编号（如 `42`）→ 出现「追溯 #42」→ 点击后结论显示在提示区。

## 落地时踩到的东西
1. 路由面从 8 变 9 —— 四处期望值（跨实例接管 / 撞车重放 / 卸载 / 路由清单）要一起改，
   否则用例会以"9 !== 8"的方式红；
2. 我一度试图把 `lastBatch` 加进 `/state` 以枚举候选条目 —— 直接被既有用例拦住
   （"服务端自己用即可"）。于是改成"用户输入编号"，零新增字段。

## 是否已落地
✅ 0.9.31。用例：未输入给提示、输入后出现按钮、单守时说明仓库；路由期望值与 preflight 同步。
