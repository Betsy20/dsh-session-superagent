# 失败要分"会不会自己好"，因为正确反应相反

## 出处
- 这是错误处理里的经典区分：**transient vs permanent**。
  AWS 的构建者指南把错误分成"可重试"和"不可重试"两类，并强调**重试策略只对前者有意义**：
  <https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/>
- 对客户端来说，这个区分直接决定它该等、该重试，还是该叫人。

## 现场
`watch_ack` 失败原来只回一句：
```
[error: #7 gh exited 1] <原始 stderr 200 字>
```
客户分不清"等一下就好"和"必须我去处理"—— 而这两种情况的正确反应**完全相反**。

## 改法
复用已有的 `classifyGhError`，输出两类文案：

| 类型 | 文案 | 长度 |
|---|---|---|
| 可恢复（网络/限流/网关） | `[error: #7 暂时失败，稍后再 ack 一次即可（网络抖动）]` | 35 |
| 需处理（登录/权限/编号） | `[error: #7 需要你处理] （gh 登录失效：跑 gh auth login，或在面板填 token）` | 55 |

JSON 里同时给 `kind` / `retryable` / `advice` —— 程序不用解析中文。

## 写的时候撞到两次文案重复
1. 第一版写 `会自动恢复：稍后再 ack 一次即可`，而 hint 里已经有"已按退避自动重试，不需要手动处理" —— **两句同义**；
2. 第二版在不可恢复分支既给 label 又给 hint，`gh 登录失效` **出现两次**。

> 判据：**一句话只承担一个信息**。可恢复的只说"要等"，不可恢复的只说"做什么"。

✅ 0.9.84。用例覆盖 6 种错误的可恢复性判定。
