# 下载量不是用户数：每个版本都会被自动化抓一遍

## 出处
- npm 的下载统计口径：**对 tarball 的 GET 次数**，包含镜像同步、安全扫描、依赖索引等自动化抓取。
  <https://github.com/npm/registry/blob/main/docs/download-counts.md>
- 这个仓库的实际形态：4 天发了 243 个版本（`npm view … time` 里 11-02 一天 183 个）。

## 现场（2026-11-04 实测）

npm 面板上显示「近 30 天 38.8k」，看着像有用户。把数据拆开：

```
逐日：11-01  2,467 | 11-02  36,296 | 11-03  0 | 11-04  0     ← 统计有 1~2 天延迟
按版本（last-week，198 个版本有记录）：
  总量 38,763 | 平均 196 | 中位 193 | 最高 287（0.8.11）| 最低 126（0.9.122）
  0.0.0-stage（占位版本，绝不可能有人装）= 258
```

**关键判据：分布是平的。** 198 个版本各 ~190 次，和版本新旧、内容、是否为 latest 无关。

真实用户的行为不是这样：他们会集中在 `latest`，老版本长尾递减；
而 `0.0.0-stage` 这种占位版本有 258 次下载，只可能是自动抓取。

## 我们能怎么用

1. **别拿下载量当采用度**。README / 发布说明里不写「已有 N 次下载」；
2. **发版节奏会放大这个数字**：一次 `npm publish` 就是一个新版本 → 每个抓取方各拉一遍。
   4 天 243 个版本 ≈ 243 × ~190 ≈ 4.6 万「下载」，全是噪声；
3. 想知道真实使用量，只能看**宿主侧信号**：`watch_start` 的仓库数、`npm` 无法提供的
   —— 或者干脆用「有多少 issue/PR 来自外部用户」这类可验证指标。

## 判据

**下载量曲线的形状比数值有用。**
- 集中在少数版本 + 长尾 → 可能真有用户；
- 每个版本都一样平 + 占位版本也有量 → 自动化抓取，与采用度无关。

## 是否已落地
✅ 0.9.169 期间识别并记录；本仓库 README 不引用下载量作为宣传。

## 还没做的
- 没有把「发版节奏」写进台账的成本项（快速迭代本身没错，但要知道它在下载统计上是噪声源）；
- npm 不提供 referrer，所以**无法确证**抓取方是谁（镜像 / 安全扫描 / 插件市场兼容性探测），
  上文的归因是"形状推断"，不是证据。
