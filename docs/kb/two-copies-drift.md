# 同一段文案有两份实现，就会慢慢走偏

## 出处
- 这是"逻辑重复"的经典后果，无需外部引用；本轮有**实测证据**：
  用 `scripts/audit-ux-copy.mjs` 逐条打印面板文案时发现，服务端 `gh-format.js:repoStructureNote`
  已经支持「已归档 / 已禁用」，**客户端的同名函数还停在只有「关闭 Issues / fork」的老版本**。

## 为什么会这样
面板不能跨包 import 服务端模块（会把 cordis 之类依赖带进浏览器包），
所以有几处"同语义、两份实现"：`repoBadges`、`durationText`、`accessNote`、`repoStructureNote`。
每次改一边、忘了另一边，就产生**同一个产品对同一件事有两种说法**：
唤醒消息说"已归档，只能看不能写"，面板什么都不说。

## 本轮修了什么
| 项 | 服务端 | 客户端（修前） | 修后 |
|---|---|---|---|
| 归档 | ✅ | ❌ 没有 | ✅ 对齐 |
| 禁用 | ✅ | ❌ 没有 | ✅ 对齐 |
| 关闭 Issues | ✅ | ✅ | ✅ |
| fork | ✅ | ✅ | ✅ |

顺序也对齐（归档 → 禁用 → 关闭 Issues → fork），因为顺序影响"客户先看到哪一句"。

## 怎么防止再走偏
1. 每处重复都要有**两端各一条用例**（现在客户端这条是新增的）；
2. 每次改一边，同步搜另一边（`grep -n "function repoStructureNote" lib/ client.js`）；
3. 抽检脚本把"面板文案"打出来 —— 走查时更容易发现"这句怎么跟消息里不一样"。

## 是否已落地
✅ 0.9.17。用例：归档/禁用必须在「需要关注」出现且说明后果。

## 还没做的
- 没有自动比对两份实现（技术上可行：把两份纯函数抽成 `.mjs` 供两端 import，
  但那要改构建，收益不抵风险）；
- `accessNote` 目前只有服务端进唤醒消息、客户端进面板 —— 也是两份，靠用例保持同步。
