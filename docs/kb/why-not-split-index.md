## 出处
- 判断方法沿用上一篇（[拆分看改动轴](split-by-change-axis.md)）：**先统计耦合度，再决定**。
- 文档体检的思路来自"链接腐烂"（link rot）这个老问题：文档越写越多，引用会悄悄失效。

## 一、index.js 要不要拆
用同一套方法量化 `lib/index.js`（1795 行）：

```
基建区（状态读写 / gh / 唤醒 / 轮询）: 1000 行
注册区（7 个工具 + 8 条路由）      :  796 行
注册区用到的基建名字               :  25 个（占基建定义 46 个）
每个路由/工具的平均跨度            :  53 行
```

对比 `watch.js` 那次拆分：那边是**零依赖的单向关系**，拆起来干净利落。
这边是 **25 个共享符号**（`ghEnv` / `run` / `readState` / `activeRoutes` / `defineTool` …），
拆开等于给每个路由传一大包依赖，或者搞一个"上帝对象" —— **复杂度从一维变两维**。

**结论：不拆。** 它已经是"上基建、下注册"的纵向结构，每条路由自成一段，
改一条路由不需要读别区的代码（已验证：53 行平均跨度）。

## 二、顺手做的：文档体检工具
45+ 篇文档互相引用，谁也不知道有没有写错的链接。新增 `scripts/check-docs.mjs`：

- 扫描全部 Markdown（跳过 `node_modules/.git/tmp/dist`）；
- 只查**仓库内相对链接**（不查 http(s)，那要联网且会误报）；
- 额外查**孤儿文档**：`docs/kb/*.md` 若没被 `docs/kb/README.md` 索引，客户永远看不到。

第一次跑的结果：
```

PASS 所有内部链接都能解析
PASS 知识库文档全部被索引
```
都健康 —— 但**这是运气，不是保证**。已接入 preflight（对应检查），以后写错立刻红。
