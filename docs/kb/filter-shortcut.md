# 快捷筛选要"带数量 + 能一键退回"

## 出处
- 沿用渐进披露的思路（<https://www.nngroup.com/articles/progressive-disclosure/>），
  再加一条来自过滤器的常识：**任何收窄视图的操作都必须有一个显眼的还原方式**，
  否则用户会以为"数据没了"。

## 改法
「按仓库」标题旁加一个 Pill：`只看有问题的 (2)`：

| 行为 | 细节 |
|---|---|
| 什么算"有问题" | 有 `lastError` / 未回音 ≥2 / 仓库结构问题（归档、无 Issues、fork）/ 警示或危险徽章 |
| 数量 | 直接写在 Pill 上，不用点进去才知道有几条 |
| 还原 | 开启时旁边出现「全部」；筛选后为空还会给一句说明 |
| 零新增请求 | 纯前端筛选，不额外打接口 |

## 又一个 useState 槽位的坑（第二次）
这次我按上轮的教训**追加在最后**，但仍踩了一次：测试里有个用例是
`[...deskQueue(snapshot), true]` —— 它把 `true` 追加到队列末尾，用来点亮某一行的"确认删除"。
新增槽位后这个 `true` 落到了 `problemsOnly` 上，等于"只看有问题的"，于是那行被筛掉、用例红。

修法：`deskQueue` 默认值补上第 18 个槽（`false`），这样"追加到末尾"的语义继续保持。

**教训**：依赖"位置"的测试桩，新增槽位不仅要追加在代码末尾，**还要同步默认队列长度**，
否则所有"追加到末尾"的用例都会悄悄偏移。

## 是否已落地
✅ 0.9.15。用例：Pill 上带数量、开启后只剩有问题的两条、健康的不出现、能看到「全部」还原入口。

## 还没做的
- 没有"只看报错的"与"只看未回音的"细分；
- 数量是首屏数据算出来的，筛选后不会重新统计（避免递归依赖）。
