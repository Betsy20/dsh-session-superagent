# 首屏区块数要有个上限，而且是写死的那种

## 出处
- NN/g 关于"信息密集 vs 认知负荷"的经典结论：**默认展示的东西越少，首次使用越容易**，
  细节应放在第二层（已在 0.9.13 引用过的渐进披露）。
  <https://www.nngroup.com/articles/progressive-disclosure/>
- 这轮补的是"怎么把它变成可执行的判据"：**默认展开的区块数 ≤ 6**。

## 体检脚本
`scripts/audit-density.mjs` 静态解析 `client.js`，数出每个 tab 变量里 `h(Section, …)` 的个数：

```
overview    2 个区块：最近被过滤 / 需要关注
judge       3 个区块：判定日志 / 追溯一条 / 时间线
trigger     6 个区块：新增主理鱼 / 来源 / 凭证 / 版本与更新 / 分诊信号与取舍 / 会话 goal
repoSummary 1 个区块：按仓库
```

## 体检抓到并修掉的两处
1. **judge 页有两个都叫「追溯一条」的区块**（我上一轮为"有编号/无编号"写了两个分支，
   各返回一个 Section）—— 合并成一个区块，内部按是否有编号分岔；
2. **trigger 页 7 个区块**（超过上限）：把「诊断」并进「版本与更新」——
   这两件事同属"排查/维护"，客户遇到问题时本来就会一起看。

修完：**最密集一页 6 个区块**，正好压在上限。

## 为什么判据写死 6
- 写死才能被自动化检查（"感觉有点多"没法当门禁）；
- 6 是按"一屏能看到、扫一眼不迷路"估的，不是严格实验结论 —— 但**有数字比没数字好**，
  以后真觉得不合理，改这一个常量即可。

## 是否已落地
✅ 0.9.36。`preflight --fast` 对应检查：`PASS 信息密度　最密集一页 6 个区块（上限 6）`。

## 还没做的
- 统计的是"区块个数"，不是"可见控件个数"（后者更能反映认知负荷，但解析成本高）；
- 设置页刻意不参与上限（它天然是"所有设置项的家"）。
