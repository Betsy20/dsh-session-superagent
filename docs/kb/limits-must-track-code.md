# "已知限制"要和代码一起改，否则它会变成谎话

## 出处（含坦白）
- 概念上参考 Keep a Changelog 的 _Guiding Principles_：文档要**反映真实状态**，
  过时的说明比没有说明更糟（<https://keepachangelog.com/en/1.1.0/#how-do-i-make-a-changelog>）。
- 但这次不是从文献推的，是**核对出来的**：把 README 的「已知限制」逐条对照代码。

## 核对结果（本轮）
| README 原文 | 实际情况 |
|---|---|
| 「单会话单仓库；多仓库请每仓库一个会话」 | **错**。守的 id 是 `repo#sessionId`，同一会话可以有多条守 |
| 「`node --test # 136 项单测`」 | 过时（实际 143），且每次发版都要改 → 改成「全部单测」 |
| 没写「服务端改动要重启才生效」 | **缺**。这是本机踩得最多的一条 |
| 没写「每小时上限是滑动窗口」 | **缺**。客户会以为是整点重置 |
| 没写「隔离区最多留 5 个」 | **缺**（这轮才加的行为） |

## 从这轮得到的两条做法
1. **限制要写"客户会误判什么"**，不是写"我们实现了什么"。
   比如"轮询而非 webhook：延迟等于轮询间隔"是有效限制；
   "单会话单仓库"其实是过时的能力描述。
2. **易变的数字不要写进 README**。`136 项单测` 这种每版都变的数字，
   写进去等于给自己造一条"每次发版都要记得改"的负担，而忘记改就是谎话。
   数字放在 `CHANGELOG`（一次性的）和 `MAINTENANCE`（当前值）里更合适。
