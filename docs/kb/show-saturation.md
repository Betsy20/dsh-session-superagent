# 只显示"用了几次"没用，要显示"还能用几次"

## 出处
- Google SRE 的四个黄金指标（latency / traffic / errors / **saturation**）：
  saturation 是"资源有多满"，它是**唯一能提前预警**的那个 ——
  错误和延迟都是事后才知道，饱和是"马上要出事"。
  <https://sre.google/sre-book/monitoring-distributed-systems/#:~:text=Saturation>

## 上一轮模拟给的证据
离线跑一小时（3 仓库 / 30 秒 / 每仓库每小时 10 条 / 会话上限 12）：

```
实际上报 12 / 共 30 条 —— 一小时只能处理 40%
被会话上限挡住 241 次
```

也就是说：**默认参数下，客户有一半的条目在排队**，但界面上看不出来。
面板原来只显示 `lastDeferred`（一句"已攒 N 条"），既不显示"这一小时已经用掉几次"，
也不显示"上限是多少"。

## 改法
`/state` 新增 `sessionUsage`：

```json
{ "used": 12, "cap": 12, "capped": 2 }
```

- `used`：本会话近一小时唤醒次数（复用 `sessionWakesLastHour`，**零新增请求**）；
- `cap`：当前 `sessionMaxWakes`；
- `capped`：有几条守正因上限暂停（数 `lastDeferred` 里含"上限/一小时内已被唤醒"的）。

面板在「按仓库」旁显示：

- 常态：`本会话近一小时唤醒 3/12`
- 到顶：`已到上限：新条目会攒到下一小时，可以把「这条会话每小时最多被唤醒」调大` + `2 条守正因上限暂停`

## 为什么"给建议"比"报警"重要
只写"已到上限"等于把问题丢回给客户；带上"把某个字段调大"才是可执行的动作。
这也是 0.8.97 那条错误信息准则的延续：**说人话 + 给动作**。

## 是否已落地
✅ 0.9.20。路由契约用例断言 `sessionUsage` 三个字段都在；面板用例覆盖"没用满不报警 /
用满要给建议 / 要说清几条守被挡住"。

## 还没做的
- `capped` 是靠匹配提示文案统计的（脆弱）；更稳的做法是服务端在暂停时打一个 `capped: true` 标记；
- 没有做"根据历史积压自动建议上限值"（需要更多真实数据）。
