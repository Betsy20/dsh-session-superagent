# 安装后待重载状态修复报告

## 结论

已修复「POST 安装成功后，GET `/update` 仍返回 `hasUpdate:true`，设置页与顶部继续引导重复安装」的主路径问题。

当且仅当安装回执同时满足以下两个条件时，客户端让回执优先于 GET 的更新提示：

- `updateResult.installedVersion === update.latest`
- `updateResult.needsReload === true`

此时：

- 「设置 → 版本与更新」的状态显示 **「已安装，等待重载」**；
- 不再渲染「安装更新」按钮，但保留原命令文本与「复制命令」手动回退；
- 顶部采用更安静的方案：**完全隐藏「有新版本 / 去更新」横幅**，不新增另一条顶部提示；
- `installedVersion`、`runningVersion`、`needsReload` 仍按服务端回执原样展示，尤其不把 `runningVersion` 推断成已经运行新版。

只有手动点击「重新检查」才清除这份回执；安装成功后的强制 GET 使用 `checkUpdate(true, true)`，仍保留回执。回执清除后，设置页与顶部恢复按 GET 判断。

## 根因与改动范围

服务端 GET 的 `hasUpdate` 比较的是运行中版本与 `latest`。安装只更新安装副本，宿主尚未重载时 `runningVersion` 不变，因此真实响应可以继续是 `hasUpdate:true`。旧客户端虽然保存了 `updateResult`，但它只用于显示回执；安装按钮与顶部横幅仍只看 `update.hasUpdate`。旧成功路径测试又把 GET mock 成 `hasUpdate:false`，恰好遮住了这个矛盾。

本次只改：

- `client.js`：新增严格匹配的待重载派生状态，并用于状态文案、安装按钮和顶部横幅三处；
- `test/update-ui.test.mjs`：成功路径改用真实语义的 `hasUpdate:true`，补充隐藏断言与三种不受影响场景；
- `docs/报告-安装后待重载状态.md`：本报告。

没有修改 `lib/`、`package.json`、版本号或派单表；没有执行真实安装、宿主重载、commit 或 push。

## 行为矩阵

| 场景 | GET `hasUpdate:true` 时的设置页 | 顶部 |
|---|---|---|
| 尚未安装（无回执） | 保留「安装更新」 | 保留「有新版本 / 去更新」 |
| 回执中的 `installedVersion` 不是本次 `latest` | 保留「安装更新」，不显示「已安装，等待重载」 | 保留 |
| `installedVersion === latest`，但 `needsReload=false` | 保留「安装更新」，不显示「已安装，等待重载」 | 保留 |
| `installedVersion === latest` 且 `needsReload=true` | 显示「已安装，等待重载」，隐藏「安装更新」 | 完全隐藏 |

## 定向回归

`test/update-ui.test.mjs` 现有 **7 条**：

1. 有更新时显示官方 primary 安装按钮；确认前、取消、关闭与复制命令均不发 POST。
2. 确认后才 POST 指定版本；busy 防连点；整轮只安装一次并强制 GET。
3. 成功后 GET 仍 `hasUpdate:true` 时，显示待重载状态、隐藏重复安装按钮和顶部误报、保留复制命令，并原样显示 running 版本。
4. 未安装、其它安装版本、`needsReload=false` 三种场景均继续按 GET 显示安装按钮与顶部提示。
5. 手动「重新检查」清掉旧回执；普通顶部入口仍能直达更新分区。
6. 安装失败保留版本与命令回退，不伪装成功，不错误刷新或关闭 Modal。
7. 老宿主缺少 Button/Modal/Toast 时，本地 fallback 仍走同一 POST 与刷新动线。
