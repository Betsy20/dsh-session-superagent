# 为什么做这个产品

> 这份文档回答三个问题：**谁在痛、痛在哪、我们凭什么**。
> 它不描述功能（那是 README 的事），它描述**判断依据** —— 以后每个「要不要做这个功能」
> 都拿它来对。

## 一、市场上的产品在回答另一个问题

同类产品很多，而且都很强：

| 产品 | 它回答的问题 |
|---|---|
| CodeRabbit / Greptile | 「**代码写得好不好**」—— 评审 |
| Sweep / Devin / OpenHands / Copilot Workspace | 「**你写不完的代码，我替你写**」—— 交付代码 |
| claude-code-action / 各种 issue bot | 「**issue 来了，自动开个 PR**」—— 自动化流水线 |
| 官方的 `dsh-superagent-prototype` | 「**一个 agent 服务一整个团队**」—— 组织级自主 |

它们共同的前提是：**瓶颈是写代码**。

对我们的目标用户 —— 一个已经在用 DSH、一个人盯几个仓库的开发者 —— **瓶颈不是写代码**。

他真正的痛是：

1. **注意力被打断**：切到 GitHub 看一眼 issue，回来上下文没了；
2. **不知道发生了什么**：三天后才看到那条 bug report，人家已经跑去用竞品了；
3. **知道有活，但不想开新窗口**：又要配一个 bot、一个 dashboard、一个 webhook，为了「看一眼」付出太多。

于是问题变成：**能不能让「我已经开着的这个会话」自己去发现活？**

## 二、所以这个产品只做一件事

> **把仓库的动态，翻译成这个会话里可以直接开工的任务。**

注意是三段，缺一不可：

| 段 | 含义 | 做错的后果 |
|---|---|---|
| **仓库的动态** | 不是「通知」，是「有人提了件需要判断的事」 | 做成通知 = 又一个红点 |
| **翻译成任务** | 带上编号、标题、标签、谁提的、链接、**完成标准**、下一步 | 只给「有新 issue」= 客户还得自己去看 |
| **这个会话里** | 就在你正在用的会话，不新开窗口、不装额外服务 | 变成又一个客户端 = 没人用 |

第三条是**产品形态**，不是技术选择。它决定了我们永远不做：
独立的 dashboard 站点、需要单独登录的 bot、必须改 CI 配置的集成。

## 三、三条诉求，也就是三条不变量

### 诉求 1：不打断

客户在写代码，不是在看通知。所以：

- 会话忙的时候**绝不插话**（等它空闲）；
- 一次别叫醒太多次（每小时上限、单次条数上限）；
- 能合并的叫醒就合并（同一轮的几条合成一条消息）；
- 深夜别叫（活跃时段）；
- 别人随手提的不打扰（作者白名单）。

**判据：如果一个功能会让唤醒次数变多，它的收益必须大到值得。**

### 诉求 2：不留手尾

叫醒之后，客户不应该再回到 GitHub 去「查我做到哪了」。所以唤醒消息里**必须有**：

- 这条是什么（编号 / 状态 / 标题 / 谁提的）；
- 为什么是它（排序依据、过滤原因）；
- 干完之后怎么办（回写到哪、要不要打标签）；
- 之前有没有处理过（叫醒过几次、上次判过什么）。

**判据：唤醒消息本身要是一份能直接开工的任务书，不是一句提醒。**

### 诉求 3：不失控

它会主动叫醒你 —— 但它**不许替你做事**：

- 只叫醒，不代写代码；
- 凭证留在插件内，**不进模型上下文**（`redact()` 是唯一出口）；
- 谁来派活有名单（`allowAuthors`）；
- 每条改动都要能被追溯（`watch_trace` 回答「这条为什么没叫醒我」）；
- 写操作要显式确认。

**判据：任何「自动做掉」的能力，都要先回答「做错了谁负责、怎么撤回」。**

## 四、我们明确不做的事

| 不做 | 为什么 |
|---|---|
| 替客户写代码 | 那是上面那些产品的活；做了就变成它们，且我们做不过它们 |
| 团队级 multi-agent 编排 | 官方原型在做；单人场景引入它 = 配置成本压垮收益 |
| 独立 dashboard | 破坏诉求 1 的第三条（就在这个会话里） |
| 全自动闭环（提 PR 不需要人看） | 破坏诉求 3 |

## 五、怎么算成功

不是「装的人多」，是这三个数：

1. **叫醒之后有动作的比例**：叫醒 10 次，客户/会话真的处理了 ≥7 次 —— 低于这个说明叫醒的是噪音；
2. **从「仓库有动静」到「会话开始干」的时间**：目标是分钟级，不是天级；
3. **客户回到 GitHub 网页去看的次数**：越少越好 —— 说明信息真的搬过来了。

## 六、当前最大的缺口（按这份文档排的优先级）

1. **「叫醒之后」的闭环还不够**：我们记了「叫醒过」，但没记「处理结果」。
   同一条被重开时，会话不知道自己上次判了什么 —— **违背诉求 2**。
2. **Ticket 状态机缺位**：水位线能表达「这条更新过」，表达不了「这条还在进行中」。
   这是官方原型最值得我们抄的一块，也是我们未来最可能撞墙的地方。
3. **成功指标没埋点**：上面那三个数，一个都测不到。

## 七、和官方原型的取舍（详见 [对比-官方原型.md](对比-官方原型.md)）

官方原型的核心是 **Policy → Ticket → Executor → Delivery** 这套组织级模型。
我们只抄它的**第一件事**（谁来派活 = `allowAuthors`），因为那一条在单人场景也成立；
其余保留为「未来可能需要」，不提前引入。
