# 主理鱼 0.9.206 · 测试覆盖缺口审计（只读）

> 审计方式：不改代码、不 commit。全部数字来自本机实跑（Node v24.20.0 / Windows / `DSH_SUPERAGENT_OFFLINE=1`）。
> 报告里唯一的写入是本文件。

**一句话结论**：`lib/` 六个文件里，五个覆盖良好（watch 98.6%、gh-format 98.9%、gitee 93.9%、body 94.4%、redact 100%）；洞几乎全部集中在 `lib/index.js` 的**轮询内核**——`pollOnce()` 与 `pollWithItems()` 两个函数共 293 行代码、**0 行被执行**，而它们正是「要不要叫醒模型、叫醒后记什么账」的全部逻辑。

## 0. 先说测量本身：官方覆盖率对 `lib/index.js` 不可信

按要求跑了命令（原始输出见第五节）。但 `--experimental-test-coverage` 报出来的 `lib/index.js` 那一行**不稳定**：同一条命令、同一份代码连跑两次，得到两个不同结果——

```
run A:  index.js | 24.14 | 40.48 | 9.09 | ... 2040-2077 ... 2819-2854 ...
run B:  index.js | 11.03 | 50.00 | 0.00 | ... 215-268 ... 1487-2883 ...
```

而只跑 `test/routes.test.mjs` 时它报 **28.03%**——比跑全量还高。全量是单文件的超集，这在统计上不可能，只能是聚合环节丢了数据。

**根因**：本仓库有 5 个测试文件、共 33 处用 `await import('../lib/index.js?parity=…')` 这种带 query 的方式重复加载同一份模块（用于跨实例/热重载场景）。每次加载在 V8 里都是一个独立脚本实例；Node 的报告器按 URL 去重时只保留了其中一个实例，其余实例的覆盖被丢弃。最小复现（与本仓库同构，已被我实跑验证）：

```js
// a.js
export function f(x) { if (x) return 1; return 2 }
export function g()   { return 'never called' }
// a.test.mjs
import * as m from './a.js'
import * as m2 from './a.js?second=1'
test('only f(true) is called', () => { assert.equal(m.f(true), 1); assert.ok(m2) })
```

实际执行了 `f(true)`，官方报告却给出 `a.js | 28.57 | 100.00 | 0.00 | 2-4 6-7` —— 函数覆盖 0%，连 `f` 的函数体都被判成未覆盖，因为它报的是那份**没被调用过的实例**。同一次运行，改用原始 V8 区间合并后是 `line 60.00% (3/5) | func 66.7% (2/3) | uncovered: 3 6`，与事实一致。

**本报告采用的数字**：`NODE_V8_COVERAGE` 原始区间，按「同一实例内区间嵌套取最内层 / 跨实例与跨进程取并集」合并，得到每个文件的真实覆盖率。校验：其余五个文件的合并值与官方值相差 ≤1.6 个百分点（body 94.44 vs 95.12、gh-format 98.93 vs 99.14、gitee 93.92 vs 95.44、redact 100 vs 100、watch 98.57 vs 98.89），说明方法本身没问题，偏差只出现在 `index.js` 这一行。

| 文件 | 官方 line/branch/func | 合并后 line | 合并后 func | 合并后块覆盖 | 代码行（合并分母） |
|---|---|---|---|---|---|
| `lib/index.js` | 24.14 / 40.48 / 9.09（**失真**） | **59.17%** | 67.9%（91/134） | 49.71% | 1155/1952 |
| `lib/watch.js` | 98.89 / 89.68 / 98.17 | 98.57% | 98.2%（108/110） | 86.53% | 620/629 |
| `lib/gh-format.js` | 99.14 / 87.50 / 100.00 | 98.93% | 100%（33/33） | 86.25% | 278/281 |
| `lib/gitee.js` | 95.44 / 73.13 / 86.36 | 93.92% | 87.0%（20/23） | 68.42% | 139/148 |
| `lib/body.js` | 95.12 / 81.25 / 100.00 | 94.44% | 100%（3/3） | 76.92% | 17/18 |
| `lib/redact.js` | 100.00 / 85.71 / 100.00 | 100% | 100%（4/4） | 66.67% | 29/29 |

口径说明：行覆盖 = 该行有任一位置落在 count>0 的 V8 区间内（V8 的 offset 是 UTF-16 码元，不是字节——我用一份带中文注释的样本核过）；纯注释、空行、只有 `}`/`);` 的行不计入分母；函数覆盖 = 函数入口区间被执行过。多行表达式的续行可能被少计一两点，不影响排序。

## 一、必须补

排序依据不是行数，而是「外部输入能不能触达 + 坏了之后客户会不会在不知情的情况下丢东西」。四条都满足「客户付现看得见」。

### M1 `pollWithItems()`：叫醒闸门与记账，整函数 0 执行

- **位置**：`lib/index.js:1226-1483`，1226 起 171 行代码，**171 行全部未覆盖**（原始 V8：该函数入口区间在 24 份进程覆盖率 dump 里 count 全为 0）。
- **为什么漏**：它只有两个入口——定时器 `tick()`（`1552`）与 `/watch` 的 `action:'poll'`（`1904`）。测试里 `DSH_SUPERAGENT_NO_POLL=1` 把 tick 关掉了；`action:poll` 只测了「不存在的 id → 404」这一条（`test/routes.test.mjs:146`）。于是整个函数在测试中不可达。
- **未覆盖的关键分支**：
  | 行 | 分支 | 后果方向 |
  |---|---|---|
  | `1248` | 响应不是数组 | 坏数据被当成功 |
  | `1300-1305` | 本轮无新增 → 清 `lastDeferred`、提交 ETag | 面板永远挂着上一轮的「等待中」 |
  | `1309-1323` | 仅观察（observe） | 该叫的不叫 / 不该叫的乱叫 |
  | `1329-1333` | 会话级上限（跨守累计） | 一条会话被多守打爆 |
  | `1339-1346` | 单守每小时上限 | 上下文被打爆 / 名额算错 |
  | `1353-1356` | 轮询期间被暂停或删除 | 已暂停的守仍然发出唤醒 |
  | `1361-1375` | 会话不存在（宽限期 vs 判死） | 重启后误报「会话已不在」 |
  | `1379-1382`、`1387-1394` | 会话忙（两次判定） | 忙时白开 worktree / 记账错位 |
  | `1440-1482` | 唤醒记账（成功 / 失败两条路） | **丢消息**或重复叫醒 |
- **如果它坏了会怎样（具体）**：
  1. **丢一条 PR 评论且永不重报**。会话正忙时 `decideWake` 会拒绝（`1379`），此时若 `seen` 已被推进、ETag 已提交，下一轮条件请求拿到 304 直接 return，`fresh` 不再重算 —— 客户面板上写「运行中·上次轮询 1 分钟前」，但那条评论永远不会再叫。这正是 `1437-1439` 注释里自己记着的 lost update，而守住它的测试是 0 条。
  2. **observe 模式的守开始真发消息**。客户把一条守设成「只看不打扰」用来评估噪音，结果会话被这个仓库刷屏。
  3. **会话级上限形同虚设**。5 条守各按 6 次/小时叫，一小时 30 条注入，模型上下文直接爆掉（`1329` 那 5 行没人跑过）。
- **建议断言**（完整代码见第四节 T1/T2）：会话 `status:'running'` 时调用后，`entry.seen` 必须仍是 `{}`、`entry.etag` 必须仍是 `undefined`、`entry.wakeTimes.length === 0`、`lastDeferred === '会话正忙，下一轮重试'`；`observe:true` 时则相反：`deferReason === 'observe'`、`seen['7']` 存在、`etag` 已提交、`wakeTimes` 仍为空。

### M2 `pollOnce()`：304 / 限流 / 额度全部没跑过

- **位置**：`lib/index.js:1053-1218`，**122 行代码全部未覆盖**。
- **未覆盖分支**：活跃时段 `1056-1061`；Gitee 分支 `1067-1126`；304 识别 `1135-1143`；错误分类与限流等待 `1146-1171`；额度自适应 `1181-1189`；204/304 `1192-1211`。
- **如果它坏了会怎样（具体）**：
  1. **304 识别一失效，守就静默死亡**。`gh` 把 304 当失败（exit 1），代码靠正则 `HTTP 304|not modified`（`1135`）把它认回来。哪天 gh 改了措辞（或换成 `304 Not Modified` 之外的写法），每一轮都会被判成「返回内容不是合法 JSON」，`bumpFailure` 指数退避（前 5 次最多 30 分钟，连续 6 次后放慢到 2 小时一次）—— 面板只显示一条旧错误，客户看到的是「仓库一直没动静」。
  2. **额度自适应失效 = 自己把 token 撞进小黑屋**。`1181-1189` 的意图是剩余额度 <500 时直接推到重置时刻；这段不跑，就永远按 60 秒撞，命中 GitHub secondary rate limit 后所有请求一起 403。
  3. **这段没跑过的代码里已经躺着一个能看见的 bug**：`1183-1186` 的字符串拼接错位——
     ```js
     entry.lastDeferred = '额度紧张（剩余 ' + parsed.remaining + '），已推迟到 '
     entry.deferReason = 'quota'
       + new Date(Date.now() + throttle).toISOString().slice(11, 16) + 'Z'
     ```
     ASI 不会在 `+` 前插分号，于是 `lastDeferred` 以「已推迟到 」结尾（没有时间），`deferReason` 变成 `quota09:30Z`。把这三行原样抄出来跑，输出是：
     ```
     lastDeferred = "额度紧张（剩余 10），已推迟到 "
     deferReason  = "quota23:57Z"
     ```
     面板的 `DEFER_LABELS['quota']`（`client.js:963`）查不到，按原因筛选（`client.js:1395`）永远空列表。**这条建议断言现在就会失败**——正好证明这段代码从没被执行过。
- **建议断言**（T3）：注入 `run` 返回 `{code:1, stderr:'gh: HTTP 304 Not Modified'}` → `lastDeferred === '未变化（304，不计入速率限制）'`、`consecutiveFailures === 0`、`nextAt === null`；注入 `remaining:10, resetAt:…` 的 200 响应 → `deferReason === 'quota'` 且 `lastDeferred` 必须匹配 `/\d{2}:\d{2}Z/`。

### M3 `run()` 的进程生命周期：全部测试都被 OFFLINE 短路掉了

- **位置**：`lib/index.js:604-646`，13/34 行未覆盖：超时 kill `623-627`、`error` 事件 `631-635`、`close` `637-641`、`stdin` 写入 `643-644`。
- **现状**：所有测试都设了 `DSH_SUPERAGENT_OFFLINE=1`，`run('gh', …)` 在 `615-618` 直接返回假数据；`run('git', …)` 也没有任何测试调用（`test/worktree-prune.test.mjs` 自己 `execFileSync`）。也就是说**这个模块里唯一真正 spawn 进程的函数，在生产之外一次都没执行过**。
- **如果它坏了会怎样（具体）**：
  1. **一条守从此不再轮询，面板还写「运行中」**。gh 卡在企业代理的黑洞里 → `await run` 不返回 → `tick` 的 `inFlight`（`1550`）永远占着这条守 → 之后每 60 秒进来都在 `1549` 直接 return。客户唯一能看到的线索是「上次轮询 3 小时前」，而 `watch_doctor` 的停滞检查（`2599`）同样没被测。
  2. **没装 gh 被误诊成网络问题**。`spawn` 的 ENOENT 若走不到 `631-635`，会落到 `close` 分支（`c === null` 时按 0 处理，`641`），于是每轮都是「返回内容不是合法 JSON」，客户去查代理，实际是 `gh` 不在 PATH 里。`test/watch.test.mjs:1350` 那条「找不到 gh 的报法要认全」测的是**分类函数**（把字符串喂给 `classifyGhError`），不是 `run()` 真的找不到命令。
- **建议断言**（T4）：`run(process.execPath, ['-e', 'setTimeout(()=>{},5000)'], {timeoutMs:150})` → `code === 'timeout'` 且在 700ms 内返回；再等 1.2 秒断言子进程写出的标记文件不存在（证明真被 kill）。`run('definitely-not-gh-xyz', [])` → `code === 'spawn-error'` 且 `stderr` 含 `ENOENT`。

### M4 面板「保存凭证」的写路径：只有 Gitee 令牌那一条被执行过

- **位置**：路由 `lib/index.js:2038-2078`；`writeSecrets()` 本体 `278-285`（6/6 行未覆盖）；`token` 校验 `2046-2050`、`sshKeyPath` 校验 `2052-2056`、`ghConfigDir` 校验 `2069-2073` 均未执行。
- **现状**：唯一真被执行的是 Gitee 令牌形状校验（`test/routes.test.mjs:1368`）。`ghConfigDir` 只有一个**grep 源码**的测试（`test/routes.test.mjs:1299-1309`）：断言源码里存在 `ghConfigDir must be absolute` 这句字符串——它即使被前面的 `return` 短路、或 `isAbsolute` 引入错了，也照样是绿的。全仓这类「用 grep 源码代替执行」的测试共 5 处（`routes:1300`、`watch:454/1414/1449`、`wake-order:9`），恰好都落在不可执行的路径上——它们本身就是覆盖缺口的症状。
- **如果它坏了会怎样（具体）**：
  1. **合法 token 存不进去，报错还怪客户**。`2048` 的正则只认 `gh[pousr]_` 与 `github_pat_` 两种形状；GitHub 一旦调整前缀/长度，客户贴的 token 会被 400 拒绝，提示「token shape not recognized」——他会以为是自己复制错了。
  2. **相对路径把 gh 指向随 cwd 漂移的目录**。`ghConfigDir` 若放行相对路径，`GH_CONFIG_DIR` 就跟着进程 cwd 变，`hosts.yml` 找不到 → 每轮「凭证失效」→ 客户按提示重新 `gh auth login` 也没用（他登录的是另一个目录）。
  3. **写盘失败被 `catch {}` 吞掉**（`284`），路由却回 200 并回读摘要。杀毒软件锁住 `secrets.json` 的那一秒，客户看到「已保存」，实际盘上还是旧值。
- **建议断言**（T5）：POST 合法 token（运行时拼接，不写真字面量）→ 200 且 `secrets.json` 里读到同一个值；POST `{ghConfigDir:'relative/dir'}` → 400 且 `secrets.json` 内容**逐字节不变**；POST 合法 token 后响应体里不得出现 token 本身。

## 三、确认覆盖良好

这些不用再花时间，测得住：

- **`lib/redact.js`：29/29 行、4/4 函数**。16 种凭证形状逐个验过，还有误伤样例（md5、commit sha、普通 URL）；样例串全部运行时拼接，不落字面量——这个习惯请保持（GitHub push protection 会拦）。
- **`lib/watch.js`：620/629 行（98.57%）、108/110 函数**。判定、文案、时间窗、优先级、合并、批处理全在纯函数层被覆盖，而且断言写得实（不是 `assert.ok(x)` 了事）。仅剩：超长标题换行 `156`、字符类非法分支 `1145`、以及两个只服务轮询的 push 函数。
- **`lib/gh-format.js`：278/281 行**。只剩归档/禁用两条文案和 `stateReasonNote` 的兜底 `return ''`。
- **`lib/gitee.js`：139/148 行（93.92%）**。请求层、分页、标签名规则、403 限流与权限的区分都测了；`giteeWhoami`/`giteeRepo` 两个一行包装没人调用（因为 `precheckRepo`/`viewerLogin` 没测）。
- **`lib/body.js`：17/18 行**。只差 `TextDecoder('gbk')` 的 catch（`15`）——这条兜底在运行时基本不可能失败，属于「测了也证明不了什么」。
- **`lib/index.js` 里覆盖得好的部分**：路由层的安全闸（跨站 403、`__proto__`、413、repo/编号校验）、`wakeMerged` 合并窗口、`parseGhInclude`/`classifyGhError` 的调用点、`/state` 的字段白名单。这些都有真执行、真断言。

### 5.5 附录：这个报告器为什么会错

`test/routes.test.mjs` 里对同一个模块 import 了 25 次（1 次不带 query + 24 次带 `?parity=`、`?status=`、`?json=` …），`contract-stability`/`cross-instance`/`state-merge`/`watch` 也各自带 query 加载。V8 里每个 query 都是一个独立脚本实例；Node 的覆盖率报告按 URL 聚合时只保留其中一份，于是**被真正调用的那个实例**可能正好被丢弃。可验证的推论：单独跑 `test/routes.test.mjs` 报 28.03%，跑全量反而只有 24.14%——全量不可能比单文件少覆盖。最小复现见第 0 节，我在本机跑过，稳定复现。
