## 2. N1 闭环复核：保存回读被刷新顶掉 → 不再假失败，真失败仍报错

### 2.1 修了什么

`load()` 被更新的一次请求顶掉时，旧代码在序号分支直接 `return null`，`run()` 的 `requireReload`
就把「成功」当失败（`操作已提交，但回读失败，请重试`）。现在：

- 序号落后时**不再返回 null**，而是 `await` 最新那次的 promise，用最新快照回话（成功/失败都跟随最新那次）。
- 位置：[client.js:2240](../client.js#L2240)（`latestLoadRef`）、[client.js:2249](../client.js#L2249)（成功支）、
  [client.js:2269](../client.js#L2269)（失败支）、[client.js:2278](../client.js#L2278)（登记最新 job）。
- `run()` 的失败语义没变：[client.js:2371-2375](../client.js#L2371) 仍是「回读拿不到 body 就抛
  `reloadError`」，所以「POST 200 + 回读 GET 500」照旧报错。

### 2.2 实测（受控 fetch 时序，真实 `client.js`）

同一探针分别跑本 HEAD 与修复前的 `c4800b5^`（只换 `client.js`，其余完全一致）：

| 场景 | 本 HEAD | 修复前 |
|---|---|---|
| goal：POST 挂起 → 成功 → 回读 GET#1 在飞 → 点「刷新」GET#2 → GET#1 先回、GET#2 后回 | **保存=true +「goal 已保存」，无「回读失败」** | 保存=false +「goal 已提交，但回读失败，请重试」 |
| 凭证：同一时序 | **保存=true +「凭证已保存」** | 保存=false +「凭证已提交，但回读失败，请重试」 |
| POST 200 + 回读 GET 500 | **保存=false +「回读失败」可见** | 保存=false +「回读失败」可见 |
| 回读被刷新顶掉、但**最新那次真失败**（断网） | **保存=false +「回读失败」可见** | 保存=false +「回读失败」可见 |

修复前那两条的原文（探针直接抓到渲染文本）：

```
goal 已提交，但回读失败，请重试
凭证已提交，但回读失败，请重试
```

本 HEAD 同一条路径输出的是 `goal 已保存` / `凭证已保存`，且文本里没有任何「回读失败」。
结论：**N1 闭环**，且失败语义没有被「等最新」吞掉——上一轮建议的核心是「等最新」，但如果实现成
「一律当成功」，POST200+GET500 就会变成假成功；本轮实测没有（最新那次失败仍然报错）。

仓库自带用例同样覆盖：[test/client.test.mjs:2362](../test/client.test.mjs#L2362)（两条保存场景，含
POST200+GET500 的既有断言保持绿）。

### 2.3 残留风险（非阻塞）

- **最新那次是更早开始的轮询**时，`run()` 会按那次轮询的快照判成功：极端情况下这个快照早于本次 POST，
  草稿清理后显示可能短暂回到旧值，下一次轮询（≤5 s）纠正。数据本身是写成功的，不丢数据。
- **保存途中切换 session**：旧闭包的 `load()` 若被新会话的 `load()` 顶掉，会等新会话的结果。
  面板按会话实例渲染，实际影响只到「切走那一帧的状态更新被丢弃」，无串值证据。

## 3. N2 闭环复核：删除失败只属于那一次确认框

### 3.1 修了什么

`clearDeleteError()` 只清 `删除失败：` 前缀（读取错误不动），并在三处调用：

- 打开删除确认时：DSH 路径走 [client.js:1697](../client.js#L1697) → `openDeleteConfirm`
  （[client.js:1740-1744](../client.js#L1740)）；旧宿主 fallback 路径走 `ConfirmButton` 的
  `onOpen`（[client.js:1936](../client.js#L1936)）。两条分支调的是同一个 helper。
- 关闭确认框时：[client.js:1861-1865](../client.js#L1861)。
- 开始一次删除时：[client.js:1836-1837](../client.js#L1836)（本次失败随后由 `act()` 重新写入）。

`deleteError` 仍直接取自 `orbitError`（[client.js:1867](../client.js#L1867)），所以「本次失败可见」不受影响。

### 3.2 实测（真实 `client.js` + 面板渲染桩）

| 步骤 | 本 HEAD | 修复前 |
|---|---|---|
| A 删除失败（500 `A denied`） | 确认框保留，框内 `删除失败：A denied` | 同左（本次失败本来就能看到） |
| 取消 → 状态里仍留着 `删除失败：A denied` | `queue[1]` 仍是该串（前置条件成立） | 同左 |
| 点 B 的「删除」 | 打开瞬间清空删除错误，框内**没有**任何「删除失败」 | **仍带着 A 的失败** |
| B 删除成功 | 框关闭、错误清空、共 2 次 delete | — |
| 再删 A 又失败（409 `A locked`） | 框内 `删除失败：A locked`（本次失败仍可见） | — |

修复前的失败原文：`打开确认框时必须清掉上一次的删除失败：[{"index":6,"next":true}]`
（只调了打开，没有任何清错误的 state 调用）。本 HEAD 同一断言拿到 `index:1, next:null`。

仓库自带用例：[test/client.test.mjs:1978](../test/client.test.mjs#L1978)。
结论：**N2 闭环**，两条删除分支共用同一个清理函数，实现层面不存在「修了一半」的分支。

### 3.3 边界

- 只清 `删除失败：`，读取错误（`读取失败：`）和写成功回读失败（`写成功了，但刷新列表失败：`）不清。
- DSH 分支的浏览器级复现没做（本轮探针走的是 fallback 的 `onOpen`；DSH 分支是
  `setAnchor` + `setOrbitError` 同一个 handler 内同步提交，静态确定，但属推断而非实测）。

## 4. N3 闭环复核：ETag 按作用域分开，两会话不串

### 4.1 修了什么

模块级 `stateEtag` 换成 `Map`，键是**完整 `/state` 路径**（含 `sessionId`）：

- 存储与读写：[client.js:522-530](../client.js#L522)。
- 写入点：304 分支 [client.js:565](../client.js#L565)、200 分支 [client.js:569](../client.js#L569)。
- 面板读自己的键：[client.js:2244-2245](../client.js#L2244)（`statePath` 带 `sessionId`）。

### 4.2 实测（真实 `client.js`，假服务端按作用域发不同 ETag 与 body）

| 请求序列 | 本 HEAD 发出的 `if-none-match` | 修复前 |
|---|---|---|
| 圆环挂载轮询 `/state` | 无（圆环只写不读） | 无 |
| 圆环第二次轮询 `/state` | 无 | 无 |
| 面板 s1 第一次 | **无**（不沿用圆环的 etag） | **`W/"global-1"`（串了）** |
| 面板 s1 第二次 | `W/"s1-1"` → **304** | — |
| 面板 s2 第一次 | **无**（不复用 s1） | — |
| 面板 s2 第二次 | `W/"s2-1"` → **304** | — |
| 无 sessionId 的面板（= 圆环作用域） | `W/"global-1"` → **304** | — |
| 再回 s1 | `W/"s1-1"` → **304**（交叉后不丢） | — |

同时断言了 body 不串：s1 拿到的 `sessionTitle` 是 `scope:/session-superagent/state?sessionId=s1`，
s2 是 `scope:…s2`；304 不产生新 body。8 次请求的 `path+search` 全部落在自己的作用域上。

修复前的失败原文：`s1 首次不得携带圆环作用域的 etag — actual 'W/"global-1"'，expected null`。

一个必须记清的机制点：**圆环自己从不发 `if-none-match`**（`loadState` 就是 `call('/state')`，
[client.js:1706](../client.js#L1706)）。所以 N3 修的是「圆环写 etag 污染面板」，
不是「圆环命中不了 304」。

仓库自带用例：[test/client.test.mjs:2411](../test/client.test.mjs#L2411)。
结论：**N3 闭环**，两个会话互不复用、全局作用域仍然自洽（无 sessionId 的面板与圆环同键，这是对的）。

### 4.3 残留（非阻塞）

- `stateEtags` 没有淘汰策略：每个 `sessionId` 留一条（几十字节），随「这次运行里看过的会话数」增长。
  量级几十条，不构成问题；要洁癖可以在 `sessionId` 变化时清掉旧键。
- 真实 Web GUI 里没有观察 304 命中（Chromium 的 apiLog 只记 method/path/body，不记条件头）。
