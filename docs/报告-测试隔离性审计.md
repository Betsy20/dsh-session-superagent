> 审计时间 2026-11-05 · 方式：**只读**（未改任何测试/代码，`git status` 干净）
> 基线：HEAD `47997a6`，Node v24.20.0 / win32，`node --test` 369 项
> 一句话结论：**默认跑法下隔离是好的** —— 22 个文件逐个单跑、全量跑、倒序跑，通过数一条不差（见 §一 的表）。

### 2. 【必须修】`npm test` 不带 `DSH_SUPERAGENT_OFFLINE=1`：会真的 spawn `gh`，同一个文件 1.1 秒 → 146.6 秒，超时就整文件红

**位置**

- `package.json:32` —— `    "test": "node --test",`（`package.json:33` 的 `"check"` 同）
- `test/routes.test.mjs:245-246` —— 作者自己知道要离线，但**只给 version 那条加了开关**：

```js
// 这条会真的去 npm registry 查最新版本，机器慢/网络抖时会撑到超时（跑过 5010ms 才失败）。
// 给它单独的宽松超时：要验的是「离线也必须给出 current」，不是网络速度。
test('/update 只读地报告版本（离线/在线都必须给出 current）', { timeout: 60000 }, async () => {
  // 走离线开关：这条用例不该因为 npm registry 抖动而红（曾经偶发超时 5 秒）
  process.env.DSH_SUPERAGENT_UPDATE_OFFLINE = '1'
```

`gh` 那几条（doctor / 断路器 / ack / diagnose）没有这层保护，靠的是**调用方**带 `DSH_SUPERAGENT_OFFLINE=1`。

**实测（同一台机器、同 58 项、全过，差在时间）**

```
带 OFFLINE：ℹ tests 58 / ℹ pass 58 / ℹ duration_ms 1123.5055
不带 OFFLINE：ℹ tests 58 / ℹ pass 58 / ℹ duration_ms 146574.2259
```

不带 OFFLINE 时最慢的三条（spec reporter 的括号内耗时）：

```
✔ 凭证失效时 doctor 要明说「不会自愈，需要重新登录」 (27839.3264ms)
✔ 连续失败很多次时，doctor 要解释「间隔已放慢」而不是让人以为卡住了 (25083.9444ms)
✔ 已知凭证失效时，工具直接拒绝发起请求（断路器的意思） (8376.9512ms)
```

**什么情况下红 / 什么时候绿**

- **绿**：显式 `DSH_SUPERAGENT_OFFLINE=1 node --test` → 1.9 秒 369 全过（本文 §三 有原始输出）。
- **红（已实测）**：任何带整体超时的跑法。我用 `timeout 120 node --test` 跑了一次全量（不带 OFFLINE）：

  ```
  ℹ pass 355
  ℹ fail 1
  ℹ duration_ms 119998.2107

  ✖ failing tests:

  test at test\routes.test.mjs:1:1
  ✖ test\routes.test.mjs (118385.8979ms)
    'test failed'
  ```

  也就是 `routes.test.mjs` 整份被 kill：`369 − 355 − 1 = 13` 项根本没跑到（killed 之前跑完的照算），文件本身记 1 条红。
- **红（换个机器就会）**：机器上没有 `gh`、或 `gh` 未登录、或网络抖动 —— 每次 `run('gh', …)` 都要等到自己的 `timeoutMs`（`lib/index.js:614` 的离线短路不生效时）。本机 `gh` 在、只是慢，就已经 146 秒。
- **更阴的一种"绿"**：机器上凭证**有效**时会走成功分支。`test/contract-stability.test.mjs:69-77` 为 ack 写了两种形态兜底，但别的断言（错误文案、`kind`）就未必；同一份代码在两台机器上跑出不同分支 = 典型的"偶尔绿偶尔红"。

**建议怎么改**

- 加 `scripts/run-tests.mjs`，照抄 `scripts/preflight.mjs` 已有的 `CHILD_ENV` 做法：

  ```js
  spawn(process.execPath, ['--test', ...process.argv.slice(2)], {
    stdio: 'inherit',
    env: { ...process.env, DSH_SUPERAGENT_OFFLINE: '1' },
  })
  ```

  `package.json` 的 `"test"` / `"check"` 都指到它。
- **别用 `--import`**：我实测过 `node --test --import ./x.mjs …`，`--import` **不透传给子进程**（子测试里 `process.env.MARK_FROM_IMPORT` 是 `undefined`），这条路走不通。
- 顺带把 `README.md:149`、`README.md:201`、`CONTRIBUTING.md:15`、`CHECKLIST.md:5`、`CHECKLIST.md:17` 写的裸 `node --test` 同步成 `npm test` —— 现在文档给的命令不是绿的那条。
- 备注：`docs/报告-CI与发布可靠性审计.md:273`（W6）记过「CI 全程离线 → 真实 `gh` 路径零覆盖」；本条是它的另一半：**离线开关没固化进 `npm test`**，于是「本地裸跑」和「CI」跑的根本不是一条路。

## 二、值得修

（按「离红最近」排序；每条的触发条件都写明，拿不准的都在这一节。）

### 2.1 `wakeBuffers` 只按 sessionId 归并，两条用例共用 `'s1'` —— 慢机器上第 2 条会拿到第 1 条的 busy 结论

- `test/wake-accounting.test.mjs:13-15`：

```js
process.env.DSH_SUPERAGENT_STATE = tempDir('zhuli-acct-')
process.env.DSH_SUPERAGENT_NO_POLL = '1'
process.env.DSH_SUPERAGENT_WAKE_WINDOW_MS = '5'
```

- `test/wake-accounting.test.mjs:36-38`（第一条，busy ctx）/ `:48-52`（第二条，idle ctx）：

```js
  __test.wakeMerged(makeCtx(busy), 's1', '测试消息', (result) => { settled = result })
  await wait(60)
  assert.ok(settled, '回调必须被调用（否则记账永远不会发生）')
```

```js
  __test.wakeMerged(makeCtx(idle), 's1', '第一条', (r) => { settled = r })
  __test.wakeMerged(makeCtx(idle), 's1', '第二条', (r) => { settled = r })
  await wait(60)
  assert.ok(settled && settled.ok === true, '应成功：' + JSON.stringify(settled))
```

- 根因在 `lib/index.js:694-717`：`wakeBuffers` 是**模块级 Map**，键只有 sessionId；缓冲由**第一次**调用的 ctx 打开，发送时用的也是那个 ctx。两条用例都是 `'s1'`，同一个模块实例。
- 探针实测（只读 import 仓库代码、窗口压到 20ms、写在 `%TEMP%` 里，未进仓库）：A 用 busy ctx 开缓冲，B 用 idle ctx 同窗口再塞一条，结果 B 的回调拿到 A 的结论：

```json
[["A",{"ok":true,"merged":true,"pending":1}],
 ["B",{"ok":true,"merged":true,"pending":2}],
 ["A-cb",false,"agent busy (running)"],
 ["B-cb",false,"agent busy (running)"]]
```

- **什么情况下红**：第一条用例的 5ms 定时器在第 2 条用例跑起来时还没 fire —— 也就是事件循环被拖 >60ms（第一条的 `await wait(60)` 先返回）。此时第 2 条拿到 `{ok:false,"agent busy"}`，`sent.length` 是 0，断言 `应成功` 红。
- **没能复现**：80 次单跑 + 30 次 8 核满载单跑 = **0 红**。所以只列「值得修」，不列「必须修」。
- 建议：两条用例换不同 sessionId（`'s1'` / `'s2'`）；或给 `__test` 加 `resetWakeBuffers()` 在 `beforeEach` 调；或把 `await wait(60)` 换成轮询到 `settled` 非空（上限 500ms）。

### 2.2 `contract-stability` 用裸 import 拿「第二个实例」，靠调用顺序才指对目录

- **什么时候会红 / 会闯祸**：只要有人在 `watch.test.mjs` 里加一句 `mod.__test.readState()`。`readState()` 不是纯读 —— `lib/index.js:146` 在备份恢复时会 `writeFileSync(STATE_FILE, …)`，`:151` 在文件坏掉时会把它 `renameSync` 成 `.corrupt-<ts>`。一次单测就能把生产状态改名。
- 建议：这三处在 import 前设 `process.env.DSH_SUPERAGENT_STATE = tempDir(...)`（和另外 7 个文件一致）；或者更彻底 —— `lib/index.js` 里检测 `process.env.NODE_TEST_CONTEXT`（node:test 在子进程里会设，实测值是 `child-v8`），在测试进程里拒绝写非临时目录。

## 三、确认隔离良好

以下各项都实际验过，不是"看着像没问题"。

1. **临时目录：文件名不会撞**。`test/` 下 39 处 `tempDir(...)`，0 处手写 `mkdtempSync(join(tmpdir(), …))`；`tempDir()`（`test/fixtures/tmpdir.mjs`）用 `mkdtempSync` 生成随机后缀并登记到 `process.on('exit')` 统一删除。所以「两个文件抢同一个临时目录」不可能发生 —— 22 个文件里重复的前缀（如 `zhuli-budget-` 在 `routes.test.mjs:682` 与 `:1139`）拿到的是两个不同的随机目录。
2. **没有端口冲突**。`test/` 下没有 `listen(`、没有 `createServer`、没有 socket。`routes.test.mjs:1339` 的 `http://127.0.0.1:65466` 只是塞进 `Origin` 头的一个字符串，不会建连接。
3. **没有 cwd 依赖**。`test/` 与 `test/fixtures/` 里没有 `process.chdir`；`process.cwd()` 只出现一次（`routes.test.mjs:307`），是当普通字符串参数传给 `watch_start`，不读不写盘。
4. **门禁锁不会互踩**。`test/gate-lock.test.mjs` 六条用例全部显式传临时 `lockPath`（`:16` 的 `tmpLock()`、`:71`），并有一条元用例（`:47-51`）专门断言这个文件里不许出现生产锁路径；`DSH_GATE_LOCK_TOKEN` 在 `:76-78` 的 `finally` 里 `delete`。
5. **纯函数模块没有可变模块级状态**。`lib/watch.js`、`lib/gh-format.js`、`lib/gitee.js`、`lib/redact.js`、`lib/body.js` 顶层没有 `let`/`new Map()`/`new Set()`（全部可变状态都在函数体内）。`lib/index.js` 里的模块级可变状态（`titleCache`、`sessionFileCache`、`ghHealthCache`、`authStatusCache`、`scopesCache`、`viewerCache`、`secretsHardened`、`activeBase`、`stateSource`、`lastWriteError`）都只在真实网络/真实会话路径上被写，而测试全程 `DSH_SUPERAGENT_OFFLINE=1` + `DSH_SUPERAGENT_NO_POLL=1`，不会触发。真正跨用例共享、可能咬人的只有 `wakeBuffers`（见 §二.1）。
6. **倒序跑不产生新红**：`node --test $(ls -r test/*.test.mjs)` → `tests 367 / pass 367 / fail 0`。
7. **重复跑稳定**：93 次全量重跑 0 红（见 §二.6 的清单）；单文件 22 次、`wake-accounting` 单跑 110 次（含满载）0 红。
