## 1. N1：保存回读被新请求顶掉时等最新快照

**复现**（`test/client.test.mjs:2362`，用例名 `N1：保存回读被刷新的新请求顶掉时等最新快照，不得假报回读失败`）

受控 fetch 时序（goal 与凭证各跑一遍）：

1. 点「保存 goal/凭证」→ POST 挂起；
2. POST 返回 200 → `run()` 发起回读 GET#1；
3. 点「刷新」→ GET#2（序号更新）；
4. GET#1 先回（旧序号）、GET#2 后回。

旧行为：GET#1 在 `load()` 里被判「已有更新请求在飞」→ 直接 `return null` → `run()` 的 `requireReload`
抛 `reloadError`，红色 Toast「goal 已提交，但回读失败，请重试」，保存返回 `false`。

**根因**：顶掉（superseded）与失败共用同一个 `null` 返回值，调用方无法区分。

**修法**（`client.js:2237-2270`）

- 新增 `latestLoadRef`（`client.js:2240`），每次 `load()` 把自己的 promise 记进去；
- 成功分支与失败分支里「被顶掉」都改成 `return await (latestLoadRef.current || null)`
  —— 等最新那次的结果，最新失败时仍然按失败返回；
- 304 无本体时清掉的 etag 改按作用域清（与 N3 同源），不再写模块级变量。

**验证**

- 该用例断言：`saved === true`、Toast 是「goal 已保存 / 凭证已保存」、**没有**「回读失败」文案；
- POST200+GET500 的既有语义不变：`test/update-ui.test.mjs:2043`（凭证）与 `:2068`（goal）保持绿，
  仍然必须在 `GET 500` 时返回 `false` 并显示可重试的回读错误。

## 2. N2：上一次删除失败不得残留到下一次确认框

**复现**（`test/client.test.mjs:1978`，用例名 `N2：上一次删除失败不得残留到下一次删除确认框，本次失败仍在框内可见`）

A 删除失败（500）→ 错误进当前确认框 → 取消 → 点 B 的「删除」→ 新确认框一打开就带着
「删除失败：A denied」，而 B 还没发任何请求。

**根因**：`orbitError` 里的「删除失败：…」只在 `act('delete')` 开始/成功时清，
打开确认框（`onRequestConfirm` 只 `setAnchor`、`ConfirmButton` 只 `setOpen(true)`）不清。

**修法**

- `clearDeleteError()`（`client.js:1738`）：只清理以「删除失败：」开头的错误，
  `读取失败：` / `写成功了，但刷新列表失败：` 原样保留；
- `openDeleteConfirm(watcher)`（`client.js:1740`）：先 `setAnchor`（保持原有 state 调用顺序），再清旧错误；
  DSH 路径 `onRequestConfirm` 改走它（`client.js:1697`）；
- fallback 路径给 `ConfirmButton` 加可选 `onOpen`（`client.js:1463` 参数、`:1476` 打开前调用），
  行内删除传入 `onOpen: clearDeleteError`（`client.js:1935`）；
- `act('delete')` 开头改用同一个清理（`client.js:1836`）；`closeConfirm` 关闭时也清（`client.js:1861`），
  失败后取消不会再让错误留在弹层里冒充新失败。

**验证**：A 失败时错误仍在当前框内（`role="alert"`，本次失败可见）→ 取消后状态里仍是旧错误（前置条件）
→ 点 B 的删除时记录到 `index 1 → null` 的清理调用 → B 的确认框文本**不含**「删除失败」→ B 成功删除后确认框关闭、错误清空。
既有 DSH 路径用例（`test/orbit-popover-integration.test.mjs:531/733/772`）全绿，确认焦点归还与 busy 禁 dismiss 未被破坏。

## 3. N3：ETag 按作用域存，圆环与面板不再互相顶掉

**复现**（`test/client.test.mjs:2411`，用例名 `N3：条件请求的 ETag 按作用域分开…`）

固定假服务端：`/state` 的 etag 为 `W/"global-1"`，`/state?sessionId=s1|s2` 各有自己的 etag。

1. 圆环作用域（无 sessionId）拉两次 → 第二次命中 304（老行为保留）；
2. 会话面板首拉**不得**携带圆环的 `W/"global-1"`（修复前实测带了，条件请求必然 200）；
3. 同会话第二次带上自己的 etag → 304，且 `setSnap` 不产生新 body；
4. 另一个会话不得复用 s1 的 etag；
5. 圆环作用域不受面板影响，仍命中自己的 304。

**根因**：`call()` 对任何 `/state` 响应都写同一个模块级 `stateEtag`；服务端 etag 对整份 body 求值，
圆环（全局 body）与面板（单会话 body）必然不同 → 面板的条件请求永远打不中 304（M1 修复带来的性能回归）。

**修法**（`client.js:518-531`）

- `stateEtags: Map`，键 = 请求 path（含 `?sessionId=…`）；`readStateEtag` / `writeStateEtag` 只处理 `/state` 前缀；
- `call()` 的 304 与 200 分支都写同一 scope（`client.js:565`、`:569`）；
- `load()` 用 `readStateEtag(statePath)` 生成 `if-none-match`（`client.js:2244`）；
- 不带 sessionId 时只有一个键 `/state`，与旧行为一致。
