## 结论摘要

门禁锁本身实现是对的（`mkdirSync` 原子性、陈旧锁清理、只删自己的锁，见「三、确认没问题」），**但它只被 2 个脚本使用；而 `verify-gates` 一个人就在 14 个路径上做注入写入，一次锁都没拿，也没有任何落盘恢复凭据**。于是：

### M5 `.gate-recover` 无条件写回：静默回滚并发改动（版本号被写回旧值）

**文件:行号**：`scripts/regression-cases.mjs:37-48`（还原）、`:98`（正常收尾也全量写回）

```js
// scripts/regression-cases.mjs:36-48
/** 开工前先把「上一次被强杀留下的改坏文件」还原掉（如果有）. */
function recoverFromLastRun() {
  if (!existsSync(RECOVER_MANIFEST)) return 0
  let manifest = {}
  try { manifest = JSON.parse(readFileSync(RECOVER_MANIFEST, 'utf8')) } catch { return 0 }
  let restored = 0
  for (const [rel, body] of Object.entries(manifest.files || {})) {
    try { writeFileSync(join(ROOT, rel), body); restored += 1 } catch { /* 尽力而为 */ }
  }
  try { rmSync(RECOVER_DIR, { recursive: true, force: true }) } catch { /* 下次再清 */ }
  if (restored > 0) console.log('（上一次门禁被强杀，已从 .gate-recover 还原 ' + restored + ' 个文件）')

}
```

**触发条件**：上一次门禁被强杀（`.gate-recover/manifest.json` 残留）→ 期间有人改了 `README.md` / `client.js` / `package.json`（最典型的就是**改版本号**）→ 下一次门禁启动。

### 1. 没有 `owner.json` 的锁会永久死锁，且永远不会自愈

**`scripts/gate-lock.mjs:57-82`**


### 6. `release-gh` 的「tag 已存在」只看本地，push 失败被吞掉且不改退出码

**`scripts/release-gh.mjs:74`、`:96-109`、`:120-126`**

```js

```

```js
  if (!existingTags.has(tag)) {
    const sha = commitFor(entry.version)
    if (!sha) { noCommit.push(entry.version); continue }
    if (!DRY) {
      run('git', ['tag', tag, sha])
      // 只推新建的这一个：`git push --tags` 会把历史遗留 tag 一起推，
      // 远端已有同名不同 sha 的会整批 reject（v0.2.0 就这样挡过一次）。

```

**触发条件**：`git push origin <tag>` 失败（网络 / 权限 / 远端已有同名不同 sha）。

2. 下一次运行时 `existingTags` 来自**本地** `git tag -l`，tag 已在本地 → 直接跳过 push；

**建议**：用 `git ls-remote --tags origin` 判断而不是 `git tag -l`；push 失败时 `process.exitCode = 1`。

### 互斥本身是原子的（`mkdirSync` + `EEXIST`）

`gate-lock.mjs:58-59` 用 `mkdirSync` 而不是「先 exists 再 mkdir」，在 NTFS 上是对的 —— 并发时只有一个进程能成功，另一个必然 `EEXIST` 进 `catch`。实测两个门禁同时抢，只有一个进入临界区（另一个在等 / 超时）。

### 陈旧锁清理是有效的


### 释放只删自己的锁

`gate-lock.mjs:65-72` 先 `readOwner` 比对 `pid`，不一致直接 `return`，不会拆掉新持有者的锁。（`owner === null` 时会走到 `rmSync`，见「二」第 1 条，但那是死锁路径，不是抢锁路径。）

### inode 比较在 Windows NTFS 上是可靠的

`sync-profile.mjs:63` 的 `statSync(src).ino === statSync(dst).ino` 不是「看起来对」—— 实测：

```console

b(硬链接) ino= 12947848934493516  -> 与 a 相同? true
c(复制)   ino= 10414574144162232  -> 与 a 相同? false
--- 原子替换（写临时文件再 rename）后 ---
```

也就是说：`writeFileSync` 原地改 → 同 inode（**内容自动同步，这正是 M1 的传播路径**）；`rename` 原子替换 → 换 inode → 被判成「断链」。判据本身正确。
