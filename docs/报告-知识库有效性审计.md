### 判定口径

| 判定 | 含义 | 本报告的验证动作 |
|---|---|---|
| **仍成立** | 规则描述的行为，今天的代码**仍然这么做** | 找到承载它的函数/常量 + 找到锁住它的用例 + 实跑 |
| **已失效** | 规则说的行为，代码**今天不这么做**了 | 复现出来 + `git log -S` 定位是哪次改动造成的 + 判「规则过时」还是「实现回退/不完整」 |
| **无法验证** | 规则是**流程性**的，代码里看不出来 | 只列出来，不硬判 |

执行原则：**「已失效」宁少勿滥**。凡是需要人拍板才能算「对」的（比如「这个权重合理吗」），一律不算失效；
只认**能用一条命令复现出来**的行为差异。

## 一、已失效（必须修）

### 1. `docs/kb/attention-list-order-is-a-decision.md` —— 「同一条只出现一次」今天不成立

**规则原文**（该条「做法」一节末尾）：

> 顺带修掉一个**重复推送**：`structure` 那条被 push 了两次，列表里会出现两条一模一样 ——
> 排序前先保证「同一条只出现一次」。

同一条给出的 rank 表还写着：

> | 6–7 | 暂停 / 未配置 token | 提示性 |

**代码现状**：

`client.js:1433` 的 `problems` 数组是**逐 watcher** 推的，每条用的 key 都是 `前缀 + watcher.repo`：

```js
// client.js:1433
const problems = []
…
// client.js:1438-1443
// 仓库结构问题（关闭 Issues / 是 fork）比轮询失败更早该说：它注定收不到条目
const structure = repoStructureNote(watcher.repoAccess)
if (structure) problems.push({ key: 's-' + watcher.repo, text: structure, rank: 3, kind: 'structure' })
// 只读：以前只在行内显示一个徽章，客户在「需要关注」里看不到，也不知道回写会 403
const readOnly = accessNoteForPanel(watcher.repoAccess, watcher.repo)
if (readOnly) problems.push({ key: 'ro-' + watcher.repo, text: readOnly, rank: 4, kind: 'readonly' })
```

循环变量是 `watchers`，而面板拿到的 `watchers` 是**全部会话**的守
（`lib/index.js:1696`：`const allWatchers = Object.values(state.watchers || {})`）。
于是只要两个会话守同一个仓库，`key` 就撞在一起、`text` 一字不差，列表里出现两条一模一样。

这不是假想：`lib/index.js:1740` 专门为「多会话守同一仓库」算了 `otherSessions` 字段
—— 说明这是**明确支持的产品形态**，不是边角输入。

**复现（真跑，非推断）**：用 `test/fixtures/panel-harness.mjs` 造两个守（`s1`/`s2` 同守 `a/b`，都 `archived: true`），渲染面板后取「需要关注」的条目：

```
--- 两守同仓库：dt-danger 共 2 条 ---
  [0] 这个仓库 已归档：GitHub 上归档仓库是只读的，评论和打标签都会失败 —— 守它只能看、不能回写。
  [1] 这个仓库 已归档：GitHub 上归档仓库是只读的，评论和打标签都会失败 —— 守它只能看、不能回写。
```

两条完全一样，正是规则说要消掉的那种「一模一样」。

**谁错了：实现不完整（不是规则过时）。**

`git show 9d6e146`（0.9.87，「顺带修掉重复推送」那次）显示，当时的改法是**删掉循环体里重复的那一行
`if (structure) problems.push(...)`**：

```diff
-        if (structure) problems.push({ key: 's-' + watcher.repo, text: structure })
         if (watcher.lastError) {
```

也就是只修掉了「**同一个 watcher 内**被 push 两次」，**从来没有做过按仓库去重**。
规则里写的「排序前先保证同一条只出现一次」是一句**当时的意图**，不是当时的实现 ——
所以这条规则从落地那天起就没真正成立过，只是一直没人用「两守同仓库」这个输入验过。

**顺带**：rank 表里的 `6`（暂停）已经不存在了 —— `client.js:1469` 那行注释写明「暂停原因不在『需要关注』里重复」，
`rank: 6` 已被刻意删除。规则表 6–7 两档现在只剩 7。

**修法（二选一，都要动代码，本次审计不动）**：

1. 在 `problems.sort(...)`（`client.js:1566`）之前按 `key` 去重：
   `problems = [...new Map(problems.map((p) => [p.key, p])).values()]` —— key 本来就是「前缀+仓库」，
   天然就是去重维度，改一行；
2. 或者承认「两守同仓库各说一条」是可接受行为，把规则改成
   「同一个 watcher 内同一条只出现一次」，并把 rank 表的 6–7 改成 7。

**推荐 1**：`otherSessions` 说明多会话守同仓库是常态，去重比改规则更符合产品意图。

## 四、反查：哪一类规则真的在守，哪一类写完就忘了

**方法**：把 182 个条目文件名当成标识符，在 `lib/*.js` + `client.js` + `scripts/*.mjs` + `test/*.mjs`

| 通知与消息设计 | 8 | 0 | **0%** |
| 判定与优先级 | 12 | 0 | **0%** |
| 安全 | 2 | 0 | **0%** |
| **合计** | **182** | **32** | **18%** |

### 反查结论

**① 「真的在守」的那一类：工程与文档（门禁类）。**

被引用的 32 条里，有 **21 条**集中在「工程与文档」板块，且都是同一形状 ——
它们被写进了 `scripts/render-acceptance.mjs` 的 `WHY` 表（「这项门禁防的是什么事故」），
而这个表本身有门禁：`render-acceptance.mjs --check` 会断言每个 `record('…')` 都有解释、
且解释里引用的 `KB \`xxx.md\`` 必须真实存在（`scripts/render-acceptance.mjs:81`）。

也就是说：**「工程与文档」这一类规则不只是被记住了，它们被编译成了门禁，还互相卡着。**
53% 的引用率是这套机制的直接产物。

**② 「写完就忘了」的那一类：交互与可用性 / 通知与消息设计 / 判定与优先级 / 安全。**

「通知与消息设计」8 条、**0 条**被引用；「判定与优先级」12 条、**0 条**；
「安全」2 条、**0 条**；「交互与可用性」44 条、只有 4 条。

这四类合计 66 条，只贡献 4 次引用（6%）。它们的特点是：
**规则正确、当时也实现了，但实现和规则之间没有一根线连着** —— 代码里没有一行注释指向那条规则，
所以下一轮改代码的人不知道自己在拆什么。

**③ 更尖锐的一条：生产代码（`lib/` + `client.js`）只引用了 3 条规则。**

剩下 29 条引用全在 `scripts/`（门禁脚本）里 —— 也就是说，
