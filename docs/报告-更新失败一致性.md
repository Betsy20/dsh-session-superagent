## 结论

已统一更新成功、非零退出、`spawn_error` 与超时后的缓存失效时机：缓存清理不再取决于 HTTP 回执是成功还是失败，而只取决于 runner Promise 是否真正 settle。旧 GET 通过 generation 比对无法把 settle 前的快照重新写回缓存。错误通道增加双层脱敏，405 响应补充 `Allow: GET, POST`，原 status/body 保持不变。

## 实现

### 1. 以 runner 实际 settle 为唯一缓存失效边界

`lib/index.js` 新增 `runUpdateAndInvalidateCache` 包装实际注入的 runner：

- runner fulfilled 或 rejected 时，`finally` 都执行 `updateCacheGeneration += 1` 与 `updateCache = null`；退出码 0、非零、`spawn_error`、runner 抛错采用同一边界。
- 外层已返回 504、runner 仍 pending 时，`finally` 尚未执行，不提前清缓存。
- 迟到 close/settle 后才清缓存并递增 generation；在飞的旧 GET 因 generation 不同不会回写安装前快照。
- semver/body 校验、profile 解析、并发闸等未调用 runner 的拒绝路径不会进入包装器，因此不清缓存。
- 删除原先仅在 `result.ok === true && result.code === 0` 时执行的缓存清理，避免成功路径重复递增 generation。

### 2. error 通道双层脱敏

- `lib/update.js` 的 `normalizeFailure`：对 `error.message` 先 `redact()`，再截到 1000 字符，避免截断后遗留可识别的 token 片段。
- `lib/index.js` 路由出口：对最终 `error` 再执行 `redact(String(error))`，覆盖 runner 直接 resolve `{ code: 'spawn_error', error: ... }`、未经过 `normalizeFailure` 的路径。
- stdout/stderr 原有脱敏与截断逻辑不变。

### 3. 405 Allow

`PUT` 等非 GET/POST 方法仍返回：

- status：`405`
- body：`{"error":"method not allowed"}`

新增响应头：`Allow: GET, POST`。

1. **非零退出与部分改盘**：runner 以 17 退出但改变 installed/latest；POST 仍为 500，随后 GET 必须重新读取磁盘与 registry，不能复用失败前缓存。
2. **504 / 迟到 settle / 旧 GET 竞态**：runner pending 时旧缓存继续可用；迟到 `spawn_error` settle 后才失效；settle 前启动的旧 GET 晚到不能回写；下一 GET 必须真查并看到部分改盘后的版本。
