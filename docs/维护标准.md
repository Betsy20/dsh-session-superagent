# 维护标准（本仓库版）

> 基准来自一份对成熟开源项目的调研（55 条，分必备 / 标杆 / 加分三档），
> 这里**只保留我们真会执行的**，其余写清「为什么不做」。
> 判断标准只有一条：**这条能不能被机器判真**。靠人记的，一律不算标准。

## 一、我们的底线（七条，违反即回滚）

1. **`main` 永远可安装**：合并前必须 `node scripts/preflight.mjs` 全绿；
2. **发布三件套**：`npm publish` + `git tag` + `GitHub Release`，标题只写版本号（`node scripts/release-gh.mjs --latest`）；
3. **凭证与路径不出插件**：所有返回过 `redact()`；新增输出路径必须补测试；
4. **没跑过的写成「未验证」**，不写「通过」；「包含某段文字」不算验证过；
5. **文档里的数字要有锚**：测试数由 `audit-readme-tests.mjs` 校验、KB 篇数由 `check-docs.mjs` 校验；
6. **修 bug 必带一条会红的用例**，否则下一个人会把它改回去；
7. **不代改他人 PR**：给意见让对方改，改完复核合入并署名。

## 四、我们**故意不做**的（写清理由，防止下次又讨论一遍）

| 项 | 为什么不做 |
|---|---|
| CodeQL / SBOM / 签名 release | 零依赖、无构建产物、单文件插件；收益低于维护成本 |
| 提交信息 lint | 强制英文 Conventional Commits 会挤掉「为什么这么改」的中文根因 |
| stale bot | 单人项目，issue 少到不需要自动关闭 |
| `enforce_admins=true` | 需要保留「线上坏了立刻直推修」的能力；用「发布前必须 preflight 全绿」代替 |
| 自动生成 CHANGELOG | 手写的「为什么改 + 数字证据」是给下一个维护者看的，工具生成不了 |

## 五、这套标准怎么被强制执行

```bash
node scripts/preflight.mjs            # 37 项，含 UI 体检 / 文档契约 / 维护一致性
node scripts/check-maintenance.mjs    # 版本 / tag / CHANGELOG / 徽章 六项
node scripts/check-docs.mjs           # 链接 / 索引总数 / 阅读路径
node scripts/audit-readme-tests.mjs   # README 的「N 项单测」与实际用例数
```

CI（`.github/workflows/ci.yml`）在每次 push 与 PR 上跑前三条中的前两条 + UI 体检 + 文档契约；
`check-maintenance` 只在 `main` 上跑（PR 分支还没有 tag，必然红）。

**标准写在文档里不算数，接进 CI 才算。**
