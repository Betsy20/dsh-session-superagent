## 一、必须修

### M1 `watch_stop` 停不掉 Gitee 守：schema 说 `owner/name`，id 却要 `gitee:` 前缀

**位置**：`lib/index.js:2860`（schema）、`lib/index.js:2867`（id 拼接）、`lib/index.js:2711`（`watch_start` 的 id 公式）

**schema 原文**（`lib/index.js:2857-2862`）：

```js
    name: 'watch_stop',
    description: 'Stop watching a repository for the current session.',
    parameters: {
      repo: { type: 'string', required: true, description: 'owner/name' },
      format: { type: 'string', description: "'text' (default) or 'json'." },
    },
```

**id 拼接**（`lib/index.js:2867`）：

```js
      const id = `${args.repo}#${sessionId}`
```

而 `watch_start` 建守时（`lib/index.js:2711`）：

```js
      const id = (provider === 'gitee' ? 'gitee:' : '') + `${repo}#${sessionId}`
```

**模型会怎么用错**：先 `watch_status` 拿守（这是它唯一的"机器可读"来源），再把 `watchers[].repo` 原样喂给 `watch_stop`。真实调用（`sessionId = session-audit`）：

```
── watch_start({"repo":"gitee:Ghandi/workbuddy-pro"})
   watching Ghandi/workbuddy-pro → session session-audit every 60s
── watch_status({})
   gitee:Ghandi/workbuddy-pro → session-audit | 每 60s | 还没轮询过
   session: 0/12 wakes last hour
── watch_status({"format":"json"})
   {
     "schemaVersion": 1,
     "session": {
       "id": "session-audit",
       "used": 0,
       "cap": 12,
       "capped": 0,
       "suggest": null
     },
     "watchers": [
       {
         "repo": "Ghandi/workbuddy-pro",
         "provider": "gitee",
         "sessionId": "session-audit",
         "enabled": true,
         "intervalSec": 60,
         "observe": false,
         "isolated": false,
         "activeHours": null,
         "labels": [],
         "onlyAssigned": false,
         "deferReason": null,
         "lastDeferred": null,
         "silentWakes": 0,
         "cursor": null,
         "lastPoll": null,
         "lastWake": null,
         "lastError": null
       }
     ]
   }
── watch_stop({"repo":"Ghandi/workbuddy-pro"})
   (no watcher for Ghandi/workbuddy-pro#session-audit)
── watch_stop({"repo":"gitee:Ghandi/workbuddy-pro"})
   stopped gitee:Ghandi/workbuddy-pro#session-audit
```

**结果**：照 schema 传 `owner/name` → `(no watcher for Ghandi/workbuddy-pro#session-audit)`，**守根本没停**（JSON 里 `enabled: true` 依旧，继续轮询、继续叫醒）；只有传 schema 里没写的 `gitee:Ghandi/workbuddy-pro` 才成功。同一份数据，文本模式给的是能用的键、JSON 模式给的是不能用的键。

**为什么算必须修**：这不是"用户写错了"，而是模型按说明书做、按工具自己的输出做，仍然失败；失败文案还是 `(...)` 而不是全套工具统一的 `[error: ...]`，模型很容易读成"本来就没有这条"，然后向用户汇报"已停"。

**建议**：`watch_stop` 复用 `parseRepoSpec()`（`2711` 与 `1942` 两处已经在用同一套 id 公式，`2779` 的注释还专门写了"id 必须和 applyOne 里算的一致"），或按 `repo` 字段匹配而不是拼 id。

### M2 `format: 'json'` 的错误分支返回纯文本（`watch_start` 7 处、`watch_ack` 2 处）

**位置**：`lib/index.js:2694`、`2699`、`2707`、`2708`、`2740`、`2741`、`2757`、`2785`（`watch_start`）；`lib/index.js:2293`、`2299`（`watch_ack`）

**schema 原文**（每个工具都有）：

```js
      format: { type: 'string', description: "'text' (default) or 'json'." },
```

**文档承诺**：`docs/json-契约.md:3`「所有工具都支持 `format: 'json'`，返回带 `schemaVersion` 的对象（当前 `1`）」；`README.md:161`「`watch_start` / `watch_stop` / `watch_ack` … 成功/失败都靠 `ok` 判断，不用读中文」。

**实测**：

```
── watch_start({"repo":"acme/alpha","workdir":"relative/path","format":"json"})
   [error: workdir must be an absolute path]
── watch_ack({"repo":"acme/alpha","format":"json"})
   [error: number (or numbers) is required]
── watch_ack({"repo":"nope/nope","number":1,"format":"json"})
   [error: no watcher for that repo — start one with watch_start first]
```

三条都明确传了 `format: 'json'`，返回的全是中文纯文本。任何按文档 `JSON.parse` 的消费方在这里直接抛异常；也拿不到 `ok`。

同文件的 `watch_trace`（`2389`、`2395`）和 `watch_stop`（`2871`）已经在错误分支里正确返回 JSON —— 说明这是漏改，不是设计取舍。

**建议**：抽一个 `fail(args, message)`，只在这一层决定文本还是 `{schemaVersion, ok:false, error}`。

### M4 必填字段没进 `required`：`watch_trace.number`、`watch_ack.number|numbers`

**位置**：`lib/index.js:2378`（trace）、`lib/index.js:2281-2282`（ack）

**schema 原文**（`lib/index.js:2375-2380`）：

```js
    parameters: {
      repo: { type: 'string', description: 'owner/name; defaults to the only watched repo' },
      // Gitee 的 issue 编号是字符串（IKSQJH），写成 number 会被宿主直接拒掉
      number: { type: ['number', 'string'], description: 'issue or PR number to trace' },
      format: { type: 'string', description: "'text' (default) or 'json'." },
    },
```

（`number` 没有 `required: true`；同一文件里 `watch_stop.repo`（`2860`）和 `github.path`（`2630`）都写了。）

**实测**（先建一条守，否则会先撞上"no watcher"，见下面第三段）：

```
── watch_trace({})
   [error: no watcher for that repo — run watch_status to see what is watched]
── watch_start({"repo":"acme/alpha"})
   watching acme/alpha → session session-audit every 60s
── watch_trace({})
   [error: number is required]
── watch_trace({"repo":"acme/alpha"})
   [error: number is required]
── watch_ack({"repo":"acme/alpha"})
   [error: number (or numbers) is required]
── watch_ack({"numbers":""})
   [error: number (or numbers) is required]
```

**结果**：schema 里 `number` 是"可选"，实测缺省必错；`watch_ack` 的"二选一必填"完全没表达（`defineTool` 造不出 `oneOf`，`lib/index.js:656-679`）。

顺带一个坑：`watch_trace({})` 在**没有任何守**时先报 `no watcher for that repo`，有守时才报 `number is required` —— 同一个调用有两种报错，模型按第一次的提示去建守，问题并不会解决。

**建议**：`watch_trace.number` 加 `required: true`；`watch_ack` 在 `number` 的 description 里补「不填则必须给 `numbers`」（两个字段各自写清，而不是只写在 `numbers` 一侧）。

## 二、值得修

### W1 `watch_ack` 的 `number` 只收 number，实现明确支持字符串编号

- **位置**：`lib/index.js:2281`（schema）vs `2289-2292`（实现：`String(args.numbers || args.number || '')`，正则 `^[A-Za-z0-9_-]+$` 放行 `IKSQJH`）
- **兄弟工具已经修过**：`watch_trace` 的同一字段是 `type: ['number', 'string']`，`2377` 的注释写着「写成 number 会被宿主直接拒掉」——`watch_ack` 没跟着改。
- **实测实现确实接受**（离线开关下，无网络写）：

```
── watch_start({"repo":"zzz-no-such-owner-9x/watch-audit-nonexistent"})
   watching zzz-no-such-owner-9x/watch-audit-nonexistent → session session-audit every 60s
── watch_ack({"repo":"zzz-no-such-owner-9x/watch-audit-nonexistent","number":"IKSQJH"})
   acked zzz-no-such-owner-9x/watch-audit-nonexistent #IKSQJH with label "主理鱼:已处理"
── watch_ack({"repo":"zzz-no-such-owner-9x/watch-audit-nonexistent","numbers":"IKSQJH,12"})
   acked zzz-no-such-owner-9x/watch-audit-nonexistent #IKSQJH #12 with label "主理鱼:已处理"
```

- **模型会怎么错**：Gitee 守的编号是 `IKSQJH`，语义上属于"单个编号"→ 模型会填 `number: "IKSQJH"`（schema 说不合法）；唯一可行路径是把**单值**塞进 `numbers`，而 `numbers` 的描述是「逗号分隔的多个编号，如 "12,13,14"（与 number 二选一）」，没提"Gitee 字符串编号也走这里"。
- **顺带**：`watch_ack` 的 description 与 `label` 默认值都只写 GitHub（`2283`「ack label, default 主理鱼:已处理」），而 Gitee 的默认标签是 `主理鱼-已处理`（`defaultAckLabel()`，`lib/index.js:652-654`），且 Gitee 走 `ensureGiteeLabel()` 自动建标签（`2311-2315`）—— 描述里一个字都没有。

### W2 `watch_start` 说「Watch a GitHub repository」，实际支持 Gitee 前缀/URL + 一次建多个仓库

- **位置**：`lib/index.js:2669`（description）、`2671`（`repo` 描述："owner/name. Omit to infer from the current working directory."）、`2705`（`String(repo).split(/[,\s]+/)` + `parseRepoSpec`）
- **实测**：

```
── watch_start({"repo":"m/one m/two"})
   watching m/one → session session-audit every 60s
   watching m/two → session session-audit every 60s
── watch_start({"repo":"gitee:Acme/Beta"})
   watching Acme/Beta → session session-audit every 60s
```

- **为什么值得修**：这是"代码支持、说明书没写 → 模型永远不会用"的典型。schema 里没有任何一处出现 `gitee:` 或"逗号/空格分隔多个"。README 有 Gitee 章节，但模型只看 schema。

### W4 `sessionMaxWakes` 说「整会话累计」，实际按条目存、显示只取 `list[0]`

- **位置**：`lib/index.js:2684`（描述 "Max wakes per hour for the whole session, summed across watchers (1-60, default 12)"）、`2748`（写进 `entry`）、`1332`（唤醒时用**当前条目**的 `entry.sessionMaxWakes`）、`lib/watch.js:1078`（状态只取 `list[0]`）
- **实测**（同样一个 `sessionMaxWakes: 3`，只是写在不同条目上）：

```
── watch_start({"repo":"acme/beta"})
   watching acme/beta → session session-audit every 60s
── watch_start({"repo":"acme/alpha","sessionMaxWakes":3})
   watching acme/alpha → session session-audit every 60s
── watch_status({})

   acme/alpha → session-audit | 每 60s | 还没轮询过

── watch_start({"repo":"acme/alpha","sessionMaxWakes":3})
   watching acme/alpha → session session-audit every 60s
── watch_start({"repo":"acme/beta"})
   watching acme/beta → session session-audit every 60s
── watch_status({})
   acme/alpha → session-audit | 每 60s | 还没轮询过
   acme/beta → session-audit | 每 60s | 还没轮询过
```

- **影响**："summed across watchers" 只有在**每条守都设**时才成立；写在一条上，只在轮到它轮询时生效，面板/状态数字还看它是不是 `list[0]`。模型按描述只设一次，会得到"看起来被忽略了"的结果。

### W6 `activeHours` 格式不对 = 静默失效，而 `watch_start` 照样回执成已生效

- **位置**：`lib/index.js:2680`（描述只给一个例子 `"09:00-23:00"`）、`2744`（只 `trim()`，不校验）、`lib/watch.js:576-587`（正则不匹配 → `return true` = 一直活跃）
- **实测**：

```
── watch_start({"repo":"acme/alpha","activeHours":"9-23"})
   watching acme/alpha → session session-audit every 60s [activeHours=9-23]
   inActiveHours("9-23", 02:00) = true
```

凌晨 2 点也算"在时段内"，而回执里 `[activeHours=9-23]` 看起来完全正常。模型转述用户口语（"只在 9 点到 23 点叫醒我"）时最可能写 `9-23`。

### W7 `observe` 会把水位前移：预览过的条目在关掉 observe 后不会补叫

- **位置**：`lib/index.js:1313-1329`（`entry.seen = advanceSeen(...)`、`entry.cursor = newestUpdatedAt(fresh) || entry.cursor`，注释还写着"仅观察模式已经把这一轮记完了"）
- **描述原文**（`lib/index.js:2677`）：`'Observe only: record what WOULD be woken, never wake.'` —— 没说"预览也消费水位"。
- **影响**：模型常把 `observe` 当"先试运行，确认没问题再开真唤醒"，结果试运行期间所有真条目都被记成已见，开启后一条都不叫。
- **说明**：这条是读代码 + 语义结论，**没有真跑轮询**（需要真仓库有动静），所以放"值得修"而不是"必须修"。

### W8 文档里的默认值漂移（不影响模型，影响照文档改代码的人）

- `docs/competitive-analysis.md:41`：「单次唤醒最多带 `batchLimit`（默认 3）条」；schema（`lib/index.js:2682`）与代码（`DEFAULT_BATCH_LIMIT = 5`，`lib/index.js:65`）、README（`README.md:27`「默认 5」）都是 5。

## 四、最容易误用的一处

**`watch_stop` 停 Gitee 守**（M1）。它比"忘了必填参数"（M4）更危险，因为模型在这一步**每一步都照着说明书做**：

1. 它先 `watch_status`（描述里唯一推荐的"看现在盯了什么"）；`format:'json'` 时拿到 `repo: "Ghandi/workbuddy-pro"` + `provider: "gitee"` —— 一个看起来完美的键值对。
2. schema 说 `repo` 是 `owner/name` —— 完全吻合。
3. 调用返回 `(no watcher for Ghandi/workbuddy-pro#session-audit)`，**不是** `[error: ...]`，模型很容易把它读成"这条本来就不在"或"已经停了"。
4. 于是用户被告知"已停止盯 Gitee 仓库"，而那条守仍在按 60 秒轮询、仍在叫醒会话。

叠加 M3 更糟：用户发现"还在叫"→ 说"停掉它"→ 模型停不掉 → 用户要求"换一个仓库盯"→ 20 条上限也不放行。三个必须修项在这条路径上会同时触发。

**其次是** `watch_ack` 不带编号（M4 + W1）：Gitee 用户看到 `[error: number (or numbers) is required]` 后，schema 里只有 `number: number` 这一个"单值"字段，模型会反复把 `IKSQJH` 塞进 `number` 继续失败，直到偶然读到 `numbers` 的中文说明。
