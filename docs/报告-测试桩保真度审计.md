## 一、会掩盖 bug 的差异（必须修桩）

> 判定标准：这条差异**已经**让一条「真机会坏」的改动在桩里保持绿。每条都给桩行号、真 React 行为、桩绿真机红的具体场景、改法，以及证据编号（探针 1–7 / 变异 M1–M9，原始输出见第五节）。

### 1.1 `useState` 的 setter 是空函数 —— 交互路径 0 覆盖

**桩**：`panel-harness.mjs:59-63`

```js
useState(init) {
  const value = hooks.index < hooks.queue.length ? hooks.queue[hooks.index] : (typeof init === 'function' ? init() : init)
  hooks.index += 1
  return [value, () => {}]        // ← 这里
},
```

**真 React**：调用 setter 会把「新值」记进这个 fiber 的 hook 队列并**调度一次重渲染**；组件函数重新执行，`useState` 返回新值。setter 的身份跨渲染稳定；传函数时按「上一次的值」计算（`setX(prev => ...)`）；`Object.is` 相等时跳过重渲染。

**桩绿真机红的场景**（三条，全部实测）：

- **设置页左栏点了不换内容**：把 `client.js:1964` 的 `onClick: () => setSettingsSection(item.key)` 改成 `setSettingsSection('source')` —— M2，**82 条全绿**。真机表现就是客户这次截图的那一屏：高亮动了、右边永远是「来源」。（0.9.248 修的是**取内容**那半边，**写状态**这半边至今零覆盖。）
- **面板永远「正在读取…」**：删掉 `client.js:1049` 的 `setSnap({ loading: false, error: null, body })` —— M1，**82 条全绿**。真机表现 = 0.9.167 那个真机 bug（`client.js:1026-1029` 的注释原话：「统计条全 0、列表空态、底下还挂着正在读取…」）。现有的「304 重取」用例（`test/client.test.mjs:1478-1490`）断言的是 `load()` 的**返回值**，跟 `setSnap` 有没有被调用完全无关。
- **页签点了不换**：`client.js:2178` 的 `onChange: setTab` → `() => {}` —— M6，**82 条全绿**。

**改法**（优先级最高，也是 1.2–1.4 的地基）：给桩一个「组件实例」概念 ——

1. `render()` 第一次调用时为这个 `registration` 建一个 hooks 数组（`{ states: [], setters: [], ... }`），**同一个 registration 再 render 时复用它**；
2. `useState` 读写 `instance.states[i]`，setter 写状态并**同步重跑一次根组件**（或标记 dirty，由 `render` 的返回值提供 `rerender()`）；
3. 顺带把 `assert.equal(hooks.index, queue.length)` 加在根组件调用后（见 1.4）。

最小可用版本：setter 至少**记录调用** `calls.push([index, next])`，用例就能断言「点这个按钮 → `setSettingsSection('creds')` 被调用」，不需要真重渲染也能堵住 M2 这类。但 M1（删除 setSnap 之后的 UI 状态）只有真重渲染才测得到。

### 1.2 `useEffect` 是空函数 —— 挂载 / 清理 / 焦点 / 轮询全是死代码

**桩**：`panel-harness.mjs:64`（`useEffect() {}`，不执行 body、不保存 cleanup、不看 deps）

**真 React**：commit 之后按声明顺序执行 effect；deps 浅比较，变了就先跑上一次的 cleanup、再跑新的；卸载时跑 cleanup。

**桩绿真机红的场景**：

- **Escape 关不掉术语表弹窗、Tab 能跑出弹窗、关闭后焦点不归还**：删掉 `client.js:458` 的 `document.addEventListener('keydown', onKey)` —— M7，**82 条全绿**。`Modal` 的整个 effect（`client.js:444-465`：记 `activeElement`、`setTimeout` 抢焦点、注册 Escape/Tab、cleanup 里 `clearTimeout` + 还焦点）在桩里**一行都没跑过**。
- **路由切换后轮询不停**：`usePoll`（`client.js:917-943`）的 cleanup `return () => { alive = false; if (timer) clearTimeout(timer) }` 删掉 —— 同样绿。真机是「切走之后定时器还在跑、还在打 `/state`」，属于内存/请求泄漏，肉眼很难发现。
- **首帧不拉数据**：`useEffect(() => { ... load() ... }, [])` 之类的挂载路径全部不执行。这也是为什么 `deskQueue` 必须手摆 21 个初始值 —— 面板真实的「挂载 → 拉 → 渲染」链路一次都没走过。

**改法**：跟 1.1 共用实例对象 —— 每次 render 收集 effects（`{ fn, deps }`），render 完统一 flush；`render` 的返回值带 `unmount()`（跑所有 cleanup）和 `rerender()`（先 cleanup 再跑新 effect）。沙箱要补 `setTimeout/clearTimeout`（见 1.5），否则 `Modal` 的 effect 一跑就 `ReferenceError`。

### 1.3 `useRef` 每次返回新对象、且 DOM ref 永远不 attach

**桩**：`panel-harness.mjs:66`（`useRef: (value) => ({ current: value })`），且 `createElement` 不处理 `ref`（`:50-55` 只剥了 `key`）。

**真 React**：`useRef(initial)` 在**同一实例的多次渲染之间返回同一个对象**，`initial` 只在首次挂载时用；给 DOM 元素的 `ref` 会在挂载后写入节点、卸载时写 `null`；回调 ref 同理（含 `null` 调用）。

**桩绿真机红的场景**：

- **保存静默不生效（lost update 类）**：把 `client.js:998` 的 `const touchedRef = useRef(new Set())` 改成 `const touchedRef = { current: new Set() }` —— M3，**82 条全绿**。真机上每次重渲染（每 5 秒轮询、每敲一个字符）都会把「这次编辑改过哪些字段」清空，点「保存」只发 `{repo, sessionId}`，服务端 200，Toast 照样说「已保存：a/b」，而 `intervalSec / labels / goal` 一个字都没写进去。这正是 T24 M1/M2 修过、`client.js:1096-1153` 里写满注释的那个 lost-update。
- **弹层定位 / 焦点归还**：`btnRef`（`:701`）、`panelRef`（`:702`）、`dialog`（`:442`）在桩里**永远是 `null`** —— 探针 7 打出来的是 `panel.props.ref = { current: null }`。所以「点击外面关闭」「打开后把焦点送进弹层」「关闭后还给圆环按钮」这些路径的 `if (ref.current)` 分支全是死代码。

**改法**：`useRef` 和 `useState` 共用 1.1 的实例槽位（`instance.refs[i]`，首次赋值后不再覆盖）；`walk` 里对 host 元素调用 `props.ref`（如果是函数就 `ref(node)`，如果是 `{current}` 就赋值），并在 `unmount()` 时写 `null`。这样 `ref.current` 才有真值，`btnRef/panelRef/dialog` 的分支才跑得到。

### 1.4 位置化队列 + 全局 hook index：静默错位，用例「测的不是它以为的状态」

**桩**：`panel-harness.mjs:43`（`const hooks = { queue: [], index: 0 }` 是**模块级全局**）、`:60`（队列不够就**静默**回落到初始值）、`:86-90`（`render` 每次重置 index，但**不校验**队列长度）。

**真 React**：每个组件实例有自己的 hook 链表，没有「外部按位置喂值」这回事；hook 顺序由组件自身决定，顺序变了就是另一份状态。

**桩绿真机红的场景**（这是本次审计最「阴」的一条，因为它让**现有的绿**变得不可信）：

- **14 条弹层用例全部错位**。`StatusOrbit` 的 hook 顺序是 `watchers / orbitError / open / anchor`（`client.js:696-700`），而用例清一色传 `[list, true, {x:720,y:860}]`（`test/client.test.mjs:43,100,122,188,205,236,242,1190,1202,1235,1247,1355,1366,1449`）。探针 1 直接打出来：

  ```
  x=100   → panel.style.left = 8  bottom = 64
  x=720   → panel.style.left = 8  bottom = 64
  x=1400  → panel.style.left = 8  bottom = 64
  渲染文本 = 主理鱼 | 1 / 1 | 主理中 | a/b | 主理中 | … | 操作失败：true | …
  ```

  也就是说：每个值都右移了一位 —— `orbitError` 拿到了 `true`（真机不可能出现的状态，因为代码里是 `setOrbitError(String(...))`），`open` 拿到了 `{x,y}`（靠 truthy 侥幸渲染），`anchor` 没值 → `null` → `left` 永远走 `else = 8`。**弹层的视口夹紧（`client.js:798-801`）从来没执行过**：M5 把 `Math.max(8, Math.min(anchor.x - width / 2, …))` 改成 `Math.max(8, anchor.x)` 也是 82 条全绿。真机窄窗口下弹层溢出右侧、`bottom` 算错，没有任何用例会红。
- **队列尾多出来的值被子组件吃掉**。探针 5：`deskQueue` 21 个值 + 追加 `true` → 按钮文案里出现「确认删除」—— 那个 `true` 落到的是**树里第一个 `useState` 子组件**（`ConfirmBtn.armed`），不是面板自己的任何状态。`test/client.test.mjs:426` 的注释还写着「第 13 个 hook 槽是 ConfirmBtn 的 armed」，实际已经是第 22 个 —— 这条注释本身就是错位在扩大的证据。
- **往中间插一个 `useState` 会整体右移**，而且**只有当新位置的旧值恰好是 truthy 时才会红**。`deskQueue` 的 21 个位置全靠三行注释维护（`panel-harness.mjs:111-119`，三行都在写「顺序必须跟组件里的 useState 一致」）。

**改法**（十行以内，收益最大）：

1. `render()` 在 `registration.Component(props)` 之后立刻 `assert.equal(hooks.index, queue.length, 'useState 槽位与 deskQueue 长度不一致')` —— 静默错位立刻变成红；
2. `StatusOrbit` 用一个具名队列：`orbitQueue(watchers, { open = false, anchor = null, error = null } = {})`，**别再**手写 `[list, true, {x,y}]`；
3. 子组件状态（`ConfirmBtn.armed`、`CollapsibleList.open`、`InfoTip.open`）改成按 1.1 的实例槽位寻址，或至少在 `walk` 里按组件名暴露 `stateOf(Component)`，不要靠「往队列尾追加」。

### 1.5 沙箱缺宿主 API —— 所有反馈（Toast）路径不可达

**桩**：`panel-harness.mjs:19-38`。给了 `window / document / fetch / setInterval / clearInterval / console`，**没有** `setTimeout`、`clearTimeout`、`navigator`、`document.hidden`、`document.activeElement`、`window.matchMedia`、`window.confirm`。

**真浏览器**：这些都存在（`matchMedia`/`confirm` 在 client.js 里是 try/catch 兜住的，`navigator` 没有兜）。

**桩绿真机红的场景**：探针 3 —— 点「保存凭证」，成功路径要 `notify('凭证已保存')`：

```
抛错 = ReferenceError: setTimeout is not defined
```

`useToast` 的 `notify`（`client.js:952-956`）里 `timer.current = setTimeout(...)` 是**每个成功/失败提示的必经之路**。也就是说：**面板上「已保存 / 已删除 / 已暂停 / 已恢复 / 已添加 / 复制失败 / 操作失败」这些反馈，一条都没有用例能跑**（跑就抛），更谈不上断言文案。`run()` 的 catch 里那句 `notify(text, 'error')` 被删掉也不会红 —— 真机上就是「点了没反应」（0.9.x 的经典投诉）。同理，`navigator.clipboard.writeText`（`client.js:1894/1914/2214`）在沙箱里是 `ReferenceError`，剪贴板三条路径零覆盖。

**改法**：沙箱补 `setTimeout/clearTimeout`（一个可手动 `flushTimers()` 的队列，默认不自动跑，避免测试之间互相干扰）、`navigator = { clipboard: { writeText: async (t) => calls.push(t) } }`、`document.hidden`（可写，测隐藏降频 6 倍）、`document.activeElement`（可写）、`window.matchMedia`（返回 `{ matches }`，测减少动效）。

## 二、已知但可接受

> 判定标准：**差异真实存在，但没有一条现行代码路径会因此掩盖 bug**（或代价明显大于收益）。每条给桩行号 + 真 React 行为 + 为什么可以接受 + 什么时候该升级成「必须修」。

### 2.1 `useCallback` 的 deps 被忽略

**桩**：`panel-harness.mjs:65`（`useCallback: (fn) => fn`）。**真 React**：deps 浅比较不变时复用**旧闭包**；少写依赖 = stale closure（永远看到第一次渲染的 state/props）。

**为什么可接受**：桩每次返回新函数，等价于「永远最新闭包」—— 它**掩盖**少写依赖的问题，但方向是「让代码更好、不是更坏」。当前三处 `useCallback`（`client.js:952` `notify`、`:1036` `load`、`:1968` `checkUpdate`）只读 setter / ref / 模块级变量，没有现行 bug。**升级条件**：1.1 的重渲染落地后，这条会被自动覆盖；在那之前，可以在 `scripts/audit-react-semantics.mjs` 里加一条静态检查（`useCallback` 体内读到的 `useState` 值必须在 deps 里）。

### 2.2 `props.children` 归一化：永远数组、null/false 被滤掉

**桩**：`panel-harness.mjs:53`。**真 React**：`createElement(type, config, ...children)` 在 `children.length === 1` 时给**单个值**（字符串/元素），否则给数组；`null` / `false` **保留**在 `props.children` 里（渲染时才丢弃）。

**为什么可接受**：当前所有 `props.children` 读取都做了数组归一（`[].concat(...)` 或 `[...(x || [])]`），而且 `dt-ticket-meta` 传了 6 个参数、重建后 7 个（探针 4：桩里 `length = 2`、`含 null = 0`；真 React 是 7 个、5 个 null），**碰不到单子节点分支**。但 `client.js:1421` 的 `[...(meta.props.children || [])]` 是个 landmine：哪天台账只剩一个子节点（比如加个 feature flag 把徽章关掉），真机就是 `TypeError: meta.props.children is not iterable`，桩仍然绿。**升级条件**：这条写法出现第二处，或者有人在这里加条件渲染。

### 2.3 `ref` 留在 `props` 里（`key` 的镜像）

**桩**：`panel-harness.mjs:50-55` 只剥了 `key`，没剥 `ref`。探针 7：`panel.props.ref = { current: null }`；真 React 的 `div` 上 `props.ref` 是 `undefined`（ref 挂在 `element.ref`；React 19 起函数组件的 ref 变成普通 prop，但 host 元素仍不在 props 里）。

**为什么可接受**：`client.js` 里**没有一处**读 `.props.ref`，`scripts/audit-react-semantics.mjs` 也只扫 `props.key` / `props` 赋值。所以它是「潜在的、还没被踩到的」同类。**升级条件**：任何人开始写 `props.ref` —— 但更省事的是现在就一行修掉：`const { key, ref, ...rest } = props || {}` + `node.ref = ref`，并把审计脚本的正则从 `props.key` 扩到 `props.(key|ref)`。

### 2.4 `memo: (fn) => fn`

**桩**：`panel-harness.mjs:58`。**真 React**：`memo()` 返回一个 exotic 对象（不是函数）。桩把它变成函数本身，`walk`（`:104`）会把 `h(MemoComp, …)` 当函数组件展开。

**为什么可接受**：`client.js` 只解构了 `useCallback/useEffect/useRef/useState`，**没用 `memo`**。真用上时，桩这边「能跑」、真 React 那边 `walk` 看到的是对象不是函数 —— 表现是**假红**（找不到节点），不是假绿。**升级条件**：开始用 `memo` 时，把 `walk` 的判断改成「`typeof type === 'function' || (type && type.$$typeof)`」。

### 2.5 重复 `key` 没有任何警告

**桩**：`createElement`（`:46-57`）不校验 key 唯一性，`walk`（`:97-108`）也不读 key。注意 **key 本身是可见的**（`node.key`），只是 82 条用例里 0 条读它。

**为什么可接受**：当前所有列表 key 都唯一（`repo#sessionId`、`b-<badge>`、`day-<date>`、`repo-<name>` 等，逐个核对过），而且 `problems` 列表在 `client.js:1574` 先按 key 去重（T34 的修法）。**升级条件**：M4（把行元素的 key 全改成 `'row'`）实测 82 条全绿 —— 真机上 React 会 console.error 并复用实例，让「删除」按钮的 armed 串到别的守身上。建议加一个 `assertUniqueKeys(tree)` 助手，在 3 个多行列表用例里调用。

### 2.6 样式注入不可断言

**桩**：`document.getElementById` 恒 `null`（`:28`）、`createElement` 返回 `{id, textContent}`（`:29`）、`head.appendChild` 空实现（`:30`）。**后果**：`ensurePortedCss`（`client.js:165-179`）的幂等分支永远走「没有」，`PORTED_CSS` 的**内容**一个字都没断言过。

**为什么可接受**：M8（把守卫的 id 打错成 `dsh-zhuli-ported-cssX`）实测 82 条全绿；真机后果是每次渲染多插一份 40KB 的 `<style>`（性能问题，不是功能问题）。**升级条件**：样式再出一次「面板裸文字」的真机 bug（0.9.159 那种）就补：让 `head.appendChild` 记录节点，加一条「只插一份 + 内容含 `.dt-page` / `.sa-dock-panel`」。

**为什么可接受**：`usePoll` 从不执行 → `discoverBase` 在测试里本来就是死代码。但「路由前缀发现」是注释里写满真机事故的地方（`client.js:19-53`：宿主重载、旧 handler 摘不掉、`/rN` 前缀），目前零覆盖。**升级条件**：1.2 的 effect runner 落地后必须一起补，否则轮询一跑就会撞上。

### 2.8 `matchMedia` / `navigator` / `document.hidden` 缺失

沙箱（`:19-38`）里 `window.matchMedia` 不存在 → `prefersReducedMotion()`（`client.js:547-549`）走 catch 返回 `false`；`document.hidden` 不存在 → 隐藏降频 6 倍（`:931`）永远走 false；`navigator` 不存在 → 剪贴板三条路径（`:1894/1914/2214`）抛 `ReferenceError`。**为什么可接受**：三条都是「少测一个分支」，不会让错误代码变绿（剪贴板那条甚至会抛，属于假红）。**升级条件**：1.5 补沙箱时顺手一起补。

### 2.9 没有 StrictMode 双调用 / 没有 unmount

**桩**：`render`（`:86-90`）只调用一次组件，没有卸载。**后果**：渲染期副作用（`client.js:1031` 的 `hasBodyRef.current = Boolean(snap.body)`）与 `apply()` 里的 `note(...)`（`client.js:2263`）在 StrictMode 下会跑两次，桩里看不到；cleanup 顺序（`Modal` 的 `clearTimeout` → `removeEventListener` → 还焦点）不可验证。**为什么可接受**：当前副作用都是幂等的。**升级条件**：1.2 落地时一并做 `unmount()`。

### 2.10 `walk` 假设 `props.children` 可迭代

**桩**：`panel-harness.mjs:106`（`for (const child of node.props?.children || [])`）。**真 React** 单子节点是字符串，`for...of 'abc'` 会按**字符**拆成 3 个文本节点。**为什么可接受**：桩自己的 `createElement` 保证 `children` 永远是数组，所以不可达；只有测试手写裸节点（`test/client.test.mjs:1328` 那种 `walk({type:'div', props: group.props})`）才可能碰到。**升级条件**：`walk` 加 `Array.isArray(children) ? children : [children]` 一行即可。

### 2.11 设置页 5 个分区只断言了 3 个

`test/client.test.mjs:1593-1596` 只覆盖 `source / creds / goal`；`update` 和 `diagnose` 的顺序漂移不会红。0.9.248 的修法把「按 key 查」换成了「按顺序取」（`client.js:1957`：`SETTINGS_SECTIONS.findIndex(...)` + `settingsSections[settingsIndex]`），两个数组由**下标**隐式耦合 —— 顺序一改就整块错位，而这条新耦合目前没有完整断言。**为什么可接受**：顺序由同一段源码（`client.js:1832/1947`）里两个相邻的数组字面量维护，改一个忘一个的概率低。**升级条件**：下次动设置页时，把 5 个 key 各断言一次（`bodyOf(k)` 的首个文本 ≠ 其他 key）。

## 三、确认一致

> 这一节是「对照过、没问题」的部分 —— 包括任务书里**假设成立但实际不成立**的那条（3.2）。

### 3.1 `createElement` 剥 `key`（0.9.248 的修法本身）

**桩**：`panel-harness.mjs:50`（`const { key, ...rest } = props || {}`）+ `:55`（`if (key !== undefined) node.key = key`）。
**真 React**：`key` 是特殊字段，不进 `props`，挂在 `element.key` 上（React 18/19 都是）；`key` 缺省时是 `null`。
**对照结果**：`node.props.key === undefined`、`node.key === <值>` —— 与 React 一致。唯一的缺省值差异是「没传 key 时桩给 `undefined`、React 给 `null`」，没有代码读它，无影响。

### 3.2 元素重建**不会**丢 `key` / 丢 `ref`（任务书假设不成立）

**代码**：`client.js:1409-1425`

```js
const bodyChildren = [].concat(rowBody.props.children || []).filter(Boolean)
…
bodyChildren[metaAt] = {
  ...meta,
  props: { ...meta.props, children: [...(meta.props.children || []), actions] },
}
```

**结论**：`{ ...meta }` 复制的是元素对象的**自有可枚举属性** —— `type`、`props`、`key`（桩里还有 `ref`）全部带过去，所以既不会丢 `key` 也不会丢 `ref`；新建的 `props` 对象还顺手避开了「开发模式冻结 props」的坑。**这条假设不成立**，不需要修。
唯一的语义差异是 `key` 的缺省值（3.1 末尾）和「重建出来的对象不是 `createElement` 的产物」—— 后者在真 React 里仍然是一个合法的 `ReactElement`（`$$typeof` 被展开复制），`walk` 也照样把它当 host 节点，两边一致。

### 3.3 `Fragment` 用 `Symbol('Fragment')`

**桩**：`panel-harness.mjs:45`；**用法**：`client.js:908` 的 `h(React.Fragment, null, button, panel)`。
**真 React**：`Fragment` 是 `Symbol(react.fragment)`，渲染时**不产生 DOM 节点**，只是把 children 摊平。
**对照结果**：桩里它成了一个普通对象节点，`walk` 会把它自己 push 进结果再下钻 children。对「找 `role=dialog` 的按钮 / 弹层」这类断言**完全等价**（`walk` 的 `out` 里多一个 Fragment 节点，但不影响 `find`/`filter` 的结果）。唯一会不一致的是「数 DOM 节点个数」的断言 —— 现有用例没有这么写的。

### 3.4 `useState` 的惰性初始化与返回形状

**桩**：`:60`（`typeof init === 'function' ? init() : init`）+ `:62`（返回 `[value, fn]`）。
**真 React**：惰性初始化只在首次挂载调用一次；返回 `[state, setState]` 二元组。
**对照结果**：一致（「只在首次挂载」这半句在桩里退化成「每次 render」，但桩本来就不能重渲染，见 1.1）。

### 3.5 `useCallback` 的返回形状

**桩**：`:65`。返回的是函数本身，与真 React 的「返回一个函数」在**形状**上一致；身份语义的差异见 2.1。

### 3.6 `h = React.createElement` 与 children 扁平化

**桩**：`client.js:13` 的 `const h = React.createElement`；`panel-harness.mjs:53` 的 `children.flat(Infinity)`。
**真 React**：同样把嵌套数组摊平（`[a, [b, c]]` → `a b c`），同样丢弃 `null/false/undefined`**在渲染时**（但 `props.children` 里保留，见 2.2）。
**对照结果**：渲染结果一致。

## 附：顺带发现（只读审计的副产品，本轮**没有改**）

1. **`Modal` 的 effect 依赖了内联箭头，弹窗开着时每 5 秒被抢一次焦点。**
   `client.js:444-465` 的 deps 是 `[open, onClose]`，而两个调用点（`:2204`、`:2222`）传的都是 `onClose: () => setGlossary(false)` —— 每次父组件重渲染（5 秒轮询 `load` → `setSnap`）都产生新函数 → effect 先 cleanup（`clearTimeout` + `removeEventListener` + **把焦点还给触发元素**）再重新跑（记 `activeElement` + `setTimeout` 抢回弹窗）。真机表现：术语表开着的时候，焦点每 5 秒抖一下。桩看不见（effect 从不执行，1.2）。修法：`onClose` 用 `useCallback` 包一层，或者把 `onClose` 从 deps 里去掉、用 ref 存。
2. **`settingsSections[settingsIndex]` 用「同序数组下标」耦合两个数组**（`client.js:1957`）。0.9.248 的修法本身把「按 key 查」换成了「按顺序取」—— 这是**新的 silent-failure 面**：两个数组任何一处顺序调整都会整块错位，而 2.11 说的 5 个分区只断言了 3 个。
3. **Toast 停留时长有两份来源**：`client.js:963-964` 的 `--dt-toast-hold: 3600ms` 和 `client.js:955` 的 `setTimeout(..., 4000)` 不一致（3.6 秒 vs 4 秒）。视觉上无害，但「改一个忘一个」是这套代码里反复出现的模式。
4. **`test/client.test.mjs:426` 的注释已经过时**：「第 13 个 hook 槽是 ConfirmBtn 的 armed」—— 实际是第 22 个（探针 5）。这类注释是位置化队列唯一的文档，过时一次就会误导下一个人。
