## 一、必须修

### M1 · `/watch` 的 20 条上限把「已暂停」也算进去 —— 面板死结，模型却能建

**位置**：`lib/index.js:1986-1988`（HTTP 面板路径）· 对照 `lib/index.js:2837`（工具路径）

```js
// lib/index.js:1986  HTTP /watch —— 数「全部守」，含 enabled:false
if (created) {
  const mine = Object.values(state.watchers).filter((w) => w && w.sessionId === sessionId)
  if (mine.length >= MAX_WATCHERS_PER_SESSION) {
    return json(res, 429, { error: '一条会话最多挂 ' + MAX_WATCHERS_PER_SESSION + ' 条守' })
  }
```

```js
// lib/index.js:2837  工具 watch_start —— 只数「还在跑的」
const mine = Object.values(state.watchers).filter((w) => w && w.sessionId === sessionId && w.enabled !== false)
```

**客户会遇到什么**：`watch_stop`（工具）只把 `enabled` 置 `false`，条目仍在状态文件里。所以「模型停过 20 个仓库」的会话，客户在面板上点「添加」会永远收到 `一条会话最多挂 20 条守`，**而屏幕上那 20 条全是「已暂停」**。他会去点「暂停」（已经是暂停了）、去点「恢复」（越点越满），就是想不到要「删除」—— 因为报错没写。

同一条会话，同一时刻，模型调 `watch_start` 返回 `ok: true`，面板返回 429。**两个入口对同一个事实给出相反答案**，这是本仓库历史上被判过「死结」的同一个 bug（`lib/index.js:2834-2836` 的注释记录了它在工具路径上被修掉的经过），HTTP 路径漏了。

**建议**：`lib/index.js:1986` 的过滤加上 `&& w.enabled !== false`，与工具同口径；错误文案改成「已挂满 20 条**在跑的**守：删掉不用的（暂停不释放名额）」。

**取证**（真实运行，见附录 C.3）：

```
POST /watch acme/fresh-panel（第 21 条，前 20 条全已暂停）
    → HTTP 429 {"error":"一条会话最多挂 20 条守"}
watch_start acme/fresh-tool（同一条会话）
    → { "schemaVersion": 1, "ok": true, "repo": "acme/fresh-tool", ... }
```

### M2 · `allowAuthors` 两条路都是死的 —— 面板新加的输入框和工具参数一样，收下、回 `ok`、永不生效

> 0.9.252 刚给面板加了「只理这些人提的」输入框（`client.js:1392`），但没同时改 `mergeFilters`。**结果不是「一边好一边坏」，是两边都设不上** —— 而且面板上那句提示是句谎话。

**位置**：`lib/index.js:2806`（工具侧写进 patch）· `client.js:1107-1112`（面板侧写进 `filters`）→ 两条路都进 `lib/watch.js:687-699`（`mergeFilters` 没有 `allowAuthors` 分支）

```js
// lib/index.js:2806  工具把 allowAuthors 放进 patch
if (args.allowAuthors !== undefined) patch.allowAuthors = args.allowAuthors
if (Object.keys(patch).length > 0) entry.filters = mergeFilters(entry.filters, patch)
```

```js
// client.js:1107-1112  面板「只理这些人提的」→ 塞进 filters.allowAuthors
filters: {
  labels: ...,
  onlyAssigned: !!draft.onlyAssigned,
  // 必须带上：filters 是**整块**发出去的，漏了它会把作者名单清空
  allowAuthors: String(draft.allowAuthors || '').split(',').map((v) => v.trim().replace(/^@/, '')).filter(Boolean),
},
```

```js
// lib/watch.js:687  mergeFilters 只认这 7 个键，allowAuthors 被静默丢弃
export function mergeFilters(base, patch) {
  ...
  if ('labels' in patch) next.labels = ...
  if ('ignoreLabels' in patch) next.ignoreLabels = ...
  if ('skipBots' in patch) next.skipBots = ...
  if ('skipDrafts' in patch) next.skipDrafts = ...
  if ('skipClosed' in patch) next.skipClosed = ...
  if ('onlyAssigned' in patch) next.onlyAssigned = ...
  if ('assignee' in patch) next.assignee = ...
  return next            // ← allowAuthors 不在其中
}
```

**客户会遇到什么**：

1. **面板上明写着「只理这些人提的」，旁边一行小字「不在名单里的人提的 issue/PR 不会叫醒你」**（`client.js:1392`）。客户填上 `alice`、点保存、看到「已保存」的 Toast —— 然后别人的 issue 照样把他叫醒。
2. 模型（或客户通过模型）说「只处理 alice 提的」，工具回执 `ok: true`、`flags` 里也没有任何提示，落盘后 `filters.allowAuthors` 恒为 `[]` —— 而 `[]` 的语义是**谁都算**（`lib/watch.js:339` 只在非空时过滤）。
3. 打开编辑框再看，那个输入框**是空的**（`client.js:1286` 从 `watcher.filters.allowAuthors` 回填，而它是 `[]`）。客户会以为刚才没保存上，重填、再保存、再空 —— 无限循环。

**自查不了**：`watch_status` 的 `statusView` 根本不回传 `allowAuthors`（见 W4），面板的 `filterText` 也不渲染它。所以「到底设上没有」两条路都查不到。

**为什么全绿也没发现**：`test/watch.test.mjs:1689`「只理名单里的人」只测了 `filterReason` 和 `normalizeFilters`，**没有一条用例走 `watch_start → mergeFilters` 或 `POST /watch → mergeFilters` 这条真实链路**。这是典型的「断言强度和实现强度不匹配」。

**建议**：`mergeFilters` 补一行 `if ('allowAuthors' in patch) next.allowAuthors = normalizeFilters({ allowAuthors: patch.allowAuthors }).allowAuthors`；再补一条「两条路各调一次 → 读状态文件 → 断言非空」的用例（`test/watch.test.mjs:1689` 那条扩一句就够）。

**取证**（真实运行，见附录 C.2 与 C.6）：

```
面板编辑保存 filters = {"labels":["bug"],"ignoreLabels":[],...,"allowAuthors":[]}   ← 面板传了 ['alice','bob']
工具 watch_start filters = {"labels":[],"ignoreLabels":[],...,"allowAuthors":[]}      ← 工具传了 ['alice','bob']
```

### M3 · 面板「追溯」只认纯数字 —— Gitee 编号没有任何入口

**位置**：`client.js:1635` · 对照 `lib/index.js:2436`（工具 schema）

```js
// client.js:1635  「判定」页的追溯入口：只接受纯数字（可带 #）
const asNumber = /^#?[0-9]+$/.test(needle) ? needle.replace('#', '') : ''
```

```js
// lib/index.js:2434-2436  工具侧明确支持字符串
// Gitee 的 issue 编号是字符串（IKSQJH），写成 number 会被宿主直接拒掉
number: { type: ['number', 'string'], required: true, description: 'issue or PR number to trace' },
```

**客户会遇到什么**：Gitee 的 issue/PR 编号是 `IKSQJH` 这类字符串。Gitee 客户在「判定」页的搜索框里输入 `IKSQJH`，**「追溯 #」按钮根本不出现**（`client.js:1638` 的 `asNumber ? ... : null`）。面板上那句提示却写着「在右上角搜索框输入编号（如 42），就能查它经历了什么：被过滤、已唤醒，还是根本没轮到」—— 客户照做，输入框里打着字，按钮就是不出现，也没有任何解释。

而「这条为什么没叫醒我」正是这个插件最核心的诉求。Gitee 客户被完全切断在门外，**而且只有模型能替他查**（`watch_trace` 支持字符串）。如果模型不说，客户永远不知道自己追不了。

**建议**：`/^#?[0-9]+$/` → `/^#?[A-Za-z0-9_-]+$/`，与 `watch_trace`（`lib/index.js:2452`）、`watch_ack`（`lib/index.js:2343`）用的字符集完全一致。

**取证**（真实渲染，见附录 C.4）：

```
搜索框="42" → 追溯 #42
搜索框="IKSQJH" → （没有追溯入口）
搜索框="#42" → 追溯 #42
```

## 二、值得修

> 「拿不准」的一律放这里。「必须修」只放会被卡住或产生错误理解的。

### W1 · HTTP 路径不校验 `activeHours`，非法值静默变成「全天有效」

- **位置**：`lib/index.js:2028`（HTTP 只 `trim().slice(0,20)`）· 对照 `lib/index.js:2819-2822`（工具走 `validateActiveHours` 并拒绝）
- **兜底为什么会静默**：`lib/watch.js:615-625` 的 `inActiveHours`，正则不匹配时 `return true` —— 等于「全天都在活跃时段」。
- **客户会遇到什么**：`activeHours: "9-23"`（少了前导 0）在面板接口上返回 `HTTP 200`，落盘为 `"9-23"`；`watch_status` 把它原样渲染成 `| 时段 9-23`，看起来「设好了」。实际上这条守**24 小时都在唤醒**，客户以为夜里不会被打扰。
- **为什么还算「值得修」而不是「必须修」**：面板 UI 用的是 `<input type="time">`（`client.js:2112-2121`），产不出非法格式。所以客户走 UI 撞不到 —— 但 `/watch` 是本机 localhost 上的公开写接口，且这条校验工具侧已经有了。两套校验、只修一半，是同一类事故的温床。
- **建议**：`lib/index.js:2028` 换成 `validateActiveHours`，非法返回 400 并带上工具的同一句 reason。

### W2 · 面板「新增」表单缺 4 个建的时候就要定的字段

- **位置**：`client.js:1177-1195`（`addWatcher` 的 payload）· 对照 `client.js:1103-1130`（`saveEdit` 里有）
- **缺**：`sessionMaxWakes`、`isolateKeepDays`、`maxIsolated`、`allowAuthors`
- **客户会遇到什么**：客户勾上「隔离执行」建一条守，想同时设「保留 2 天 / 最多留 4 个」—— 新增表单上没有这两个框，**必须先建好、再点开那一行、再点保存一次**。而这三项恰恰是「不设就会一直累积磁盘」的那类配置，默认值（3 天 / 5 个）不是所有人都合适。
- `allowAuthors` 同理：新建时填不了，只能建完再编辑（而编辑那条路本身是坏的，见 M2）。
- **建议**：`addWatcher` 的 payload 补这四项（`isolateKeepDays` / `maxIsolated` 随 `isolated` 条件显示，与编辑表单保持一致）。

### W3 · 面板能**显示** `ignoreLabels` / `assignee`，却没有任何控件能**改**它们；`ackLabel` 连显示都没有

- **位置**：`client.js:626-633`（`filterText` 会渲染「排除: wontfix」「只看指派给 @octocat」）· `lib/index.js:1731-1779`（`/state` 的 watcher 映射里**没有** `ackLabel`）
- **客户会遇到什么**：客户在总览的徽章行看到 `排除: wontfix`，想知道怎么加一个、怎么去掉 —— 点开编辑表单，里面只有「只处理这些标签」，没有「排除」。他会怀疑自己看错了，或者以为这是个只读的展示字段。
- **方向二的后果**：`ackLabel` 只能由模型经 `watch_start` 设，而 `/state` 不回传、面板不显示 —— **客户永远不知道 ack 标签被改过**。而 ack 标签是「这条处理完了」的唯一凭据，改错了整条守就失效。
- **建议**：二选一，别停在中间：(a) 编辑表单补「排除这些标签」「指派给」两个输入框 + 一个只读的「ack 标签」展示行；或 (b) `filterText` 去掉这两个不该出现的字段，并让 `watch_start` 的 `ignoreLabels`/`assignee` 在文档里标明「仅模型可设」。

### W4 · `watch_status` 不回传 9 个可写字段 —— 模型设完无法自查

- **位置**：`lib/watch.js:1128-1150`（`statusView` 的 watcher 投影）
- **缺的字段**：`batchLimit`、`maxWakesPerHour`、`sessionMaxWakes`、`isolateKeepDays`、`maxIsolated`、`ackLabel`、`workdir`、`priority`、`ignoreLabels` / `assignee` / `allowAuthors`
- **客户会遇到什么**：模型设了 `batchLimit: 3`，下一轮 `watch_status` 一个字不提。模型要确认「到底设上没有」，只能再调一次 `watch_start`（幂等覆盖，但是盲写）或者去读状态文件（它读不到）。**这是模型侧的信息黑洞**：它写进去的配置，自己看不见。
- **对照**：面板侧的 `/state`（`lib/index.js:1731-1779`）回传了其中大部分（`batchLimit`、`maxWakesPerHour`、`sessionMaxWakes`、`isolateKeepDays`、`maxIsolated`、`workdir`、`priority`）—— 也就是说**面板看得见，模型看不见**。
- **建议**：`statusView` 补齐这几个标量字段（`priority` 可只回「关掉了哪几个」，别整对象回传）。

### W5 · 面板能**真删**，工具只能**停** —— 模型无法释放名额

- **位置**：`lib/watch.js:519-522`（`action === 'delete'` 直接 `delete watchers[id]`）· 对照 `lib/index.js:2979`（`watch_stop` 只 `enabled = false`）
- **客户会遇到什么**：模型没有办法「删掉一条守」。它只能说「停了」。停掉的守仍然占面板一行、仍然计入 M1 的那个 20 条上限、仍然出现在 `/state` 里。客户被告知「已经停了」，回头一看列表里还是 20 条。
- **与 M1 的关系**：M1 让这件事变成死结；即使 M1 修好，「模型停掉的守永远留在列表里」也不对。
- **建议**：`watch_stop` 加 `purge?: boolean`（默认 `false` 保持兼容），`purge: true` 时走 `applyWatcherAction({action:'delete'})`；或在 M1 的报错文案里明确写「模型也可以让你 purge」。

### W6 · 面板有 `priority` 5 个开关，工具一个都设不了

- **位置**：`client.js:1398-1403`（重开优先 / 评论优先 / 标签优先 / 未认领优先 / 积压优先）· `watch_start` 参数表（`lib/index.js:2736-2755`）里没有 `priority`
- **客户会遇到什么**：客户跟模型说「关掉『未认领优先』，这是你们的判断不是规则」—— 模型没有任何参数能表达，只能回「请到面板里点」。**只有面板有的能力**，而且是一项会影响处理顺序的判断。
- **建议**：`watch_start` 补 `priority?: object`（或拆成 `priorityUnassigned` / `priorityStale` 这类扁平布尔），与面板同名字段对齐。

### W7 · HTTP 路径 `intervalSec` 不取整，同一个值两条路存成两个数

- **位置**：`lib/index.js:1977`（HTTP）· 对照 `lib/index.js:2798`（工具）
- **差别**：工具 `Math.round(...)`，HTTP 没有。
- **客户会遇到什么**：`intervalSec: 30.7` 经面板接口存进去就是 `30.7`，面板显示「每 30.7s」、`watch_status` 也显示 `30.7` —— 看起来像浮点 bug。工具走同一个值会存成 `31`。
- **建议**：`lib/index.js:1977` 补 `Math.round(...)`。

### W8 · `watch_doctor` 把路由总数写死成 `/6`，实际是 9 条

- **位置**：`lib/index.js:2543`

```js
lines.push(`WARN 面板接口部分失败（${mounted}/6 成功）：${failed.join('；')}`)
```

- **客户会遇到什么**：真出现挂载失败时（`lib/index.js:2542` 那个分支），客户会看到「面板接口部分失败（8/6 成功）」—— **分子比分母大**。第一反应是「插件坏了」，而不是去看后面那句真正的失败原因。
- **建议**：`/6` 换成 `attempted.length`（同函数内有这个变量，`lib/index.js:1694`）。
- **附**：正常路径那句 `OK 面板接口挂载：${mounted} 条，无失败` 用的就是变量，所以只有失败分支会露馅。

### W9 · 工具路径没有「添加前体检」，`repoAccess` 永远是空的

- **位置**：`lib/index.js:2054`（`precheckRepo` 只在 HTTP 的 create 分支调）· `watch_start` 全程没有等价调用
- **客户会遇到什么**：面板建的守会告诉客户「这个仓库归档了 / 没开 Issues / 你是只读」，模型建的守什么都说（`entry.repoAccess` 不会被填，面板那行徽章是空的）。同一个仓库，换个入口建，提示就消失了。
- **建议**：`watch_start` 在 `!existing` 时也调一次 `precheckRepo`，把 `warnings` 放进返回值（文本和 JSON 两个分支都要）。

### W10 · `isolated` 但没给 `workdir` 时，两条路的默认值不同

- **位置**：`lib/index.js:2035`（HTTP 会兜底成 `process.cwd()`）· 工具路径没有兜底
- **客户会遇到什么**：面板建的隔离守能正常跑；模型建的隔离守会在 `watch_doctor` 里报 `WARN 隔离开着但没有 workdir，会在宿主 cwd 里建 worktree（lib/index.js:2637）`。**同一个配置，一个告警一个不告警**，客户会以为是自己设错了。
- **建议**：`watch_start` 里 `isolated === true && !entry.workdir` 时也兜底成 `process.cwd()`，或者两条路都别兜底、都靠 doctor 提示。

### W11 · 追溯文本两套模板（已经漂过一次）

- **位置**：工具 `lib/index.js:2472-2478` · HTTP `lib/index.js:2182-2185`
- **差别**：工具是 `  水位 seen：…` / `  被过滤（reason）：at` / `  唤醒尝试：at　成功`（全角冒号 + 两格缩进）；HTTP 是 `水位 …` / `被过滤（reason）at` / `唤醒尝试 at　成功`（无缩进、无冒号）。
- **客户会遇到什么**：同一件事，模型转述给客户时是一套措辞、客户自己在面板上点「追溯」是另一套。改文案要改两处 —— 这个仓库里已经有 `noTraceText`（`lib/index.js:62`）和 `UNCHANGED_TEXT`（`lib/index.js:58`）两处「两入口必须逐字一致」的注释，说明团队知道这个风险，但 trace 这两段还是各写各的。
- **建议**：把两段渲染收成一个函数（例如 `formatTraceText(traces, scope)`），HTTP 直接复用。

### W12 · `watch_start` 无条件把 `enabled` 置 `true` —— 只想加个标签，会把暂停的守悄悄恢复

- **位置**：`lib/index.js:2831`（工具：`entry.enabled = true` 无条件执行）· 对照 `lib/index.js:2039`（HTTP：`body.enabled === undefined ? isEnabled(entry) : …`，不传就保持原值）
- **面板侧的原话**（`lib/index.js:2038` 的注释）：「没传 enabled 就保持原值：只改间隔/标签不该把暂停的 watcher 悄悄恢复」。**这条政策工具侧没有遵守。**
- **客户会遇到什么**：客户把某个仓库的守暂停了（比如休假）。模型在后面的会话里调 `watch_start({repo: X, labels: ['bug']})` 只想加个标签 —— 落盘后 `enabled` 变成 `true`，那条守开始轮询，然后半夜把会话叫醒。客户明确暂停过的东西，被一句「改个标签」解除了。
- **两种读法**（所以放「值得修」而不是「必须修」）：也可以认为 `watch_start` 的语义就是「开始看」，`enabled = true` 是有意的。但那样的话**面板的 `saveEdit` 就缺一个「恢复」的动作**，两边的语义模型不同，应该在文档和提示里说清楚。
- **建议**：工具侧改成 `if (typeof args.enabled === 'boolean') entry.enabled = args.enabled`（新增一个 `enabled` 参数），默认不传就保持原值 —— 与 HTTP 对齐；或者反过来给面板的 `saveEdit` 加 `enabled: true`，并接受「编辑即恢复」。
- **取证**（真实运行）：

```
1) 工具停掉后 enabled = false
2) 再调一次 watch_start（只想加个标签）→ enabled = true ← 被悄悄恢复
3) 面板这一条停掉后 enabled = false
4) 面板保存（只改间隔/标签，不传 enabled）→ enabled = false ← 保持暂停
```

## 三、对等

以下是逐项核过、**确认两边一致**的（不是「看不出问题」，是「两边跑了同一个函数 / 同一个常量」）：

**另外两处「刻意不对等」**（不是缺陷，写下来免得下次被当成漏掉）：

- **`github` / `repo_here` 没有面板对应物**。这是设计意图：凭据留在插件里、不进模型（`lib/index.js:2693` 的 description 写得很明确）。面板侧不需要「调 GitHub API」这个能力 —— 它自己的 `/state`、`/trace`、`/diagnose` 已经覆盖了客户要看的。
