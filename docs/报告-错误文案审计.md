### 三问 + 三类（判据写死，后面逐条套）

1. **说清是什么错了吗**——具体到「哪个字段 / 哪个来源 / 什么状态码」？`failed` / `error` / `undefined` 不算。
2. **给了下一步吗**——可执行动作（跑 / 填 / 等 / 检查 / 确认 / 换 / 刷新）。
3. **把内部实现泄漏给客户了吗**——堆栈、内部函数名、`undefined`、`[object Object]`、绝对路径、内部 id、英文内部状态名、token。

| 类别 | 下一步的写法 | 判据 |
|---|---|---|
| **客户能自己解决** | 一个**具体动作 + 去哪**（「先点恢复」「去掉 # 号」「显式传 repo」） | 正确反应是「动一下手」 |
| **只能等** | 明确「会自己好 / 多久 / 不用管」 | 正确反应是「什么都别做」——写错会让人瞎折腾 |
| **要报障** | 明确「收集什么 + 贴给谁」 | 正确反应是「别重试，去报」 |

### M1 `lib/index.js:2406`（watch_trace）/ `lib/index.js:2304`（watch_ack）——「number is required」是**假话**

**原文**

```js
// lib/index.js:2406-2408（watch_trace）
const rawNumber = args.number == null ? '' : String(args.number).trim()
if (!/^[A-Za-z0-9_-]+$/.test(rawNumber)) {
  return (args && args.format === 'json') ? JSON.stringify({ schemaVersion: 1, error: 'number is required' }) : '[error: number is required]'
}
// lib/index.js:2300-2304（watch_ack）同一个坑：先按逗号切、再按字符集过滤，被过滤掉就报「必填」
if (numbers.length === 0) return toolError(args, 'number (or numbers) is required')
```

**真跑**（`watch_trace` / `watch_ack` 都传 `number: '#14'`，`%TEMP%\sa-audit\out-tools.txt` 原样）

```
--- watch_trace({ number: '#14' }) ---
[error: number is required]

--- watch_ack({ number: '#14' }) ---
[error: number (or numbers) is required]
```

**客户/模型看到之后会怎么做（以及为什么那是错的）**

编号**明明给了**（`#14` 就是从 issue 页面复制的形状，`lib/index.js:2299` 的注释自己写了「看着像用户没填」）。模型唯一合理的推断是「我漏传了」→ 它会**原样再传一次 `#14`**，拿到同一句报错，然后要么死循环重试、要么转头问客户「你要处理哪个编号」——而客户刚把编号给它。

这条尤其贵：`watch_ack` 是**每条主理任务的最后一步**（不打标签下一轮还会叫醒），一次假报错就等于这条 issue 永远关不掉。

**分类**：客户能自己解决（改写法即可）——**但文案把「写法不对」说成了「没给」。**

**建议文案**

```js
// watch_trace
`[error: 编号要写成 14，不要带 # 号（收到的是 "${rawNumber}"）—— 去掉 # 再试一次]`
// watch_ack
`[error: 编号要写成 14 或 12,13，不要带 # 号（收到的是 "${String(args.numbers || args.number)}"）—— 去掉 # 再试一次]`
```

同一份 `lastError` 在 `/state` 里是完整的（`%TEMP%\sa-audit\out-routes.txt`）：

```json
  "lastError": "HTTP 401: Bad credentials（gh 登录失效：跑 gh auth login，或在面板填 token）",
```

**客户/模型看到之后会怎么做（以及为什么那是错的）**

- 模型跑 `watch_status` 只看到「HTTP 401: Bad credentials」——**它有现象、没有动作**；它可能去猜「要不要重试」，而正确动作是「跑 `gh auth login`」。

**分类**：取决于 kind——auth / permission 是「客户能自己解决」，ratelimit / network 是「只能等」。**现在两类都被抹平成一句没有动作的话。**

**建议文案**

```js
// 1) 走与面板同一个拆分（现象截断、建议完整）
const { main, hint } = splitErrorTextLite(w.lastError)   // 抽到 lib/gh-format.js，client.js 与 server 共用
if (w.lastError) problems.push('上次失败：' + main.slice(0, 60) + (main.length > 60 ? '…' : '') + (hint ? ' ' + hint : ''))
// 2) statusView() 增加 lastErrorKind（与 /state 同源）
lastErrorKind: w.lastError ? classifyGhError(String(w.lastError)).kind : null,
```

（对比：同一套渲染下 401 那条多了 `（gh 登录失效：…）` 和「去填 token」按钮。）

**客户/模型看到之后会怎么做（以及为什么那是错的）**

三处都错：

1. **归错了类**。「轮询失败」是错的——轮询成功了，是**唤醒**失败。客户会去查网络 / token / 仓库权限（轮询相关），而真正的问题在会话。
2. **英文内部原因**。`session not live` / `no followup/steer/inbox on agent` 是宿主 API 的形状，不是人话。后者客户看到只会一脸问号（它意味着宿主版本不兼容，要**升级宿主**，不是重试）。
3. **没有下一步，也没有按钮**。`classifyGhError('wake failed: …')` → `kind: 'other'` → `FIX['other']` 不存在（`client.js:1355`）→ 面板只留一句红字。而这条恰恰是**最需要人动手**的一类（删守 / 升级宿主 / 重试，三者动作完全不同）。

**分类**：**要报障**（`no followup/steer/inbox` = 宿主版本不兼容）、**客户能自己解决**（`session not live` = 删掉这条守）、**只能等**（`agent busy` = 3 秒合并窗口里会话转忙，下一轮就好）。**现在三条被压成同一句英文。**

**建议文案**

```js
// lib/watch.js — 按 reason 给不同的「下一步」，别再拼英文原文
const WAKE_FAIL = {
  'session not live':             '唤醒失败：宿主里找不到这个会话（可能已被删除）—— 到面板确认会话还在；不在了就删掉这条守，还在就点「立刻」重试',
  'no followup/steer/inbox on agent': '唤醒失败：宿主不支持投递消息（版本太旧）—— 先升级 DSH 宿主；升级前这条守只记录不唤醒',
  'merged empty':                 '唤醒失败：这一批没有可投递的内容（可能刚被 ack 掉）—— 下一轮会自动重试，不用处理',
  'agent busy (running)':         '会话正忙，这一轮没投递：下一轮自动重试，不用处理',
}
error: WAKE_FAIL[String(reason || '')] || ('唤醒失败：' + String(reason || '') + ' —— 跑 watch_doctor 看检查清单，或把这行贴给对方'),
```

### M4 `lib/index.js:2714` + `2722`——推断仓库失败时把 `undefined` 当仓库名报给客户

**原文**

```js
// lib/index.js:2711-2715
let repo = args.repo
if (!repo) {
  const res = await run('gh', ['repo', 'view', '--json', 'nameWithOwner'], { cwd: process.cwd(), env: ghEnv() })
  try { repo = JSON.parse(res.stdout).nameWithOwner } catch { return `[error: cannot infer repo]\n${redact(res.stderr)}` }
}
// …
if (bad.length > 0) return toolError(args, '仓库要写成 owner/name 或 gitee:owner/name，这些不对：' + bad.join(', '))
```

**真跑**（`gh repo view` 返回的 JSON 里没有 `nameWithOwner`，`%TEMP%\sa-audit\out-tools.txt`）

```
--- watch_start({})（不给 repo，gh repo view 返回 {full_name:...}） ---
[error: 仓库要写成 owner/name 或 gitee:owner/name，这些不对：undefined]
```

**客户/模型看到之后会怎么做（以及为什么那是错的）**

`JSON.parse(res.stdout).nameWithOwner` 是 `undefined` 时**不抛错**，所以 `catch` 那条「cannot infer repo」永远不会触发；`undefined` 一路走到 `String(repo)` 变成字符串 `'undefined'`，最后被当成「客户写错的仓库名」报出来。

模型看到 `这些不对：undefined` 会得到两个错误结论之一：**(a) 照字面再传 `repo: "undefined"`**（然后拿到 `只支持 github.com 与 gitee.com` 之类的二次错误）；**(b) 以为客户填错了**，去追问一个客户根本没填的字段。正确动作是「显式传 `repo`」或「先 cd 到有 git remote 的目录」——**一个字都没说**。

**分类**：客户能自己解决（显式传 repo / 换目录）。

**建议文案**

```js
if (!repo) {
  const res = await run('gh', ['repo', 'view', '--json', 'nameWithOwner'], { cwd: process.cwd(), env: ghEnv() })
  try { repo = JSON.parse(res.stdout).nameWithOwner } catch { repo = undefined }
  if (!repo) {
    return toolError(args, '没法从当前目录推断仓库（gh repo view 没返回 nameWithOwner）—— 请显式传 repo: "owner/name"，或先 cd 到带 git remote 的仓库目录')
  }
}
```

### M6 `lib/index.js:1907-1909`——HTTP 错误体直接当客户文案：`watcher is paused` / `unknown watcher: …` / `already polling`

**原文**

```js
// lib/index.js:1905-1909
if (action === 'poll') {
  const entry = state.watchers && state.watchers[id]
  if (!entry) return json(res, 404, { error: 'unknown watcher: ' + id })
  if (!isEnabled(entry)) return json(res, 409, { error: 'watcher is paused' })
  if (inFlight.has(id)) return json(res, 409, { error: 'already polling', id })
```

面板拿到后**原样显示**（`client.js:1079-1081` → `notice.text` → `client.js:2158`）。

**真跑**（`%TEMP%\sa-audit\out-extra.txt`，真渲染 `client.js` 的提示条）

```
--- 面板提示条："watcher is paused" ---
可见：watcher is paused

--- 面板提示条："unknown watcher: a/b#s1" ---
可见：unknown watcher: a/b#s1

--- 面板提示条："already polling" ---
可见：already polling
```

**客户/模型看到之后会怎么做（以及为什么那是错的）**

这三条是**面板上最常点到的两个按钮**（「立刻」）的失败路径：

| 客户点了什么 | 看到什么 | 它会怎么做 | 正确的下一步 |
|---|---|---|---|
| 已暂停的守上点「立刻」 | `watcher is paused` | 以为坏了，重复点；或者去查网络 | 先点「恢复」，再点「立刻」 |
| 面板快照过期（守已被删） | `unknown watcher: a/b#s1` | 以为自己填错了仓库名；`a/b#s1` 这个 id 他没见过 | 刷新面板 |
| 连点两次「立刻」 | `already polling` | 以为卡住，越点越急 | 等这一轮跑完（约 30–60 秒） |

三条都同时犯了「英文 + 内部 id + 无下一步」。`a/b#s1` 里 `#s1` 是本会话 id 的截断，`gitee:` 前缀更会带出 `gitee:a/b#s1` —— 客户没有任何办法理解。

**分类**：全是**客户能自己解决**（点恢复 / 刷新 / 等），但文案让人往「坏了」的方向想。

**建议文案**

```js
if (!entry) return json(res, 404, { ok: false, id, error: '这条守已经不在了（可能被别处删掉）：刷新面板再操作' })
if (!isEnabled(entry)) return json(res, 409, { ok: false, id, error: '这条守已暂停：先点「恢复」，再点「立刻」' })
if (inFlight.has(id)) return json(res, 409, { ok: false, id, error: '这一轮已经在跑：等它跑完（约 ' + Math.round((Number(entry.intervalSec) || 60)) + ' 秒）再点，不用重复点' })
```

## 三、确认合格

> 逐条说明「审了什么、为什么算合格」。**没有真跑的会标出来。**

### 3.1 分类器（`classifyGhError`）：7 类 + 兜底，全部有非空且可执行的 hint

**真跑** `node scripts/audit-error-hints.mjs`（原样）

```
检查 7 类错误的建议文案（上限 60 字符）
---
PASS auth      35 字符　动作=跑
PASS ratelimit 31 字符　动作=等
PASS gateway   43 字符　动作=检查
PASS nogh      22 字符　动作=确认
PASS notfound  43 字符　动作=检查
PASS network   35 字符　动作=不需要手动处理
PASS other     50 字符　动作=跑
---
PASS 覆盖 7 类错误
```

**为什么合格**：① 每类 ≤60 字（面板窄，超了折三行）；② 每类都含可执行动作；③ 兜底 `other` **不是空的**（50 字，含「跑 watch_doctor」）——这正是 `docs/kb/error-must-have-next-step.md` 要的「兜底不必聪明，但必须有下一步」。Gitee 的三种形状（`Access token does not exist` / 中文 `登录失效，无权限访问该资源` / 429）在 `lib/gh-format.js:94-124` 里排在 GitHub 之前，不会被抢走。

### 3.2 `watch_doctor`：FAIL / WARN / OK / INFO 四档都写了「怎么处理」

**真跑**（`%TEMP%\sa-audit\out-tools.txt`）

```
FAIL 凭证失效（1 条守）：跑 gh auth login 重新登录，在此之前这些守只会一直失败 —— 它不会自己恢复
OK 版本一致：0.9.234
WARN 还没有挂载记录（刚装上或从未加载过路由）
OK   gh 登录：正常
OK   r0/x 可访问：{"full_name":"r0/x","private":false,"items":[],"total_count":0}
OK   gh 账号：使用宿主当前登录的账号（未绑定独立配置目录）
OK   ack 标签「主理鱼:已处理」：已存在
INFO 运行中 · 上次轮询 无 · 正常
```

**为什么合格**：这是全仓文案质量最高的一块——每条都「现象 + 动作」，且**不吓人**（`INFO … 刚重启，等下一轮即可`、`WARN … 定时器可能丢了` 分级正确）。`FAIL 凭证失效` 还额外说了「它不会自己恢复」（对应 `docs/kb/credential-failure-never-self-heals.md`）。

### 3.3 `watch_ack` 的「可恢复 / 需要处理」二分

```js
// lib/index.js:2348-2361
const retryable = ['network', 'ratelimit', 'gateway'].includes(why.kind)
const advice = retryable ? '暂时失败，稍后再 ack 一次即可' : '需要你处理'
return retryable ? `[error: #${failed.number} ${advice}（${label}）]` : `[error: #${failed.number} ${advice}] ${why.hint}`
```

**为什么合格**：两类文案**不重复**（可恢复的只说「要等」，不可恢复的只说「做什么」），JSON 里另给 `kind` / `retryable` / `advice` 供程序判断。符合 `docs/kb/failure-classes-need-different-actions.md` 的判据。
**没真跑**：`watch_ack` 真跑会往 GitHub 写标签（`POST …/labels`），审计不改仓库，所以这条只有代码 + 单测覆盖（`test/` 里 6 种错误的可恢复性），**没有生产输出**。

### 3.4 `parseRepoSpec`：四种「写错了」都有具体原因

```js
'repo 不能为空' / '只支持 github.com 与 gitee.com 的地址' / '要写成 owner/name'
'owner/name 只能包含字母、数字、下划线、点、短横线' / 'owner/name 不能是 . 或 ..'
```

**为什么合格**：全部**说清是哪一段不对**（不是 `invalid repo`），且都能直接告诉客户「改成什么」。`/watch` 路由与 `watch_start` 工具共用同一个解析器（`lib/index.js:1931` / `2720`），不会两套说法。

### 3.5 `github` 工具的两条前置校验

**真跑**（`%TEMP%\sa-audit\out-tools.txt`）

```
[error: path must be a GitHub API path, not a flag]
[error: PATCH requires confirm: true — this plugin never writes to GitHub without an explicit flag]
```

**为什么合格**：第二条把「为什么要有这个 flag」也说了（`never writes to GitHub without an explicit flag`），模型不会试图绕过。第一条挡住了 `-X` 注入。**唯一小瑕疵**是 `unsupported method TRACE` 没列可用方法（已记 S6）。

### 3.6 面板的「下一步按钮」映射完整

**真跑**（`%TEMP%\sa-audit\out-panel.txt`，真渲染）

```
=== 面板 · 401（lastErrorKind=auth） ===
… a/b 轮询失败：HTTP 401: Bad credentials （gh 登录失效：跑 gh auth login，或在面板填 token） …

```

**为什么合格**：`auth → 去填 token`、`moved/notfound → 改仓库地址`、`network/ratelimit/gateway → 立刻重试`、其余**不给按钮**（不猜）——与 `docs/kb/error-needs-a-button.md` 的表格逐行对得上。`needsReauth` 还有一条独立红条：「凭证失效：跑 gh auth login 重新登录 —— 它不会自己恢复，在此之前这条守只会一直失败」。

### 3.7 `splitErrorText` 的拆法本身对

```js
// client.js:683-688
const match = /（[^（）]*）\s*$/.exec(value)   // 只认「末尾一整个括号」
```

**为什么合格**：用 `[^（）]*` 而不是贪婪匹配，`（甲）（乙）` 会只取最后一个括号；没有括号时 `hint=''` 不报错。**问题在调用方**（M2 没用它、S5 只用 main），不在这个函数。

### 3.8 `quotaDeferText`：reason 稳定、时间只在人读的那句

```js
{ reason: 'quota', text: '额度紧张（剩余 12），已推迟到 09:30 UTC' }
```

**为什么合格**：`deferReason` 是稳定的 `'quota'`（面板按 reason 筛选不会空——这正是 `lib/index.js:1197` 记的 T20 教训），时间只出现在 `text` 里。

### 3.9 `sessionMissingVerdict`：把「宿主刚启动」和「真被删了」分开

```js
// 宽限期内：'会话尚未就绪（宿主可能刚启动）：约 N 分钟后仍找不到才报错'
// 过了宽限期：'会话已不在（连续 N 分钟找不到）：确认该会话是否已被删除，再决定是否重建这条主理鱼'
```

**为什么合格**：真机事故（2026-11-04 重启后第一轮就报「请删除或重建」）的修法是对的——**不可逆建议必须等**，且两句话都给了时间量。这是全仓唯一一条「等到 N 分钟才说」的文案。

### 3.10 `repoStructureNote` / `accessNote`：仓库结构问题提前说

```js
'… 关闭了 Issues —— 主理鱼只认 issue / PR，这里不会有任何条目可接。'
'… 是 X 的 fork。fork 默认不带 Issues，issue 大多落在上游 —— 确认你要守的是哪一个（守上游就把仓库填成 X）。'
'你对 a/b 只有读权限：能看、能被叫醒，但没法回写评论或打标签 —— 要么换有写权限的 token，要么把结论写在本地/PR 描述里。'
```

**为什么合格**：「现象 + 为什么 + 两个具体选项」，且 `fork` 那条直接把正确写法（上游全名）给出来了。

### 3.11 `pickSuggestion`：404 之后给「是不是想填 X？」

```js
if (picked) hint = ' 是不是想填 ' + picked + '？'
// → '仓库 a/bc 不存在，或当前 token 没有访问权限 —— 先确认名字（owner/name）与权限。 是不是想填 a/b？'
```

**为什么合格**：这是「猜得准就说，猜不准不说」——只在 search 真的有结果时才拼这句，且**问句形式**（不替客户决定）。同时受 `docs/kb/404-is-not-always-missing.md` 约束（404 也说「或没权限」）。

### 3.12 Gitee 的三形态覆盖

**为什么合格**：三种真机形状（2026-11-05 本机 curl 复刻，注释里有原始字节数 7187）都有专门分支，且**没有**放宽成裸 `404` / 裸 `Not Found`（否则会抢走 GitHub 的提示）。429 那条还额外提醒「Gitee 上未带私人令牌的额度低得多 —— 先确认令牌已填」，把「等」和「填」两个动作分开了。

## 四、找矛盾：同一个失败，三种说法

> 这是审计里最有价值的一张表：**同一份 `lastError` 在四个面上的可执行性递减**。

### 4.1 401 Bad credentials（最常见）

| 面 | 客户/模型看到 | 有下一步吗 | 能点吗 |
|---|---|---|---|
| 工具 `github` | `HTTP 401: Bad credentials` + `（gh 登录失效：跑 gh auth login，或在面板填 token）` + `[exit code: 1][kind: auth]` | ✅ | — |
| 面板行 | 现象 + 建议 + **「去填 token」按钮** | ✅ | ✅ |
| 弹层（常驻） | `HTTP 401: Bad credentials`（hint 被 `splitErrorText(...).main` 丢掉，只有 hover 的 title 里有全文） | ❌ | ❌ |
| `watch_status` | `上次失败：HTTP 401: Bad credentials`（`split('（')[0]` 无条件切掉建议） | ❌ | — |
| `/diagnose`（报障用） | `错误: <前 160 字>`（180 字现象之后全丢） | ❌ | — |

**结论**：同一个失败，**5 个面 2 个可执行**。M2 / M5 / S5 就是在修这张表。

### 4.2 唤醒失败

| 唤醒消息 | —（失败时根本没有消息） | — |

### 4.3 会话/全局上限

| 面 | 看到 | 形式 |
|---|---|---|
| 工具 `watch_start` | `一条会话最多同时挂 20 条在跑的守（现在 20 条，这次要新增 1 条）—— 先 watch_stop 停掉不用的，或把多个仓库合成一条规则` | **纯文本，无 `[error:`**（S1） |

## 八、顺带发现（这次没动，也不该由这次审计定）

1. **版本号漂移**：`package.json` / `SERVER_VERSION` = `0.9.233`，`client.js` 的 `CLIENT_VERSION` = `0.9.234`。`watch_doctor` 因此会输出 `OK 版本一致：0.9.234`（它比的是 `installedVersion()` 与 `SERVER_VERSION`，不碰客户端常量）。本次审计不判断这是不是漏提交，只记一笔。
2. **工作区有未提交改动**：`git status` 显示 ` M docs/派单表.md`，**不是本任务改的**（本任务只新增本文件）。按只读约束没有碰它。
3. **`watch_status` 的 JSON 契约缺口**：`statusView()` 的 16 个字段里没有 `lastErrorKind`/`lastErrorAt`，而 `/state` 有。面板靠 kind 选按钮，模型只能读中文——这跟 `docs/kb/contract-snapshot.md` 的方向相反（结构化字段该先于中文）。已记 M2。
